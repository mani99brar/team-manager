# Engine worker: a reviewer for each lane (PRD_LANE_REVIEWER)

## Goal

A feature.json 2.9.0 lane may declare `lane_review: {reviewers: [1 to 4 {transport, model, effort?}], rounds?, timeout_minutes?, budget_usd?}` (PRD section 3). After that lane passes its own verification and before the candidate is built, the controller has those reviewers review the lane's diff only, in parallel; a P0 or P1 from any of them starts one fix round of that lane through the existing repair loop, and the lane is verified again. A provider failure is recorded and never blocks the run. A lane without `lane_review`, and every feature before 2.9.0, runs byte for byte as today. `docs/PRD_LANE_REVIEWER.md` sections 3, 4 and 7 are the specification; `features/lane-reviewer/decisions.md` records the operator's decisions and wins over this task where they differ.

## Context

- Graph (`workflow/pipeline.py` `build_pipeline`): `launch_<lane>` → `handoff` (freeze) → `verify_<lane>` → `candidate` → `review` → `approval` → `integrate`. The automatic loop is `workflow/automatic.py` `drive`; failures go through `advance_or_block`, `fix_decision`, `fix_round` (the in-run fix loop, RUNBOOK "In-run fix loop", `plan.automatic.fix_rounds`, `repair_timeout_seconds`). A blocked `verify_<lane>` packet reaches a repair through `fix_decision` → `fix_round` (trigger `verify`) → `workflow/repair.py` `repair_session` / `launch_session` / `session_brief(findings=...)`; the repair forks the graph at the freeze boundary and the lane is re-verified. A lane-review block takes this route (decisions.md [L1], [L2]): trigger `verify`, `origin: "lane-review"` in `repairs.json`, findings passed as `findings=`, its own round count.

## Design (default; decisions.md wins)

- Placement and gate (decisions.md [L1], [L2], [L3]; [L3] wins where they differ): the block is re-derived from the (lane, snapshot) record on every entry to `verify_<lane>` after `verify_revision` returns, never read back from the saved packet; the lane review runs inside `verify_<lane>` after the policy checks pass, with a `running` event when the review starts. A P0/P1 blocks that verify packet only when the plan is automatic, `fix_rounds(plan) > 0`, the lane has rounds left and `len(applied repairs) + 1 < MAX_REPAIRS`; it blocks it with `lane-review:` gate reasons that the check-retry path never reruns; the existing fix loop repairs it with trigger `verify` and `origin: "lane-review"` in `repairs.json`; those repairs count against `lane_review.rounds`, not `--fix-rounds`. Rounds used up: the packet passes, open findings recorded and passed to the run reviewers. A lane-review repair that ends blocked counts as a spent round: no `exhausted`, the packet passes with findings recorded, and `fix_decision` recognises a lane-review block by its `lane-review:` gate reasons, applies only `lane_review.rounds` to it and leaves lane-review sessions out of its ordinary count and last-blocked test; a resumed round takes `origin` and `brief.findings` from the open journal entry. The review record is keyed by (lane, snapshot commit); a resume, a fork or a sibling's failure reuses a terminal record instead of restarting reviewers.
- Brief: a bundled lane brief (for example `workflow/prompts/lane-review.md`): review this lane's diff against its task, `decisions.md` and the PRD; report only defects, as the panel's output schema.
- Findings are untrusted data ([L1] e, [L2] d): cap each field; gate reasons stay short (`lane-review: <severity> <file>:<line> <title>`); the full findings go to the repair through `findings=` (quoted as data, with the note that they are claims to check against the code), never as raw gate-reason text into events or error messages.
- Failure: a reviewer's start failure, timeout or unparseable reply → record `failed` with the error; the others still count; all failed → the lane passes unreviewed. Kill provider process groups in a `finally`. Never raise into the graph except a KeyboardInterrupt.
- Order: land review-only (`rounds: 0`: review, record, pass findings on) with its tests first, then the repair route ([L1] e).
- Records: `<run>/lane-review/<lane>/<n>.json` (schema `contracts/workflow/lane-review.schema.json`), event `lane_review` on the lane, a `status` line per lane. No export or viewer change.
- Handoff must say the repair route's value is unproven and the operator should read the first review-only run's findings before relying on it ([L3](d)).
- Docs: RUNBOOK section "Lane reviewer (feature.json 2.9.0)", the README feature.json table, `docs/handoff/lane-reviewer.md` (what changed, how to turn it on, every open P2).

## Constraints

- Owned paths only: `workflow`, `contracts/workflow`, `docs/handoff/lane-reviewer.md`. Do not touch `contracts/projects`, `server`, `src` or the export.
- The panel stays report-only and byte-for-byte the same in behaviour; the run's reviewers, sidecar, attack pass and challenge are untouched apart from receiving open lane-review findings in the reviewers' prompt.
- Module docstrings cite the RUNBOOK section they implement.

## Acceptance

PRD_LANE_REVIEWER section 7 (items 1 to 14), each item with a test the verifier runs through `workflow-unit`, and `test:contracts` for the schemas. Run targeted tests while iterating, then this lane's policy checks once before writing the completion.

## Stop

Stop and report `blocked` when a blocked lane-review verify packet cannot reach the existing `verify` repair route without changing the export's fix-loop section or the packet schema incompatibly, or when adding 2.9.0 would change the launch or flow of any existing feature. Do not widen scope to the viewer, the export, more than four reviewers per lane or a worker spawning agents.
