## server P1 (2)
- [general] Landings are always unknown on the local default branch when the repository has no origin ref. In server/dispatchGit.ts:157, `localDefaultExists` starts false and is only set inside the `if (default_branch && originRef && originSha)` block (dispatchGit.ts:160-161). At dispatchGit.ts:202, `on_default` is `default_branch && localDefaultExists ? ancestor(...) : null`. Input: a local-only repository (refs/heads/main exists, no refs/remotes/origin/main) with an integrated run whose sha is on main. Expected (PRD 5, Landing): "For each of the local default branch and the origin ref: `true` when `git merge-base --is-ancestor <sha> <ref>` exits 0, `false` when it exits 1, and `null` (unknown) when the ref or the object is missing". The local ref is not missing, so on_default should be true or false. Actual: on_default is null for every landing, and the viewer shows 'local main unknown' and counts each one as unknown (GithubColumn.tsx:133-135). No test covers landings without an origin ref (server/dispatch.test.ts:197 only uses a clone). Consequence: for the local-only repositories where runs integrate and never push, the operator never sees which runs landed on local main; every landing reads unknown.  (disposition: open; requirement: Landings: on local and origin is `true/true`; on local only is `true/false`; a sha the clone lacks, or a missing ref, is `null`.)
- [general] After a failed gh read, the repository is read again on every one-minute tick, not after the refresh window. GithubReader.due() (server/dispatchGithub.ts:242-244) looks only at `readAtMs`, and read() (dispatchGithub.ts:252-258) sets `failReason` without recording when the attempt was made. So a repository that has never been read (readAtMs null), or whose refresh failed (readAtMs stays at the old good read, already past the window), is due again on the next tick. Input: gh logged out, rate-limited, timing out or exiting non-zero for a registered repository. Expected: decisions.md [D3]: "GitHub is read with the host's `gh` CLI, timer-driven ([P18]): at most once per repository per 15 minutes". The task: a tick reads a repository only when its last read is older than MD_MANAGER_GITHUB_REFRESH_MINUTES. Actual: one `gh api graphql` call per failing repository per minute, up to 15 times the allowed rate. With 20 s timeouts, the cycle runs back to back. No test covers how often a failed read is retried (dispatch.test.ts:329-346 advances the clock 16 minutes before re-reading). Consequence: when gh is logged out or GitHub rate-limits the host, the server keeps spawning gh and calling GitHub every minute for every repository, which prolongs a rate-limit failure and adds load on the operator's machine and GitHub account.  (disposition: open; requirement: then a one-minute tick that reads whichever is due (older than `MD_MANAGER_GITHUB_REFRESH_MINUTES`))
