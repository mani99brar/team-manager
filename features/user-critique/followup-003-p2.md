For a follow-up run of the engine; the viewer run (004) need not act on them.

1. [P2 general] Export regression for a run that does NOT declare critique but has a native reviewer named `critique`. This run deliberately keeps that id legal outside critique features: the schema no longer reserves it, and test_pipeline.CritiquePrepareTests.test_a_reviewer_named_critique_prepares_when_critique_is_not_declared asserts that it prepares. The base commit's schema allowed the id too. But export_state.reviewer_entries (workflow/export_state.py:209-221) picks the headless-critique branch on `entry["reviewer_id"] == CRITIQUE_ID` alone, never on has_critique(plan). Every other critique hook is gated on plan.critique (critique.py:832/877/935/966/984, export_state.py:281). Inputs: a 2.8.0 feature with reviewers [general, critique], whose native `critique` reviewer launched (receipt review-critique.interactive.json carries launch_requested_at) and either approved or was superseded with a null verdict. Expected, as on main: launched_at from the receipt, and status from automatic-review-critique.json (e.g. `superseded`). Actual: launched_at is read from the native status file's absent `launched_at` key, so it is always null. Status is derived from the verdict alone, so a superseded or pending native reviewer with a null verdict exports `blocked`. Fix: pass the plan (or has_critique) into reviewer_entries and branch only when the plan pins critique. Consequence: an operator viewing an existing (pre-2.9.0) run with a reviewer named `critique` sees no launch time, and sees a superseded or pending reviewer named among the blockers.
2. [P2 general] The `retries` bookkeeping behind PRD 4.4's 'a resume before the review decided reruns a failed critique once' is unreliable in both directions. (a) CritiqueChild.run_job calls save_record('running', ...) (workflow/critique.py:640), which writes retries 0. So when a rerun fails at the job stage (timeout, spent budget, invalid output), save_record('failed') sees an existing 'running' record and writes retries 0 again (critique.py:474-478). settled() (critique.py:799-803) then never reaches retries>=1, and only review.json bounds the reruns: every further exit 75 or crash before review.json reruns the job again, up to $15 and 45 minutes each. test_failed_critique_is_rerun_once_then_settled (workflow/test_critique.py:644-652) passes only because it uses app_mode='crash', which fails in start_app before the 'running' record is written. (b) In the other direction, close_or_wait_critique records a failure for ANY non-interrupt error before review.json (critique.py:944-945), including the 'Prior reviewer invocation needs reconciliation' raise and 'Partial review worktree exists' (automatic.py:1270-1273), which come before the critique was ever started. Each such attempt bumps retries through failed_record (critique.py:811). After two of them the critique is 'settled' as failed without ever having run, and the reconciled review then blocks on a critique null verdict. Consequence: depending on the timing of interruptions, an operator either pays for more than one critique rerun or gets a review blocked by a critique that never ran, with no lane to repair.

6. [P2 general] Two weaknesses remain in the new security hardening. (1) confined_png's magic-byte check (workflow/critique.py:223, 240-245) reads only the first 8 bytes. A Bash command that writes the PNG signature and then appends a host file (`printf '\x89PNG\r\n\x1a\n' > x.png; cat <file> >> x.png` under $RUN/critique/<round>/) still passes, and the file is then hashed, registered and served by the artifact route. The RUNBOOK's 'or is not a PNG is dropped' reads stronger than the check is. A full PNG chunk or IHDR parse, or a statement that only verbatim copies are stopped, would align them. (2) CritiqueChild.cleanup (critique.py:489-499) sends SIGTERM and then SIGKILL to the job's group. When the leader has already exited, the wait loop breaks at once (process.poll() is not None), so the background processes this change aims to reap get SIGKILL with no grace period. It is also untested whether the real `claude` runs Bash commands inside its own process group at all: the test's lingering child is a plain subprocess of the leader. Consequence: a prompt-injected critique can still publish a host file through the run page, and real headless browsers may be killed without cleanup or escape the group kill.
