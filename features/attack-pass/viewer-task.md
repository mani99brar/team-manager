# Viewer worker: the attack pass in the Projects viewer (PRD_ATTACK_PASS sections 4.6, 6 items 8 and 9, Appendix A)

## Goal

The Projects viewer shows a run's attack pass. The server accepts export 1.8.0 and serves the pass's record on its own route, read live from `<run>/attack.json` while the controller rewrites it and else from the export's `attack` section, and a record can never fail a run or the run list. The run page gets an "Attack pass" section, and the graph's `attack` node opens it: a report-only line, the pass status and counts, the verified findings as cards with their label, the rest folded, the attackers and the out-of-reach notes. A run without an attack pass looks exactly as today.

## Design (settled)

- **Contract 1.8.0** in `contracts/projects/v1.ts`: `attackResult`, the Appendix A record with its enums and field rules, its `settings` closed to exactly the eight keys (decisions [L1]) (the export's extra `pending` status included), plus `source: "live" | "export"`; the version history names 1.8.0. Examples and contract tests follow the existing pattern.
- **Server.** `EXPORT_VERSIONS` gains 1.8.0. The export's `attack` section is kept as unknown data and validated only when its route serves it. The route `/:project_id/workflows/:workflow_id/runs/:run_id/attack` serves the live `<run>/attack.json` when it is readable and valid, else the export's section when it is a valid record, else 404 `ATTACK_NOT_FOUND` (a run with `attack: null`, an export before 1.8.0, an unreadable or invalid record); a skipped live file is logged as the sidecar's is. `attack` and the prefix `attack-` join the server's reserved lane ids. The `attack` node's rows never change the run's headline, Now banner, status or verdict: the node only ever gets `running`, `interactive` and a closing `succeeded` (Appendix A), and its rows are excluded where the sidecar's are.
- **Run page.** An "Attack pass" section, listed in the section index, present only when the run's export has a non-null `attack` (or its node exists). It shows, in order: the line "Report-only: never changes the run's verdict"; a headline with the pass status and `<n> finding(s), <r> reproduced, <v> verified`; one card per verified finding with the skeptic's severity, title, threat, requirement (or "No requirement quoted"), the test file path, and its current label (the latest `labels` entry, with review-found and note) or "Unlabelled" with the exact `attack-label` command; then the unjudged, refuted and not-reproduced findings folded under one disclosure, each with its status and re-run reason; the attackers with angle, status, cost and duration; the out-of-reach notes. A `pending` pass says it runs at the review step; a `failed` or `refused` pass shows its error; a run with `attack: null` has no section. The graph's `attack` node (kind `review`; in the exported definition it sits right after `review`, with the same `depends_on`, and `approval` depends on both) is laid out beside `review` and opens a node page that shows the same section component; the graph legend keeps its entries. The page polls the route as the sidecar page does, so a running pass updates without a reload.
- **What the repository needs beyond the analog.** `EXPORT_VERSIONS` must gain 1.8.0 before anything else: the new controller exports every run as 1.8.0, with or without a pass, and an unknown version fails the run (`RUN_STORAGE_INVALID`). `tests/project-workflows/seed.ts` seeds runs only up to 1.6.0 (the sidecar section only at exactly 1.6.0): extend it so the candidate phase seeds 1.8.0 runs with and without `attack`, a live `attack.json` and the `pending` record. `tests/project-workflows/fixtures/index.ts` merges a closed list of payload keys: an attack payload needs its type entry, its merge line, a map in `fixtures.ts` and a route in `mock.ts`, as the sidecar ledgers have. `contracts/projects/contract.test.ts` requires every schema in `schemas` to have an example and a generated `<name>.schema.json` (`npm run contracts:export`), and the contract test reads the Appendix A example from `docs/PRD_ATTACK_PASS.md` verbatim, as it reads the sidecar's Appendix B. The sidecar node is kept from taking the run's focus by exclusions on `SIDECAR_NODE_ID` in `contracts/projects/triage.ts` and in `src/projects/status.ts`, `steps.ts`, `lists.ts` and `node/model.ts` (`nodePhase`): mirror each for `attack`, so the attack node never becomes the run's headline, Now banner or current step and the review keeps them. Events on node `attack` need no controller-row pattern; add one only if a text of Appendix A lands on another node.
- **Pure helper** `src/projects/attack.ts`: counts, the effective severity (the skeptic's for a verified finding), the current label, the folded list's order, and the label command text, with unit tests in `tests/unit/`.
- No execution controls: the viewer never runs `attack-label` or anything else; it prints the command.
