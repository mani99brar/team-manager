# Engine worker: the multi-provider panel in the controller (PRD_MULTI_PROVIDER_PANEL sections 3, 4, 6 item 1, Appendix A)

## Goal

A `feature.json` 2.6.0 feature can declare `panels`, and its run gets each panel at the stage it names (`challenge` or `review`): a **detached child** (`python -m workflow.panel <run> <stage>`) with a running marker and a pid-cmdline liveness check — exactly like the attack pass — assembles one read-only context file (each section labelled with a canonical repo-relative path) and runs one provider job per `providers[]` entry through a transport adapter (`claude` on the print path, `pi` on `pi -p --mode json`). Each job reviews the same context file and returns findings; the child normalizes them (canonical-path anchoring), computes cross-provider overlap, marks each `accepted` per the panel's `overlap_threshold`, and writes `<run>/panel.json` (Appendix A), the `panel-<id>` node's events, the cost records and, when a panel ends with at least one accepted finding, one attention record. The panel is report-only: it never blocks, never changes the run's verdict, and never raises into the run — a provider or panel that fails, times out or returns nothing changes nothing. A feature without `panels`, every older feature version and every run prepared before this change behave exactly as today. **Scope: this slice builds the `review` stage only; `stage: challenge` is refused at launch and its wiring (the no-wait path, the reaper for a child that outlives a paused controller, the pinned-sources challenge context, the challenge view) is the follow-up slice (PRD §5 step 3), with the config/schema kept stage-agnostic.**

It carries only run material already inside the pipeline; never `userEmail`, credentials or host paths outside the candidate tree. ## Design (settled)

- New file `workflow/panel.py`: the detached-child entry (`python -m workflow.panel <run> <stage>`), the running marker + liveness, context assembly with canonical labels, the transport adapter (`claude` + `pi` builders/parsers), overlap, and the guard that records and swallows every failure. The controller's `ensure_started(runtime, stage)` starts the child at the same three points as the attack pass (after `review.diff` exists) for the **review** step this slice (the `challenge`-stage `ensure_started`, its no-wait path and a reaper for a child that outlives a paused controller are the follow-up slice). A separate `panel.close_or_wait` runs **after** `close_or_wait_attack`, each bounded from its **own** record's `started_at`, so the step closes at `max(attack, panel)` wall-clock without editing attack's tested wait loop; a review child not alive past the startup grace is recorded `failed` by `close_or_wait` (the attack precedent). The child read-modify-writes only its own stage's entries in `panel.json` under `panel.lock` (load, replace by `id`, save — never the whole record from memory), so a future challenge entry survives.
- `contracts/workflow/panel.schema.json` 1.0.0 is the `panel.json` schema of Appendix A; `workflow/run_tests` validates every `panel.json` a test writes against it, with no key or enum outside Appendix A.
- `contracts/workflow/feature.schema.json` gains the optional `panels` at version 2.6.0 (2.5.0 and earlier unchanged; `panels` on an earlier version refused at launch). `prepare` pins `panels` into `plan.panels`, resolving each panel's `requirements` to repo-relative paths exactly as the attack pass resolves `requirement_docs`.
- **Version enums.** Join `2.6.0` to the `feature.schema` version enum **and** to `GUARDED_VERSIONS` (guardrails.py), `SIDECAR_VERSIONS` (sidecar.py), `ATTACK_VERSIONS` (attack.py) and `CRITICAL_VERSIONS` (launch.py) — so a 2.6.0 feature carrying `prd`, `sidecar`, `attack`, `critical` and `panels` launches; `panels` on 2.5.0 and earlier is refused.
- Launch guards (PRD 4.2): `report_only` must be `true`; a `pi` entry needs a `provider/id` model; the DeepSeek key guard (`WORKFLOW_PANEL_ALLOW_DEEPSEEK=1` plus the live key's SHA-256 matching `~/.config/md-manager/panel-deepseek.fingerprint`, 0600; refuse when absent/unreadable/mismatched); and **`stage` must be `review`** this slice — a `stage: challenge` panel is refused (challenge wiring is the follow-up slice; do **not** key off a missing `challenge` key, since `manifest.get("challenge", True)` defaults true). **The transport proofs run in `launch_commands` (dry run included), NOT preflight** (a dry run never reaches preflight; the attack pass guards in `launch_commands` too): a `claude` provider requires `--max-budget-usd` in `claude --help` + a valid effort; a `pi` provider resolves `pi` (controller PATH, then the nvm bin), runs `pi --version`, and passes the resolved bin dir to `prepare` (pinned into `plan.panels` for the child's `env -i` PATH); preflight re-checks. `test_pipeline` covers each refusal (without executing preflight) and that a full 2.6.0 feature launches.
- **Export (engine-owned):** in `workflow/export_state.py` add the `panels` section and bump `EXPORT_VERSION` to 1.9.0. The section is the `panel.json` record **verbatim** (the object `{version, panels:[...]}`), with a **`pending`** record built from `plan.panels` before `panel.json` exists and **null** without `plan.panels`. **Do NOT change `graph_nodes()`/`definition()`** — no exported node this slice; `definition()` stays byte-identical and `approval.depends_on` is untouched. Update `contracts/workflow/contract.test.ts` so its feature.schema version-enum assertion includes `2.6.0` (and a `panels` shape beside the `attack` assertions) — else `test:contracts` fails in the engine lane. The panel's prepare pin runs **last** so `plan.feature_version` reads `2.6.0`. **Panel costs live in `panel.json` only — do NOT add a `panel` role to the C49 `ROLES`/`by_role` export**, so every old run's `costs` section stays byte-for-byte unchanged. Add the `legacy_run`/panel-null regression to `workflow/test_export.py` (asserting `costs`/`by_role` **and** `definition()` are unchanged for a run without panels). The `viewer` lane consumes this section and owns only `panelResults` in `contracts/projects` and the UI — it does not edit `workflow/`.
- Events, attention kind `panel`, the outcome line and the status line exactly as Appendix A spells them. Events carry node id `panel-<id>` but there is **no graph node** this slice, so they render as **run-level rows**; their **statuses still mirror the attack pass** (`running` on start, `interactive` for any provider/panel failure, exactly one closing `succeeded`, never `failed`/`blocked`, never left `running`; the `panel.json` record status is separate and advisory). No reserved-id change and no `triage.ts` change this slice (both arrive with the node in the follow-up slice). No "Traceback"/"Error" literals the monitor would trip on.

## Constraints

- Owned paths only: `workflow`, `contracts/workflow`, `docs/handoff/panel-engine.md`. This **includes** `workflow/export_state.py`, `workflow/test_export.py` and `contracts/workflow/contract.test.ts` (the export section + 1.9.0 bump + version-enum are engine's; `graph_nodes()`/`definition()` are NOT touched). Do not touch `server`, `src/projects` or `contracts/projects` (the `viewer` lane owns them); coordinate only through Appendix A.
- Report-only in v1: `report_only != true` is refused at launch; the panel never feeds the run's verdict, never pauses a stage, never raises.
- Do not change the transport of any other role (workers, reviewers, judges, the attack pass): the adapter is used by the panel only.
- pi jobs get no tools (`-nt`) and only the context file; the env is `env -i` as above; `userEmail` is never written into a context file or passed to a provider. DeepSeek stays behind its fingerprint guard.
- A plan without `panels`, older feature versions and runs prepared before this change are byte-for-byte unchanged in behaviour and export.

## Acceptance

`workflow/test_panel.py` covers, end to end, with fake `claude` and fake `pi` jobs over the toy repository and the **captured** `pi --mode json` fixture:
1. A `review` panel with two providers assembles one labelled context file, runs both as a detached child, and writes a `panel.json` that validates against `panel.schema.json`; each provider has its status, `context_bytes` and (where reported) `cost_usd`, with `openai-codex` carrying its non-zero reported estimate; the panel's run-level events go `running` → exactly one closing `succeeded` (never `failed`/`blocked`), and `definition()` is byte-identical (no graph node added).
2. Overlap on canonical labels: a finding both providers raise (one citing `b/workflow/x.py`, one citing an absolute `<review-worktree>/workflow/x.py`) normalizes to the same label and is `accepted` at threshold 2; a challenge finding citing the PRD by its label anchors; a finding naming no label is `unanchored: true` and folded; threshold `"all"`/`1` behave correctly.
3. A provider that times out → `timed_out`, the panel keeps the other's findings; a non-JSON reply → `parse_failed` with raw text; the parser skips `thinking*` and reads the assistant `message_end` from the fixture, and extracts `usage.cost.total`.
4. A panel whose overall bound passes, or whose assembly throws, is recorded `failed`, the review step continues, and the run integrates exactly as without a panel; after a simulated controller restart mid-wait the review child re-attaches via its running marker + liveness (the attack re-entry precedent), not a duplicate.
5. The `review` panel's `ensure_started` runs at the attack pass's three points and writes its record under `panel.lock` (read-modify-write by `id`); `panel.close_or_wait` runs after `close_or_wait_attack` and a faked-clock test with both children shows the step closing at `max(attack, panel)`, not the sum; a second `ensure_started` on a terminal record is skipped.
6. A plan without `panels` writes no `panel.json`; `definition()`/`graph_nodes()` and the `costs`/`by_role` export are byte-identical with and without a panel (`legacy_run` regression in `test_export.py`).
7. Launch (dry run included) refuses: `panels` on a feature < 2.6.0; `report_only` not `true`; a `pi` entry without a `provider/id` model; a `deepseek/*` provider without the fingerprint guard satisfied; a `stage: challenge` panel; a `claude` provider when `--max-budget-usd` is absent; a `pi` provider when `pi` cannot be resolved. And it **launches** a 2.6.0 feature carrying `prd` + `sidecar` + `attack` + `critical` + a `review` `panels` entry.
8. The `pi` parser extracts the findings array, **severity-normalized to P0/P1/P2** (the committed fixture — captured until the reply carried a non-P severity like `"high"` — exercises the mapping), and `usage.cost` from the **committed** `--mode json` fixture (`workflow/testdata/`); the pi command-builder passes the brief as a positional message and the context as `@file`, its env includes `PATH` and its cwd is the scratch dir; the claude command-builder uses a `{"findings":[...]}` object schema (`print_command --json-schema` needs an object root), cwd the stage worktree, exactly one `--effort`, no run-dir `--add-dir`; the normalizer parses **both** a bare array and `{findings}`. The brief the child uses is the **pinned** text from `plan.panels` (sha256-pinned at prepare, or `builtin:<stage>`), not re-read from the worktree.

The policy checks (`workflow.run_tests`, `test:contracts`) pass, including the export 1.9.0 regression. Write `docs/handoff/panel-engine.md`: the record shape, the adapter interface, the detached-child mechanism, the launch guards (incl. the fingerprint file + comparison), what the `viewer` lane consumes, the accepted-finding count (filled after pilot run 1 — not produced in this build run), and every open P2 with one line each (incl. rerun-on-changed-pins and context-window size).
