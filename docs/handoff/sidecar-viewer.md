## What shipped

**Server**: `EXPORT_VERSIONS` gains `1.6.0`; `sidecar` and `sidecar-` are reserved lane names; `exportSchema` keeps the `sidecar` section as `z.unknown()`, so a garbage section never fails a run or the list. `RunStore.sidecarLedger` (route `GET/HEAD .../runs/:run/sidecar`, 405 otherwise, `conform` + `crossChecked`): 404 when the pinned graph has no `sidecar` node; else the live `<run>/sidecar.ledger.json` (own 4 MiB cap `SIDECAR_LEDGER_BYTE_LIMIT`, no-follow bounded read), else the export section, else `SIDECAR_NOT_FOUND`. A malformed, invalid, oversized or foreign (`run_id` of another run) ledger is skipped with its reason through `warn` (the app logs it). Texts are path-redacted (and clipped back to their bound), parseable times served with a Z. The node's status comes from `EVENT_STATUS` only; `projectSnapshot` has no sidecar branch. The run headline's fallback row skips sidecar rows.

**Triage** (`triage.ts`, `SIDECAR_NODE_ID`): `focusOf` never picks the sidecar while another node runs; `runningNow` leaves it out of the running list; the timeline's last activity and run end skip its rows; `deriveAttention` drops its events; `buildGaps` ignores its span; `scopeStart` does not count it as a parent of the handoff (without this a blocked run whose sidecar closed after the block lost its `blocked_before_freeze` banner, caught by the twin test).

**Viewer**: `RunView` polls the ledger with `useResource` + the run's `pollToken` (5 s, stops with the run, never the immutable `useRunReview` cache) and only when the definition has the node, so a run without a sidecar sends no request. `NodeDetail` classifies `sidecar` first; the review is the review-kind node named `review`. The page: `sidecar-headline` above the index (`2 of 6 passes failed · 3 open (2 P1) · 2 messages delivered, 1 undeliverable, 1 refused · last pass 13:50 (4 min ago)`, "no pass yet" without passes or ledger), a source line (`sidecar-source`, live or export, settings), then Open (cards, P0/P1 first then by id), Escalations, Resolved (closed `<details>`, last transition's evidence), Messages (status chip with the reason in words), Passes (table, cards at ≤760 px, "pane not captured"), Handoff (five lists or "no final pass recorded"), History last. Executor wording "one print job per pass", agent outline, no legend change; step strip label "Sidecar"; `lists.ts` `who()` says "review sidecar". No buttons were added.

## Deviations and open assumptions

- Ledger timestamps are non-empty strings with no format check (Appendix B: "no format check"); the server serves parseable ones with a trailing Z and passes others through.
- Ledger objects are not strict: a key the engine adds is dropped, never a reason to refuse the ledger. Stored escalations are pinned only as `{finding_id, kind, text}` by Appendix B; `pass` and `at` are accepted as optional.
- A ledger whose `run_id` is not the run's is skipped (treated as foreign). A live ledger beside a run whose pinned graph has no `sidecar` node is never served.
- Headline: failed passes are every pass not `completed` (failed, timed_out, rejected, interrupted), shown as `N of M passes failed` in place of `M passes`; the message part adds `refused`/`pending` counts after the PRD's `delivered, undeliverable`. "UTC" follows the clock only when the UTC zone is chosen.
- "A run without a sidecar … its sidecar route shows not recorded": the viewer sends no request for such a run (no node); the test asserts the API answers 404 `SIDECAR_NOT_FOUND`, the node page says the node is not in the graph, and the page made no ledger request. A run with the node but no ledger shows "Sidecar ledger not recorded" and the headline "no pass yet".
- "The blocked lane as the focus": a deadline block is recorded by the controller on the handoff (like `ux-run/run-deadline`), so the focus is `handoff` (failed) and the headline names the blocked lane (`Worker engine deadline exhausted…`); the sidecar shows succeeded. The twin assertion covers it.
- Beyond the PRD rule, the sidecar is never the running focus while any other node runs (not only `launch_`/`verify_`); alone it may be.
- The sidecar's event message texts in the fixtures (`pass 3 (cadence): …`, `closed at freeze after 7 passes…`) are illustrative; the viewer does not parse them, except the escalation's fixed form, which it does not need either.
