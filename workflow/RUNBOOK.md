# Runbook: supervised multi-lane LangGraph workflow

**Entry point: `python -m workflow`.** This is the complete operator-driven path, for md-manager or any other Git repository (the target: `--repo`, else the current directory when it is a Git repository with `features/`, else md-manager; see [README.md](README.md#use-it-in-another-project)). `workflow.interactive` keeps only `attach-one`, which the Herdr panes run.

Worker lanes come from configuration. A feature declares any number of lanes (`<target>/features/<feature>/feature.json` 2.0.0 to 2.7.0, one `{node_id, task}` per lane, from 2.7.0 with an optional `model` and `effort` of its own; `policy.json` 1.2.0 with each lane's `role` label, `owned_paths`, `checks` and `required_check_kinds`). A launch runs every declared lane or the subset named with `--workers a,b`; the selection is pinned in `plan.json` as `workers` and `excluded_workers`. Every lane gets the same session command, tools, permission mode and deadline; only a 2.7.0 lane's own `model` and `effort` can differ (see "Who runs the run is pinned"). The graph shape is fixed; only the lane list varies:

```text
              launch_<lane> ┐  (one per selected lane)          ┌ verify_<lane> ┐  (one per selected lane)
START ────────              ├─ handoff / freeze ────────────────┤               ├─ candidate + combined checks
              launch_<lane> ┘                                   └ verify_<lane> ┘
                                                                         │
                                                            independent review (interrupt)
                                                                         │
                                                            integration approval (interrupt)
                                                                         │
                                                             fast-forward source branch
```

A `feature.json` 2.2.0 run puts the design challenge before every launch (`challenge ──▶ launch_<lane>` in the exported graph). It runs inside `start` and `resume`, not as a LangGraph node: it decides before any worker session exists and pauses and resumes on its own; see "Guardrails" below. A 2.3.0 run with a review `sidecar` adds the node `sidecar` after the challenge (first without one) and before every launch, with `sidecar ──▶ handoff`: a pass loop inside the controller's wait, not a LangGraph node; see "Review sidecar" below. Every other run has exactly the graph above.

## One-command launch

A feature is any directory under `<target>/features/` that holds a `feature.json`; an unknown name is refused with the list found. From a clean checkout in Herdr:

```bash
.venv/bin/python -m workflow launch <feature> --live --automatic --by operator                       # md-manager's own features
.venv/bin/python -m workflow launch <feature> --repo ~/dev/project-B --live --automatic --by operator # any other repository
```

This performs preflight, creates a feature branch (not main) in the run's own checkout, prepares one worktree per selected lane, starts the interactive workers with run-scoped permission bypass/Bash access, and supervises them through checks and independent automated review. Your checkout never switches. Preflight checks that it is clean; then `git worktree add -b <branch> <run root>/<run-id>.source HEAD` (run in the target) gives the run its own worktree, the source checkout, beside the run directory. Every later command gets it as `--repo`, and reads the feature files (policy, tasks, `decisions.md`, the PRD, feature reviewer and sidecar briefs) at their paths in it: the same committed files. Built-in briefs stay in the tool's folder. So `plan.repository` is the source checkout, and integration fast-forwards the run's branch there. The Projects registry still names your checkout. A second launch from the same checkout gets a second worktree and does not disturb a live run. Runs launched before this keep your checkout as their source checkout. Launch prints the source checkout's path. The `python -m workflow` commands run from the tool's directory. Add `--workers ui` (or any comma-separated subset of the declared lanes) to run only those lanes: the others are not launched, their owned paths stay off-limits to every running lane, and the candidate is built from the selected lanes only. The command remains running until it stops on a verified feature branch, at the approval stop (finish `approval`, "Approval stop"), or on a blocker; a design challenge pause or hold stops it earlier. Meanwhile it prints the run's timeline (`events.jsonl`) as it grows, one line per event: `HH:MM:SS` in UTC, node, status, message. It starts with a header and the last five events, so a resumed `automatic --live` shows at once where the run stands; no separate timeline pane is needed. It never pushes or merges main. When it finishes it prints the merge: from your checkout, without switching, `git merge --ff-only <branch>`; once the run is finished, `python -m workflow clean "$RUN" --by operator` removes its checkouts, the source checkout last (see Cleaning up a run; while the source checkout exists the note also gives the `git worktree remove <source checkout>` form). A manual run's `approve`, and `status` once a run integrated, print the same. While that worktree exists, `git switch <branch>` in your checkout fails ("already checked out"); merging does not need it. When your checkout has moved on since the launch (another run's branch was merged), `--ff-only` refuses ("Not possible to fast-forward"): merge without it, or rebase the run branch in its source checkout (`git -C <source checkout> rebase <your branch>`), then `git merge --ff-only <branch>`. A rebase run from your checkout fails while the run's worktree exists: the branch is checked out there. For md-manager's own features the controller runs from your checkout, so merge into it or switch it only when no other md-manager run is live, or run the controller from a separate checkout. Never list workflow files (features, briefs) in `.git/info/exclude`: excluded files are untracked and missing from every worktree, so the run would not see them. Launch, and its dry run, refuse feature files the run reads (policy, tasks, `decisions.md`, the PRD, feature briefs) that are not committed at HEAD (new, ignored or excluded), before any Git action; they list every such file. A repository with no commit yet is refused too. Launch from your own checkout: a launch whose target is a run's source checkout is refused, since it would register a project named after that worktree. Use `--dry-run` instead of `--live` to inspect without execution; it also prints the source checkout and the Projects registry entry a live launch writes. Omit `--automatic` for the manual gates. `--run-id` defaults to `<feature>-001`; the run root to `~/.local/state/md-manager-workflows/<feature>` for md-manager and `~/.local/state/agent-workflows/<repo-name>/<feature>` for other targets.

Before launching, `launch` refuses: a feature directory with a `TODO:` placeholder left in a file `init` writes (each is named; see the README), a `feature.json` at version 1.0.0 (rewrite it as 2.x with `workers: [{node_id, task}]`), lanes that differ from the policy's, a missing or empty task or brief file, a reviewer `prompt` naming an unknown bundled brief (`builtin:<id>`), a run directory inside the target, an existing run directory, and an existing source checkout (`<run-id>.source`; it is never reused). For a 2.2.0 feature it also refuses a task without non-empty `## Goal`, `## Acceptance` and `## Stop` sections (naming the file and the headings; `init`'s default Acceptance line on running the checks alone leaves the section empty), a missing or empty `decisions.md`, and a `prd` that does not exist in the target. None of these touches Git. A 2.0.0 or 2.1.0 feature launches as before and prints `Note: feature.json 2.1.0: no guardrail is enforced ...` with the migration steps (the dry run also reports it under `guardrails`). A guarded feature whose `decisions.md` has no `## Operator decisions` heading launches as before, all of the file binding the run, and prints `Note: decisions.md has no '## Operator decisions' heading ...` (the dry run also lists it under `notes`).

Launch also warns, never refuses, and the dry run lists the same lines under `notes`. `prepare` records them in the run as one `controller` event, `Launch notes: ...`, so the viewer shows them:
- a selected lane that requires no test kind (unit, integration, contract or browser): allowed when tests were declined, for information only;
- a lane's required kinds or check ids that the pinned policy of the feature's previous run in the same runs root had and this policy removed;
- each owned path that a run of another feature on the same repository (the same Git common directory, as a linked worktree, or a shared root commit, as a clone) also owns, when that run has an event in the last 48 hours and its work is not in the new base: no candidate yet, or a candidate (its integrated commit once integrated) that is not an ancestor of `HEAD`. The runs are those under every runs root of the Projects registry, except the feature's own. A run's repository is read from its source checkout, else, once that is removed (`clean`), from one of its worktrees or its project's registered checkout.

A check that took more than 60% of its timeout is named at the end of its `verify_<lane>` or `candidate_<lane>` event: `; slow: unit took 210 s of its 300 s timeout (70%)`.

A policy may declare a `failure_drill`: a deliberate first verification failure of one lane, retried explicitly ("Status, failures and recovery"). Every lane/phase has a hard limit of three verification attempts per revision (a lane repair starts a new one). An automatic worker's prompt sets one default, unless its task says otherwise: run targeted tests while iterating, then the lane's non-browser policy checks once before writing the completion, and browser specs only through `check-report` on the lane's own specs (the line `init` also puts in a task's Acceptance), and it runs its tests through `run-report` so only a summary of their output enters its context ("run-report: test output for workers"); a manual worker has no shell. Automatic mode adds persisted per-worker deadlines (default 4 hours, `--worker-timeout-seconds`) enforced by the running supervisor and a reviewer deadline (default 30 minutes, `--review-timeout-seconds`, counted from the reviewer's launch). Interrupting the supervisor leaves the workers running and the run resumable, and so does Claude Code itself being unavailable, an update respawning a session under a new PID included (exit 75, see "Status, failures and recovery"); only deadline expiry, a worker that writes `status: blocked`, or a native session that is gone (`stopped` or `failed`, or listed under another identity) stops them. A worker whose native state is `blocked` (its turn ended on a question, a permission prompt or a refusal the harness could not continue past) is not a failure: the controller records one `interactive` event naming the lane, keeps the other lanes running and waits until that worker's deadline (for a lane whose completion was already accepted, the bound in "Worker questions"), so the operator can answer in its pane. A completion signal is accepted once the worker's turn is over: the registry lists its state `idle` or `done`, or its status `idle` (Claude Code 2.1.288 never lists state `idle` and can keep a finished session's state `working`, while its status says `idle`); a signal that has waited over 2 minutes for that gets one `interactive` event naming the raw state and status the registry lists. It does not impose token caps or automatically repair code. Manual mode retains operator-controlled worker lifetimes. The independent review runs as a third native session by default; `--reviewer-transport print` keeps the headless `claude --print` reviewer for environments without Herdr (see "Automatic mode: the review step").

## Who acted: --by and notes

Every gate action names who runs it: `start`, `automatic`, `retry`, `reconcile`, `approve`, `resume` (with or without `--accept-challenge`), `answer`, `repair`, `launch`, `note`, `abandon`, `clean` and `tryout` require `--by operator` or `--by maintainer`, with no default. A missing `--by` is refused (exit 1) before anything reads the run; for the operator's decisions the refusal asks for `--by operator`. `launch` passes its `--by` to the `start` and `automatic` steps it runs; `launch --dry-run` does not need it, prints the operator's commands, and refuses `--by maintainer` as a live launch does.

- **The operator** owns the run and decides. Every command the controller, `status` and the viewer print carries `--by operator`, because it is addressed to you.
- **The maintainer** is a Claude session acting for the operator. Claude sessions use `--by maintainer`. It does mechanical recovery only: `retry`, `reconcile`, `start`, `automatic --live` after a crash, and `resume` when it decides nothing (no challenge record yet, a challenge that passed or was accepted and no worker launched, or a rerun the operator started that was interrupted and is newer than the paused record). With no record yet, or after such a rerun, it is refused while a pinned feature file holds an edit that rerun was not committing (made after the interruption, perhaps half-written): committing it is your decision. It is refused `answer`, `--accept-challenge`, `resume --launch` (releasing a held challenge), `repair`, `approve`, `launch`, `abandon`, `clean`, `tryout` and `--allow-untried`, and `resume` while the latest challenge record is paused or held, with or without edits.
- **The record.** `start`, `automatic`, `retry`, `reconcile`, `approve` and `resume` write one `controller` event, `<Action> by the operator|maintainer`, as a plain record (status `note`): the viewer shows it as a log line, and it never makes a stopped run look running. `resume --accept-challenge` names the actor in its `challenge` event (`accepted by the operator`). `repair` names it in its `verify_<lane>` events (`Repair <n> by the operator`) and keeps `by` in `repairs.json`. `answer` writes an event on the lane (`Question <n> of <lane> answered by the operator`) and keeps `answered_by` in `<lane>.questions.json`. `note` writes an event on the lane and keeps `author` in `<lane>.notes.json`. Both lane events are plain records (status `note`, a log line in the viewer): they need no controller, so they never hide an interrupted one. `launch` writes none of its own: its `start` and `automatic` steps do. `abandon` writes one `controller` event with the status `cancelled` (`Abandoned by the operator: <reason>`) and keeps `by` (and `via`) in `abandon.json`. `tryout` writes one `controller` event with the status `note` (`Tryout recorded by the operator: <result>`) and keeps `by` (and `via`) with each verdict in `tryout.json`. Run from a Claude Code session (`CLAUDECODE=1`, the `!` prefix too), the text adds `(via a Claude Code session)` and the records `via: "claude-code"`. That is evidence, never a refusal. The actor never goes into `challenge.json`, whose schema is closed.
- **The label is cooperative.** Nothing checks who typed it; a wrong label goes unnoticed.

**Notes.** `"$PY" -m workflow note "$RUN" <lane> "<text>" --by operator` types `[Note from the operator N-k] <text>`, then Enter, into a running worker's pane, through the review sidecar's gate. Nothing is recorded or typed after freeze, for a lane not launched, a lane that went on (its completion, handoff or stop) or a lane waiting on a question (`answer` it instead). The note is recorded `undeliverable` and nothing is typed while the pane is not attached to the lane's session, its input line is not empty, its row is not `working` or `idle`, or Herdr is unavailable; look at the pane, then send it again. Each note is kept in `<lane>.notes.json` (author, text, sent_at, delivery) with one event on the lane. The worker prompt says an operator note may amend the task, while maintainer notes and sidecar messages are advice. The reviewers read the notes that reached a worker next to the repairs; they never read the sidecar's messages.

## Guardrails (feature.json 2.2.0)

The rules are in the README ("Guardrails"); these are the procedures.

**Before launch.** Write the tasks as outcome briefs and run the `workflow-grill` skill (`/workflow-grill <feature>` in Claude Code, linked once as the README says) so that `features/<feature>/decisions.md` exists. It writes `## Operator decisions` (your answers, which bind the run and win over the task), `## Grill defaults`, `## Changes after launch` and `## Deferred`, and before it hands back it lists every bullet you did not choose for you to confirm or edit, also when you asked it to launch; what you change or confirm by its id there becomes a new `[O<n>]` with the date. Answer any `TODO: Q<n>` line it left: launch refuses it. An older `decisions.md` without the `## Operator decisions` heading still launches and binds as a whole, with a Note; rerun the grill to split it: it carries the old bullets over as grill defaults and asks at the read-back which of them are yours. Commit. `launch --dry-run` shows `--guardrails --decisions <path> [--prd <path>] [--no-challenge]` on the `prepare` command, the registry graph starting with `challenge`, `guardrails.enforced: true`, and under `guardrails.conventions` what every session's prompt will get of the target's `CLAUDE.md` at `HEAD` (`CLAUDE.md at <commit>: <n> bytes, up to the operator-notes heading`, or `the whole file` when it has no `## Workflow (operator notes; workers skip this section)`), or `none`. A `## ` section below that heading is cut with your notes: the dry run names each one in a Note; move what sessions must follow above the heading and commit.

**The design challenge.** `start` runs it before any worker: one `claude --print` job (Read, Glob, Grep; `--add-dir` only for the run's `challenge-inputs/`, which holds the PRD copy and, for a `--restore-from` run, the read-only `restore/` copy) in `$RUN/challenge-worktree/`, a detached checkout of the base commit; the prompt (kept as `challenge-<n>.prompt.txt`) holds the pinned tasks, the project conventions (`=== CLAUDE.md ===`, when the base commit has one) and decisions and names the PRD copy and, for a `--restore-from` run, the commit and the `restore/` copy. Its deadline is the run's review deadline (30 minutes for manual runs). While the job runs, the terminal prints `Design challenge attempt <n> still running (<m> min)` once a minute; the timeline gets no such line. Ctrl-C stops the job, records a `blocked` event (`KeyboardInterrupt`) and prints the `resume` command that runs the challenge again and launches the workers; `launch` names the same command, never `automatic --live`, since no worker exists yet. A job that fails, times out, returns output that violates `contracts/workflow/challenge.schema.json` or changes its worktree blocks `start` with a `blocked` event, and no worker is launched. So does a challenge checkout that cannot be created or is not the clean base commit, before any job runs; fix it, then run `"$PY" -m workflow resume "$RUN" [--herdr] --by operator`, as the refusal says: no job ran, so it runs attempt 1, launches the workers and supervises an automatic run. After `launch`, rerunning `launch` is refused (the run directory exists), and `start` would leave an automatic run's workers unsupervised. The result is `challenge.json`:

- `passed` (no P0/P1): the timeline records `challenge succeeded`, then the workers launch as usual. Each worker prompt (`<lane>.prompt.txt`) carries the concerns as numbered advisory notes, under `Design challenge notes (advisory, attempt <n>)`; reviewers never get them. A note marked `Acts: operator` that a worker's work depends on comes back to you as its question (in a manual run, in its pane).
- `paused` (a P0 or P1): the timeline records `challenge paused`, the run's attention record says so with the two ways on (`challenge_paused`, see "Attention records"), no worker session exists, `start` (and therefore `launch`) exits 0 and prints every concern with its consequence, the simpler alternative, the cheap experiment and the two ways on. `launch --automatic` stops there; the supervisor is not started. `start` again refuses and points at `resume`.
- **Held** (`passed`, in a run launched with `--hold-challenge` or `--profile attended`, pinned as `plan.holds = {"challenge": true}`): you read every concern before any worker starts. The pass event says `held for the operator`, not `launching workers`. Then `challenge-hold.json` records `{attempt, held_at, released_at: null, released_by: null, dropped: []}` once, the timeline records `challenge paused` (`... passed (<n> P2 concern(s)) and is held for the operator before any worker launch`), the attention record is `challenge_paused` with both commands, and `start` exits 0. It prints every concern numbered as in `challenge.json` (the numbers `--drop` takes), the simpler alternative, the cheap experiment and two commands, and no accept line. `launch` stops there too: `Launch held at the design challenge; no worker was launched`. `challenge.json` stays `passed`; `status` prints `"challenge": "held"` with `challenge_attempt`, and the viewer shows the node paused. Ways on:
  - `"$PY" -m workflow resume "$RUN" --launch [--drop 2,5] [--herdr] --by operator` with nothing edited records `released_at`, `released_by` and `dropped`, launches the workers and supervises an automatic run. The workers' prompts leave out the dropped notes. With edited feature files it commits them, reruns the challenge as after a pause and launches unless the rerun finds a P0/P1 (then it is an ordinary pause); `--drop` is refused then, since the rerun numbers its own notes. That rerun's pass event says `launching workers`, and a `Resume by the operator: ... passed under --launch, hold released` note follows. That attempt was never held: its `challenge-hold.json` carries `"held": false`, so the export gives it no `hold` and the viewer shows it passed. `--drop` is refused wherever no held attempt would take it: on a paused or undecided attempt, and after a release whose launch failed (rerun `resume --launch` without it; the release keeps its drops).
  - `"$PY" -m workflow resume "$RUN" --by operator` after an edit reruns the challenge and holds again on a pass (a new hold record for the new attempt; the earlier one stays as `challenge-hold-<n>.json`).
  - A plain `resume` with no edit, and `--accept-challenge` on a held run, refuse and name both commands (after an edit, the refusal says the files changed and what each command does with them, or `resume refuses: <reason>` when resume's checks fail). `--hold-challenge` belongs to `launch` and `prepare`; every other action refuses it. `--accept-challenge` on a paused run that holds works as today and counts as the release.
  - Releasing a hold is your decision: `resume --launch --by maintainer` is refused. `--launch` on a run that does not hold is refused. `launch --hold-challenge` is refused for a feature with `"challenge": false`.
- **Rerun after an edit:** change the task files, `decisions.md` or the PRD in the run's source checkout (the paths pinned at prepare; the paused message, the refusals and `status` name it; an edit in your own checkout is not seen), then `"$PY" -m workflow resume "$RUN" [--herdr] --by operator`. In a `decisions.md` with `## Operator decisions`, add a change as a new bullet that cites the id it changes, never an edit in place: your own answer as an `[O<n>]` with the date or run, anything else as an `[L<n>]` under `## Changes after launch` with the run id and attempt. It re-reads them and checks the source checkout and every run worktree first; a refusal leaves everything as it was. Then it commits exactly the changed ones on the run's branch as `Workflow <run>: feature files revised after design challenge attempt <n>` (the pipeline's identity, hooks off) and moves the run to that commit: the lane worktrees and `challenge-worktree/` check it out, and one `plan.json` write pins it as `base_commit` and each lane's `observed_start_commit` together with the updated task, decisions and PRD copies. The source checkout stays clean for integration and the workers start from the edited files. Then it reruns the challenge as the next attempt (the previous record is kept as `challenge-<n>.json`) and, when it passes, launches the workers exactly as `start` would and, for an automatic run, supervises it like `automatic --live`. The rerun's prompt lists the paused attempt's P0/P1 concerns and the feature files changed since, and asks the job to raise each concern again unless the change resolves it. A task counts as changed by the text you wrote, not by the rules and check-report command the controller appends to a browser lane's task, so a `resume` from another checkout of the tool does not list an unedited task. Still paused: it prints the concerns again and exits 0. Without an edit `resume` refuses (exit 1, naming the attempt, nothing written): the paused attempt read exactly what the plan pins (its `pinned` digests), no later attempt was started and nothing waits to be committed or re-pinned, so a rerun would only draw another sample of the same challenge. Edit a feature file or record `--accept-challenge "<reason>"`; a concern outside the feature files (the code at the base, the policy) needs a new run. The commands the refusal and the paused record name keep `--herdr` when you gave it. A rerun whose job fails, or whose checkout fails after the re-pin, keeps the moved base and the re-pinned files, so run `resume` again: the paused attempt read other files, so it reruns the challenge as the next attempt. Paused or failed, `resume` re-exports `run-state.json`, so the viewer shows the latest attempt on the run's current base. It refuses a task that lost a required section; a task or `decisions.md` with a line that begins with `TODO:` (a placeholder, or a grill question never answered: launch refuses it too), naming the file and the line; any other change in the source checkout, naming the paths (stash or revert it); a commit on the branch it did not make (`git reset --soft <base>` and rerun: it commits the files itself); and a run worktree that is not a clean checkout of the base. Once those checks pass it writes `challenge-revision.json` (the old base and the paths) and removes it only after `plan.json` pins the new base and files. While it exists `start` and `--accept-challenge` refuse (also when `resume` ran before the first challenge), so no worker launches on a half-moved run; rerunning `resume` continues from the commit already made, without a second one. The policy is never re-pinned; changing it needs a new run.
- **Override:** `"$PY" -m workflow resume "$RUN" --accept-challenge "<reason>" [--herdr] --by operator` rewrites the paused attempt as `accepted` with the reason (the paused record stays as `challenge-<n>.json`), reruns nothing and launches the workers. Their prompts list the P0/P1s you overrode apart from the notes, with the reason, marked as context only: the worker neither acts on them nor asks about them, whatever their `Acts:` line says. The reason is shown in the viewer. It refuses while a pinned feature file no longer holds the plan's copy, edited or committed by hand (the workers would run without the edit: rerun without `--accept-challenge` to use it, or revert it; a task file is compared as written, so an override from another interpreter or checkout of the tool than prepare's is no edit), while an interrupted `resume` has not finished (`challenge-revision.json`, or a revision commit the run does not use yet), and when the paused attempt read other files than the plan now pins (a rerun failed after its re-pin; the digests in `challenge.json` `pinned` differ): rerun without `--accept-challenge` so a challenge reads them.
- `resume` refuses once any worker was launched, and for runs without a challenge. `"challenge": false` records `disabled` at `start` and runs no job.

**Worker questions.** A worker that cannot decide alone writes its completion file with `status: question`; once its turn is over (state idle or done, status idle, or the session `blocked`: a turn that ends waiting on the operator usually reports `blocked`, and needs no other attention event) the controller keeps it as `<lane>.question-<n>.json`, appends `{n, question, asked_at, answer: null, answered_at: null}` to `<lane>.questions.json`, records an `interactive` event with the question and the `answer` command, and pauses that lane's deadline (`<lane>.deadline.json`: `paused_at` while waiting, `paused_seconds` accumulated). The pause starts when the worker wrote the file (its modification time, never before the lane's deadline last ran again), so a question the controller first reads after the deadline, because it was away (exit 75, Ctrl-C), still pauses it; one written after the deadline is refused as before. The other lanes and their deadlines keep running; a controller restart reads the same pause. A deadline runs from launch to the completion signal: a lane whose completion file was accepted (its turn over) has none while another lane works or waits on a question, so a lane that finished early never ends the run while another lane waits on its answer. Once every lane's completion was accepted, a lane whose session works or blocks again (an operator prompt in its pane, a command of its own) is held to the latest lane deadline (launch plus `worker_timeout_seconds` plus the lane's paused time, the latest over the run's lanes): an `interactive` event names that time, a turn that ends before it is handed off as usual, and past it the run stops like any deadline. Answer with:

```bash
"$PY" -m workflow answer "$RUN" <lane> "Use option B; record the trade-off as an open assumption." --by operator
```

It refuses when the lane's latest question is answered or the worker went on from it (a completion file written since, its saved handoff, its stop: the pane of a stopped worker is a shell, which would run the text), records the answer and its time (with `delivered: false`), restarts the deadline (the paused time is added to it) and types the text into the lane's pane from `terminals.json` (`herdr pane send-text <pane> <text>`, recorded as `typed: true` with the exact text in `typed_text`, then `herdr pane send-keys <pane> Enter`; needs `HERDR_ENV=1`), then sets `delivered: true`. The text typed is the answer followed by the lane's new deadline in UTC, so the worker knows how long it has: `[Controller: your deadline is now <time> (UTC); the time your question waited was added to it.]`. A lane whose completion was accepted before its question is told the deadline the controller holds it to instead: none while another lane works or waits on its answer, then the latest lane deadline, which the note names once every lane's completion was accepted. It types only while `herdr pane process-info` shows `claude attach <id>` of the lane's session in that pane's foreground: once attach-one ended (Ctrl+Z detaches to the pane's shell, which would run the text; an interrupt; a give-up), or while it waits between two attaches, nothing is typed and the delivery fails; run attach-one in the pane again, then rerun `answer`. With `--no-herdr` it prints `claude attach <id>` and the text to type, the deadline note included, so you can type it yourself; that counts as the delivery. If the delivery fails (outside a Herdr pane, a run started without `--herdr` so no pane is recorded, a closed pane, a pane that does not show the session), it exits 1 with the reason: the answer stays recorded and the deadline keeps running (a deadline paused until a delivery would never run again if you then typed the answer in the pane), but the worker has not received it. Rerun one of the two commands it prints (the same command from a Herdr pane, or with `--no-herdr`): it delivers the recorded answer, typing the text at most once, and records nothing again (refused, and nothing typed, once the worker went on). After a failed Enter the text was typed into the session's input: the rerun presses Enter only, and only while `herdr pane read` shows the text typed then (`typed_text`; the bare answer for an entry a controller before it typed) in the pane's input line (`❯` under a rule and the text below it, down to the closing rule or to the end of the screen, since Herdr's capture can end at the input). A session an update respawned (a new PID) starts with an empty input: a pane showing the input empty, other text or no input line (a dialog) gets no Enter, and the answer stays undelivered. Look at the pane, then rerun with `--no-herdr` (it prints what to do and records the delivery) and press Enter there, typing the answer first if the input does not hold it. When Herdr does not confirm the text in time it may be in the input anyway: look at the pane before rerunning, and if the input holds it, press Enter there instead. A different text for that question is refused, and so is any rerun once the answer was delivered; if you type the answer in the pane after a failed delivery, do not rerun `answer` too. If you type into the pane directly instead, the controller records `(no answer recorded: the worker's session worked again in its pane)` as soon as it sees the session work again, restarts the deadline and says so in an `interactive` event. It sees that when a poll finds the session busy (status `busy`, or state `working` on a row without a status; a `working` row whose status is `idle` is the turn that asked, still over), or else when the worker writes its next completion signal: the registry may report a whole reply turn as `blocked`, or keep `done`, and the deadline stays paused until then. A session can also work again with nobody answering (a background command it started ended): until the worker writes its next completion signal, `answer` still records your text over that placeholder and types it, and the deadline keeps running. Once you typed the answer in the pane yourself, do not run `answer` too: it would type it again. A worker gets at most three answered questions; a fourth `question` blocks the run like `status: blocked` (the file stays as evidence): the `controller` event quotes the question, and the viewer shows that lane as blocked with its text.

**Completion evidence.** A 2.2.0 run pins completion `1.1.0` (`plan.completion_version`): `completed` needs `untested` (a list, may be empty), non-empty `falsifying_check` and `verify_yourself`, and `question: null`; a file without them, or a 1.0.0 file, blocks the run like any malformed completion. The export serves a completion only as the controller reads it, so the viewer shows a refused file as no completion signal; the `controller` event says why. Check `falsifying_check` against the verify node's evidence: the executed checks, not the worker's claim, are what passed. When the controller first accepts a lane's completion (its turn over), the lane's timeline says so once: `Worker <lane> completion accepted: <n> untested, verify_yourself given` (or `none`); a later poll, the final sidecar pass or a restarted controller never repeats it. The prompt asks each worker to end its `summary` with a Proof table: one row per line of its task's `## Acceptance` and per line under `## Design (settled)` in the documents the task cites, each naming its proof (a test `file::name`, a check id, a self-report, or none). The coverage reviewer verifies each row, starting from the worker's `untested` and `falsifying_check` (every reviewer gets them inline as worker claims, unverified). Its own tested/untested map has a row per line under `## Goal`, `## Acceptance`, `## Constraints` and `## Design (settled)` in each task, per `## Design (settled)` line of the documents the tasks cite, and per Operator decision (every decision under `## Decisions` in a `decisions.md` without an `## Operator decisions` heading). A gap is a P1 only in four cases, which its brief lists: a failure it shows on the candidate; a contradicted line, anywhere in the candidate, code the diff did not change included; a failure the worker disclosed, in any completion field or in its own words; or a line it could not check because its test source or packet was unreadable (a browser scenario's screenshot is part of its packet). A line of the PRD or of another cited document that conflicts with a task line the worker followed is a P2, whether or not the worker disclosed the conflict, quoting both lines and ending `Acts: operator`, since you settle conflicts between your own documents; a contradicted task line or Operator decision stays a P1. Every other gap is a P2 quoting the line. Each md-manager feature's `reviewers/coverage.md` carries the bundled brief's case paragraph word for word, and a test fails when they differ; the bundled brief names nothing specific to md-manager, so what a feature adds (its proofs, the screenshot sentence, its P2 examples) goes in its other paragraphs.

## Approval stop (attended runs and critical features)

An automatic run stops after review for your approval when its profile is `attended` (`launch --automatic --profile attended`) or its `feature.json` 2.4.0 says `"critical": true`; `prepare` pins `plan.automatic.finish: "approval"` (`--critical` on prepare; launch passes it). `critical` on an earlier version is refused. The workflow-grill skill sets the flag when you confirm a feature's code is critical: it reads the "Critical paths" list in the operator notes of the target's `CLAUDE.md`, and when a lane owns a listed path its first question is whether AI workers may write those paths or you write them by hand and audit with AI; the answer and the feature's R32 cell go into `decisions.md` as an Operator decision. Launch never refuses a lane for its critical paths.

Once every reviewer approves, the approval node waits as in a manual run. The controller writes one `note` row on `approval` and one `awaiting_approval` attention record, both naming the approve command with the exact bundle, then the report: its flow line ends `independent review → your approval → integration`, and its timeline holds the note. `automatic-step` exits 76 and the supervisor stops on it (75 still means a checkpoint persisted, 69 that Claude Code was unavailable). `automatic`, `resume` and `launch` exit 0 and print the approve command and the open items: open P0/P1 (none after an approval), the open P2s below the block threshold, accepted P2s, the sidecar's unresolved list (or, when no final sidecar pass wrote it, the ledger's findings still `open`, `acknowledged` or `fix_reported`), and each lane's `untested` and `verify_yourself` items. Nothing is fast-forwarded until you run `"$PY" -m workflow approve "$RUN" --bundle-sha256 <digest> --by operator`. The maintainer is refused it. `approve` checks the bundle digest and every reviewer's approval, records `Approved by the operator: ...` on `approval` (the viewer's approval line names that actor), and integrates as a manual approve does. Any other automatic run finishes as before. A waiting run holds its source checkout on its branch at the base; another run must not switch it.

## Tryouts and the untried-feature limit (feature.json 2.4.0 `tryout`)

A user-facing feature says `"tryout": true` in `feature.json` 2.4.0 (`init` writes `false`; the key on an earlier version is refused). Launch passes `--tryout` to `preflight` and `prepare`; prepare pins `plan.tryout` (`false` for every other launch; runs prepared before have none). When a selected lane has a browser check and the feature leaves the key out, launch prints a note; before 2.4.0 it says to move `feature.json` to 2.4.0 and set `"tryout": true`.

- **Try it.** Once the run integrated, the viewer's Now banner names each lane's Goal and its `verify_yourself` line and the tryout command, and marks the run Untried; each check row keeps its screenshots. Try the candidate, then record what you found: `"$PY" -m workflow tryout "$RUN" --result works|broken|skipped [--note "<text>"] --by operator`. It appends `{result, note, at, by}` to `<run>/tryout.json` (the history is kept), writes one `controller` row with the status `note` (`Tryout recorded by the operator: works. <note>`) and exports the run, so the chip goes. It refuses an abandoned run, a run whose plan asks for no tryout, a run with no candidate yet, a run a controller holds, a tryout.json it cannot read, or one with no verdicts list (fix or move it; the history is never replaced), and the maintainer. If the export fails after the verdict is written, it says the verdict was recorded (exit 1): do not record it again, refresh the viewer with `"$PY" -m workflow export "$RUN"`. The record is advisory: nothing merges main for you.
- **The limit.** A feature is untried when its latest integrated run (its `Fast-forwarded to` row) has `tryout: true` and no verdict; any verdict clears it, `broken` included. A new tryout launch stops when 3 other features are untried, counted across every runs root of the Projects registry. Launch, its dry run and preflight refuse it before any Git action and list the waiting runs. A continuation still launches: a run of a feature that is untried itself, or a run with `--follows`. Launch and preflight know the feature the same way (`tryout.launch_check`): by its runs root, or by its registered workflow in the same repository, which preflight finds from the policy's `features/<name>/` folder. So a run stored under a new `--run-root` still counts as its feature's own. Launches of features without `tryout` are never held.
- **The override.** `launch ... --allow-untried "<reason>" --by operator` launches past the limit and prints a note naming the waiting runs. A blank reason is refused, at launch and its dry run too. Under the limit, or for a continuation, launch says the override was not needed and drops it. Past the limit, launch passes the reason to preflight and prepare, which pins `plan.allow_untried` (`reason`, `by`, `at`); `status` prints it under `tryout`, beside `required` and the verdicts. `--by maintainer` is refused, at launch, preflight and prepare.

## Review sidecar (feature.json 2.3.0)

The rules are in the README ("Review sidecar"); these are the procedures. The sidecar never blocks the run: whatever its passes do, the lanes run, freeze, verify and integrate exactly as without it.

**Declare it.** Add `"sidecar": {"prompt": "builtin:senior-review"}` (or a feature file, plus any of `cadence_seconds` 60..7200 default 900, `pass_timeout_seconds` 60..3600 default 600, `max_passes` 1..64 default 16, `max_messages_per_lane` 0..20 default 6) to a `feature.json` at `"version": "2.3.0"`, commit, and check `launch --dry-run`: it prints the settings under `sidecar` and the prepare command carries `--sidecar-brief <path> --sidecar-settings <json>`. A 2.2.0 feature, or a 2.3.0 one without the key, runs exactly as before. The lane id `sidecar` and the prefix `sidecar-` are reserved.

**Watch it.** The timeline shows the node `sidecar`: `running` when pass 1 starts and one line per completed pass (`Review sidecar pass 3 (cadence): 2 new finding(s), 1 changed, 1 verified resolved; 1 message(s) delivered to ui, 0 refused, 0 undeliverable`), `interactive` for a pass that failed, was rejected, timed out or was interrupted (`see sidecar-<n>.stderr.log`) and for an escalation (`escalation S-3 (security): see the sidecar page`, written before anything is typed, so before its pass's line; nothing pauses). The findings, messages and passes are in `$RUN/sidecar.ledger.json` and on the node's page in the Projects viewer. Event lines carry counts and ids only; read the text in the ledger. Every escalation, and every P0 or P1 a pass found, raised or reopened that no message of that pass delivered to its lane, also writes a `sidecar` attention record ("Attention records") with its first sentence, so it reaches you even when no lane can take it, as on a one-lane run's final pass. Each is written once, when the ledger first shows that the lane will not get it: an escalation, or a P0 or P1 refused or never sent, right after the pass's merge, before anything is typed; an undeliverable one when its delivery ends; one whose message a stopped controller left `pending` when the next controller records it `interrupted` (see Recovery).

**Messages.** A message is typed into a lane's pane only while its row is `working` or `idle`, its pane shows `claude attach <id>` of that session and the input line is empty; never into a dialog, a menu, your typed draft or a shell. A lane that waits on its question is refused (answer it with `answer`; a typed message would count as your answer), and so is a lane that wrote its completion: a completion pass reviews it but its findings reach you only through the ledger (a P0 or P1 the pass found, raised or reopened is an attention record too). An `undeliverable` message stays in the ledger with its reason: relay it yourself if it matters (a P0 or P1 the pass found, raised or reopened is an attention record too). Messages never move a lane's deadline.

**Manual runs.** The controller runs no pass by itself: run `"$PY" -m workflow sidecar-pass "$RUN"` when you want one, and `"$PY" -m workflow sidecar-pass "$RUN" --final` before `freeze` (it fills the ledger's handoff; freeze records `no final pass` otherwise). It exits 0 for a completed pass and 1 for a refused or failed one. In an automatic run it is refused while `automatic --live` runs (it owns the passes); use it only to debug a run whose supervisor is stopped.

**Recovery.** A Ctrl-C or exit 75 stops a running pass's job (its process group) and records nothing; the next controller records that pass `interrupted` (it kills a job left running only when the pid's command line holds the pass's session id) and turns any message left `pending` into `undeliverable` (`interrupted`). A P0 or P1 such a message carried to its lane, which its pass found, raised or reopened, is then an attention record, as the delivery would have made it; the ledger that pass read (`sidecar-inputs/<n>/ledger.json`) says which. A Ctrl-C during a ledger write (the merge, a delivery's outcome, this recovery) waits until that write and the attention records and events it triggers are written, so none is lost. In the merge and a delivery's flip that wait includes the wait for the ledger lock. The Ctrl-C is raised even when one of those writes fails, with that error as its cause. A run stopped before freeze (a deadline, a `blocked` worker, a controller block) closes the node `succeeded` with `closed_at`, after the workers are stopped.

## Attack pass (feature.json 2.5.0)

A feature.json 2.5.0 feature may declare `attack`, and its automatic run gets a report-only attack pass beside the review (the exported graph has the `attack` node right after `review`; `approval` depends on both). An independent `claude --print` attacker per angle, offline, in its own worktree of the frozen candidate, proves each stated requirement that does not hold with a failing test; the controller re-runs each test on a clean copy and a read-only skeptic judges the reproduced ones. **The review verdict alone decides the run.** It is report-only: a pass that fails, times out, is refused or finds nothing changes nothing.

**Declare it.** The grill sets `"attack": {"angles": ["auth-funds"|...], "requirements": [...]}` in `feature.json` (angles from `inputs-state`, `permissions-files`, `auth-funds`; budgets default to $15/60 min per attacker and $5/20 min per skeptic, `max_findings` 8). The policy needs an `attack_check` (policy 1.3.0): `{"argv": ["pnpm", "--filter", "@pine/api", "exec", "vitest", "run", "{file}"], "timeout_seconds": 600}`, with `{file}` exactly once. Launch refuses an `attack` feature with no `attack_check`, and a `requirements` path not committed at HEAD.

**The guard.** Launch (its dry run included) and preflight refuse the run while any file on the secret-file list exists on this host (`~/.config/vps-wallet.env` plus `WORKFLOW_ATTACK_SECRET_FILES`, colon-separated): `Blocked: an attack pass needs <path> off this host: move it, then launch again`. Move the wallet file off the host first (PRD 5, step 1). The list is read once at prepare and pinned; the pass checks it again before any attacker starts and records the pass `refused` if a listed file reappeared.

**Watch it.** The timeline shows the node `attack`: `running` (`Attack pass started (auth-funds)`), `interactive` for an attacker or skeptic that failed or timed out (`see attack/<angle>.stderr.log`) and for a refusal or failure, and exactly one closing `succeeded` line — `Attack pass: <n> finding(s), <r> reproduced, <v> verified` for a pass that ran, or `Attack pass ended: refused`/`Attack pass ended: failed`. The record is `$RUN/attack.json` (contracts/workflow/attack.schema.json) and the node's page in the viewer; the reviewers can reach `$RUN`, where `attack.json` lives. `status` prints `attack: <v> verified, <u> unlabelled` (or the pass status while nothing is verified), and the outcome block adds one report-only line after the review lines. A pass that ends with a verified finding writes one `attack` attention record naming the label command. The attacker, re-run and skeptic can each run for minutes; after the review decides, the review step waits for the pass up to its overall bound — `len(angles) * (timeout_minutes + skeptic_timeout_minutes)*60 + len(angles)*max_findings*attack_check_timeout + 2*setup + 10 min`, **≈ 170 minutes plus twice the policy setup under pine's defaults** (near three hours per angle). Past the bound the controller stops the child and records the pass `failed`.

**Labels.** The operator labels each verified finding: `"$PY" -m workflow attack-label "$RUN" <A-n> --label real|false|out-of-scope [--review-found yes|no] [--note "<text>"] --by operator`. It is refused for `--by maintainer`, an unknown id and a finding that is not `verified`. It prints the review's findings (`review.json`) as a hint so you can set `--review-found`, re-exports the run, and appends to the finding's label history (the latest is the current label).

**Manual pass.** `"$PY" -m workflow attack-pass "$RUN" --by operator` runs the pass once in the foreground at the review gate (and is how a staged old-run copy is calibrated, PRD 5.0). It is refused for `--by maintainer`, for a plan without `attack`, before a candidate exists, and when `attack.json` already exists. It takes the run's `automatic-supervisor.lock` and then its `controller.lock`, non-blocking (as `clean` does), and holds both for its whole run ([L14]): so it is refused with `Another controller owns this run` while an automatic run holds either, and an automatic run cannot start a second attack child beside a live operator pass. **Recovery:** because it is refused once `attack.json` exists, a manual pass interrupted by Ctrl-C or a lost terminal leaves `attack.json` `running` with no command to close it (on an automatic run the review step resumes a non-terminal pass; a manual one has no resumer). Remove `$RUN/attack.json` and its markers by hand to retry, pending the operator's decision on amending this refusal (run 003 handoff).

**The tally.** `"$PY" -m workflow attack-tally` prints, across the registered runs: runs with a pass, findings, reproduced, verified, labelled real/false/out-of-scope, real ones with `review_found: yes`, cost per run, **added runtime** per run and in total, and (per [L12]) any attacker that finished before the review decided. Added runtime is `max(0, attack.json finished_at − the review's decision time)`, and the decision time is the latest non-null `reviewers[].accepted_at` in `review.json`'s content ([L18]), not the file's mtime (an approved run re-saves it after the wait). When a reviewer's `accepted_at` is null (a reviewer ran past the decision, so it could still read `$RUN/attack.json`), the run's added runtime prints as an upper bound `≤ N s` and the flag as `unknown (a reviewer ran past the decision)`; a run missing either time prints `unknown` and is left out of the total.

**Recovery.** A Ctrl-C, exit 75 or a Claude Code outage during the review stops the attack child (its jobs' process groups) and records nothing; the next controller resumes the child from `attack.json`, kills a recorded orphan (only when its pid's command line holds the job's session id), records an attacker or skeptic left `running` as `failed` (`interrupted`), and runs only what is still owed. **Nothing reruns an interrupted attacker,** so the attacker running at the moment of the outage is lost. A review that exits with no `review.json` (or a print-transport review interrupted mid-way) records the pass `failed`. `clean` removes `<runs root>/<run id>.attack/` (the two worktrees).

**Before the pilot.** Run the chosen `attack_check` on a known-failing test in a reset worktree ([L5], [L10]): confirm the test is collected from `attack-tests/`, a real assertion failure reads as `reproduced`, a missing-module case reads as `error`, and the reset (`git checkout -- . && git clean -fd`, no `-x`) leaves `git status --porcelain` empty while ignored setup outputs stay.

## Guarantees and boundaries

- One implementation worker per selected lane, as many lanes as the feature declares; each is a native interactive Claude background terminal in its own worktree. A dedicated Herdr tab attaches every terminal with keyboard input enabled: the first lane takes the root pane, each following lane splits right of the previous one, and each reviewer (one per declared reviewer, in declared order) splits right of the previous pane.
- Exact shared starting Git revision is recorded and verified. Frozen ownership is checked against actual captured files, not just agent reports, against the full declared policy: a selected lane that edits a path owned by an excluded lane is an ownership violation naming both lanes. Lane ids follow `^[a-z][a-z0-9-]{0,31}$` and never take a reserved graph name (`review`, `candidate`, `handoff`, `approval`, `integrate`, `multiple`, `none`, `both`, or a `launch_`/`verify_`/`candidate_`/`review-` prefix), nor the design challenge's node and run files (`challenge` or a `challenge-` prefix), nor the review sidecar's (`sidecar` or a `sidecar-` prefix). `role` is a free label; each lane's `required_check_kinds` decide which check kinds it must pass (policies before 1.2.0 derive them from the role: `frontend` needs `build` and `browser`, `backend` needs `unit`), so relabelling a lane cannot bypass required tests.
- **Idle is not complete.** The operator gathers handoff summaries/assumptions and explicitly freezes the run. The runtime stops every worker process before snapshotting. Source ownership violations or uncertain termination block capture.
- Verification runs in fresh worktrees, with separate cache, temp, browser-output and artifact directories. Installed Python/Node/browser executables may be shared read-only; do not share mutable dependency installations. Checks start from the controller's environment without secret-like names: names ending in `_KEY`, `_TOKEN`, `_SECRET` or `_PASSWORD`, and `GH_*` and `GITHUB_*` names (matched in any case). `*_URL` names stay; pine-chain's fork check reads `GNOSIS_RPC_URL`. `HUSKY=0` and `GIT_TERMINAL_PROMPT=0` are set. The packet lists the dropped names, never their values, as `dropped_env_names`, so a check that needed one shows why it failed.
- Worktrees are created one at a time per repository. Two overlapping `git worktree add` in one repository can make Git fail, so every worktree change (lane, verification, candidate, review and challenge worktrees) holds an exclusive lock, `workflow-worktree.lock` in the repository's common Git directory, which threads, processes and concurrent runs over the repository all share (`workflow/worktrees.py`). A failure on one of Git's own lock files is retried with a short backoff, five attempts in all; any other failure is raised with Git's stderr in the message.
- **The shared .git is watched, not guarded.** Every lane worktree shares the target's `.git`, so a hook, an fsmonitor command, a filter or diff driver or an attributes line planted there reaches the controller's own Git calls. `python -m workflow` (and `python -m workflow.pipeline` or `workflow.launch`) adds `core.hooksPath=/dev/null` and `core.fsmonitor=false` to its environment (`GIT_CONFIG_COUNT`, after any entries you set; the count is read as Git reads it, so an empty one is 0), so its own Git calls run no hook and no fsmonitor command; Claude processes, Herdr and the checks get the environment without them, and run the target's hooks as written. Every `review.diff`, lane patch, repair diff and sidecar diff is written with `--no-ext-diff --no-textconv`. `prepare` records `plan.shared_git`: a digest per watched config key in every scope (`core.hookspath`, `core.fsmonitor`, `core.sshcommand`, `core.askpass`, `core.attributesfile`, `filter.*`, `diff.*`, `merge.*`, `include*`, `credential.*`, `url.*`; a token in a URL key is never written), per entry of `hooks/`, and for `info/attributes`, `info/exclude` and the `config.worktree` files. Two files outside the `.git` are in it too, since the controller's Git calls read them and a worker's Bash can write them: the global attributes file (`core.attributesFile`, else `$XDG_CONFIG_HOME/git/attributes` or `~/.config/git/attributes`) and the global config beside `~/.gitconfig` (`$XDG_CONFIG_HOME/git/config` or `~/.config/git/config`). An entry that is not a regular file, such as a FIFO, is named by its kind and never opened; a file is read up to 1 MiB, and past that its size, modification time and change time stand in for the rest (a change time cannot be set back without root, so a same-size rewrite whose modification time was restored still shows). A worktree removed since prepare is no change, nor is a `config.worktree` holding a copy that prepare saw (`git worktree add` copies the main worktree's). Freeze (after the workers stop), the review node (before `review.diff` is written) and integrate compare against it. A change is one `warning` event, `Shared .git changed during the run: <keys or files>`, and the `shared_git` line of `status`; the same text is not recorded twice, and the run goes on. It is a tripwire, not a boundary: a planted filter still runs on freeze's `git add -A`, and a `-diff` attributes line still turns a text change into a binary patch. Git's own reads still block on a FIFO planted at `info/exclude` or `info/attributes` (freeze's `git add -A`, the review diff, the integration): the warning names it before the step hangs. Stop that step (Ctrl-C), remove the FIFO and run the step again (in automatic mode, `automatic "$RUN" --live`). In a run with a review sidecar the first sign comes earlier, in the worker phase and before any warning: each sidecar pass fails with `TimeoutExpired` (its lane Git calls are killed after 60 seconds; see `sidecar-<n>.stderr.log`) while the lanes go on. Remove the FIFO then; the next pass reads the lanes again. Runs prepared before compare nothing. Repositories that rely on post-checkout hooks (git-lfs locking, husky) do not get them in controller worktrees, nor on `launch`'s `git worktree add` of the source checkout.
- Each lane runs the checks its policy entry lists and must cover its `required_check_kinds` (for example a UI lane that builds and runs real Playwright scenarios with a PNG attachment per scenario, and a backend lane that runs unit tests plus contract/build checks). Missing tests, skipped required scenarios, flaky browser retries, nonzero exits and missing/tampered artifacts block the graph.
- **Created files are evidence.** In the worker phase only, after the verification worktree is confirmed clean at the snapshot commit and before setup or any check runs, the verifier copies each changed file of the snapshot into the packet as an artifact of kind `file` with its repo-relative `path`, in changed-file order. A file is captured when it is a regular file inside the worktree, is text (decodes as UTF-8 and contains no NUL byte) and fits the caps: 512 KiB per file (`FILE_CAPTURE_LIMIT`) and 8 MiB of captured files per packet (`PACKET_FILE_CAPTURE_LIMIT`), both in `workflow/checks.py`. Every other changed path is listed in the result's `files_not_captured` with its reason: `binary` (not UTF-8 or contains a NUL byte), `too_large` (over 512 KiB), `missing` (deleted or renamed away in the snapshot, or not a regular file, such as a symbolic link, which is never followed) or `budget` (it would take the packet's captured total past 8 MiB; a later, smaller file may still fit). A check that rewrites a captured file cannot change what was recorded, and the post-check cleanliness rule blocks the packet. A recheck verifies every `file` artifact's hash like any other artifact, so a retained copy edited after capture blocks the packet. Candidate-phase packets capture nothing and have no `files_not_captured`, except a reused one (a one-lane run without a browser check, below): it names the worker packet by reference, and its result copy keeps that packet's captured files and `files_not_captured`. Packets recorded before capture have neither and stay valid. The Projects viewer serves these files through the artifact route as `text/plain`; nothing reads the repository.
- Every lane's snapshot is checked separately, then the combined integration candidate (the selected lanes cherry-picked in declared order) is checked again per lane. Thus individually passing workers are not sufficient for integration. A run over one lane is valid: its candidate is that lane's snapshot itself (the cherry-pick fast-forwards). When that lane has no browser check, its first candidate attempt reuses the worker packet instead of running the checks again: the candidate packet names it in `reused_from` (its path and sha256), and the gate re-checks that packet as a candidate packet, so a build the worker phase recorded as failing still blocks. A browser lane, a retry, a repaired candidate and a run of several lanes run every check again.
- Review is performed by Pi/a fresh reviewer or a human against the exact bundle and candidate. The CLI imports that review; it does not spawn an unconfigured Pi model or fabricate independent review. Review identity is an operator attestation, not a cryptographic identity service.
- Explicit approval authorizes a **local fast-forward of the original source branch**. Source drift/dirty state blocks it. The controller never pushes, publishes or changes provider/billing plans; the only worktree it removes on its own is a passed check attempt's (Cleaning up a run). A worker runs as your account and could; README "What a worker can reach" says what stops it and what does not.
- **Who runs the run is pinned.** `prepare` pins `plan.roles`: the workers' model and effort, and the judges' (the design challenge, every reviewer of either transport and the review sidecar). The judges run at `--effort high` unless `--judge-effort` says otherwise; the workers take `--worker-effort`, else `WORKFLOW_WORKER_EFFORT` read once at prepare. The workers run `--worker-model`, else `claude-opus-4-8` (`sessions.DEFAULT_WORKER_MODEL`); a judge model left unset is Claude Code's default, and no `--model` is passed. A `feature.json` 2.7.0 lane may carry its own `model` and `effort` (`workers[].model`, `workers[].effort`; either on an earlier version is refused at launch): `launch` passes them to prepare as `--lane-model <lane>=<model>` and `--lane-effort <lane>=<level>`, and prepare records every selected lane's effective worker pin, its own field else the run-wide one, as `plan.nodes[<lane>].roles` (`plan.roles` stays `{worker, judges}`). That lane's worker launches with it and its receipt `<lane>.interactive.json` records it as `requested`; the judges never take a lane pin. A lane prepared before lane pins (no `roles` on its node) runs the run-wide worker pin. Nothing changes the pins later: `resume` takes no such flag, every action but `prepare` refuses `--profile` and the role flags (`automatic --live` included), and a changed variable is ignored, so a wrong pin means a new launch. Runs prepared before the pins keep their old flags (the variable for workers, nothing for the judges), but their sessions start without `ANTHROPIC_MODEL` too: a run in flight when the controller checkout updates runs its later sessions on Claude Code's default model. `prepare` also pins `plan.controller`: the controller checkout's commit, whether a tracked file differed from it, and the `claude --version` line. Prepare reads that tracked-file check with `GIT_OPTIONAL_LOCKS=0`, so it never takes the checkout's `index.lock`. `automatic --live` re-executes the controller checkout at every checkpoint, so a step that runs another commit writes one `warning` event naming both; that check reads only `git rev-parse HEAD`. Each print job writes `<stem>.role.json` beside its output (`challenge-<n>`, a print reviewer's `review[-<id>]`, `sidecar-<n>`): the pins it asked for and the models its output reports (`modelUsage`); the CLI may clamp an effort per model. A native reviewer's status file records its pins as `requested`. Print jobs, the `--bg` helper and the checks start without a surrounding Claude Code session's variables and its model and effort overrides (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_MESSAGING_*`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CLAUDE_CODE_EFFORT_LEVEL`, `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_*_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL`); config, auth and provider variables stay. This is hygiene, not a boundary: a process of your account can read another's environment.
- This is a trusted local development tool, not a sandbox or multi-tenant service. Tests/configuration are executable code. Review policy commands and task ownership before approving a run. CLI/manual terminal input is trusted operator authority.

## 2. Preflight and prepare (no model calls)

Use a new run directory outside the source repository. Keep the source clean, and use a named source branch.

```bash
RUN="$HOME/.local/state/md-manager-workflows/my-feature/my-feature-001"
PY="$PWD/.venv/bin/python"                 # md-manager's interpreter, run from its root
TARGET="$PWD"                              # or the other repository

"$PY" -m workflow preflight "$RUN" --repo "$TARGET" --policy /path/to/policy.json --herdr
"$PY" -m workflow prepare "$RUN" --repo "$TARGET" --policy /path/to/policy.json \
  --task ui=/path/to/ui-task.txt --task adapter=/path/to/adapter-task.txt
```

**Restore from a candidate.** `--restore-from <commit>` (on `launch` or `prepare`) starts a follow-up run from an earlier candidate instead of hand-written `git checkout <sha> -- <paths>` lines in the tasks. It needs `--automatic`: a manual worker has no shell to run its restore command, so launch and prepare refuse the flag without it, and also refuse it for a run with a lane named `restore-from`, both before any Git action. `prepare` resolves it with `git rev-parse --verify <x>^{commit}` in the source checkout and refuses anything else. It pins `plan.restore_from = {commit, paths: {lane: its owned paths present at the commit}}`, keeps the commit reachable under the run's `refs/workflow/<hash>/restore-from`, and writes those paths at that commit into `challenge-inputs/restore/`, read-only (files 0444; directories 0755, so `rm -rf` of an old run still works). It comes from `git archive`, so links are left out and the target's `export-ignore` and `export-subst` attributes apply. That copy is a plain directory, not a worktree, so `resume` moves only the lanes' and the challenge's worktrees. The design challenge gets `challenge-inputs` with `--add-dir` (also without a PRD) and is told that each lane starts from the base with its owned paths replaced by that copy, and sees only its own. Each worker prompt starts with its lane's `git restore --source=<commit> --staged --worktree -- <its paths>`; it has no overlay, so files the commit lacks under those paths are removed. Owned paths absent at the commit are left out. Runs without the flag behave as before. The pin cannot change after `prepare`: every other action refuses `--restore-from` (exit 2), as it refuses `--profile` and the role flags.

`--task <lane>=<path>` is given once per selected lane. `--workers ui,docs` (a subset of the policy's lanes; unknown ids, duplicates and an empty list are refused before anything is allocated) selects the lanes to prepare; without it every declared lane is selected and needs a task. A `failure_drill` naming an excluded lane is pinned as `null` and the timeline records that it was skipped.

Preflight checks the policy (lane ids, ownership, required check kinds), source cleanliness, CLI flags/authentication and required executables. It does not run the feature's tests or assume future dependencies are already installed. `prepare` creates verified worktrees and pins the policy digest/starting revision/branch. Run configuration is immutable after preparation; change feature requirements by creating a new run.

`prepare` also pins `base_unreviewed` in `plan.json` and prints it: what the base holds that no approved run reviewed. It reads the runs under every `runs_root` of the Projects registry, and the new run's own runs root: each run's `review.json` (candidate and verdict) and `plan.json` (base). It finds the newest approved candidate that is an ancestor of the base and classifies each first-parent commit after it up to the base: `blocked` (a commit of a blocked run's candidate, or a merge that brings one in, with the run), `config` (outside any run, and every file under `features/` or `docs/`, or `CLAUDE.md`) or `code` (outside any run). Reviewed commits are left out. Each entry has the commit, its subject, its class, the blocked run and its files (against the first parent). The list is capped at 20 commits (`more` and `total` say how many there are), and without an approved ancestor it covers the base's whole history. Your own deliberate commits are listed too. Nothing else changes: the review still covers only the run's own diff. A registry that cannot be read only costs the record, with a warning; a run whose `plan.json` or `review.json` cannot be read is skipped silently. Commits below the anchor are not listed, even a blocked run's candidate that an approved fix run started from: `ledger` on the branch still shows that commit as `blocked`. For a whole branch, run the same classifier:
`"$PY" -m workflow ledger --repo "$TARGET" --branch main [--since <sha>]`.
It writes `ledger.json` beside the registry (one record per repository and branch, replaced on each run) and reads everything else. Runs whose commits the repository does not have (another project's) are ignored. It does not flag, block or tag anything.

## 3. Start and interact (explicit model usage)

```bash
"$PY" -m workflow start "$RUN" --live --herdr --by operator
```

This is the only initial launch command. Native Claude assigns actual session IDs; receipts and worktree identity bind them to graph nodes. `start` refuses an already-started run. Keep the initial controller call in a persistent terminal to protect startup from SSH disconnects.

Select a lane's `Claude: <lane>` pane in the dedicated workflow tab and type normally. Manual permission prompts are yours to answer. File read/edit tools are enabled; shell tools and nested agents are disabled in this training profile. The trusted verifier, not the worker, executes tests later.

Ctrl+Z detaches without stopping the native terminal. Closing a panel only detaches it. To reconnect a worker in an available terminal, use the validated attachment entry point:

```bash
"$PY" -m workflow.interactive attach-one "$RUN" --node <lane>
```

A pane reattaches by itself, so never wrap `attach-one` in a shell loop. When the connection drops while the session lives (a Claude Code update restarts the background service, which drops every attached pane), it prints `Lost the connection to <lane> (<id>); ... Reattaching in <n>s` and attaches the same session again, backing off from 2 to 10 seconds; while `claude agents` fails or does not list the session yet it prints `The background service does not list <lane> (<id>) yet` and waits the same way. About 15 seconds after the restart the update respawns each idle session onto the new binary under a new PID, and attach-one follows it (`The background service respawned <lane> (<id>) as PID <n>`), also when `claude attach` ended with `Session <id> has exited.`, since a detach never changes the PID; until the new PID is listed it waits the same way for a row without a PID, a row still starting, or, for up to 30 seconds, a listing without the session (`claude agents` omits a finished session while it has no process) or a row still listing the ended PID. It gives up after 30 attempts in a row, naming the last error. Once the controller has stopped the session (`<node>.stop.json`: the freeze, a blocked run, a decided review) it prints `Worker <lane> was stopped by the controller at <time> (<reason>); nothing to attach.` and exits 0; while that stop is requested but not yet confirmed it prints `The controller is stopping <lane> (requested at <time>, not yet confirmed); not attaching.` with the read-only `claude logs <id>` to inspect it yourself (attaching could restart a session the stop already ended), and exits 0. It reads the stop again right before each `claude attach`. A session gone without a recorded stop (a `stopped` or `failed` row, or an ended process with no new one listed after 30 seconds) is refused once (exit 1), never restarted. Ctrl+C while it waits ends it; the session keeps running.

If `start` was used without `--herdr`, `python -m workflow attach "$RUN"` creates the dedicated tab. Partial/duplicate panel allocations are preserved and reported, not silently replaced. "Interactive panes and session identity" below covers what typing into a pane does and how sessions are bound.

While workers run, do one independent task outside their worktrees and leave `$RUN/return-note.md` describing the run, independent task, current state and next action.

### Playwright evidence convention

Every required scenario ID must appear in exactly one test title as `[scenario:<id>]`, and that test, when it passes (status expected, one result, no retries), must attach exactly one `image/png` named `screenshot:<id>`. Attachments with other names are fine, but they never count: a test that attaches `screenshot:<id>-file` and `screenshot:<id>-decisions` and no `screenshot:<id>` is refused. The screenshot must lie in the runner's isolated output directory, which `testInfo.outputPath` gives:

```ts
import { test, expect } from '@playwright/test'

test('[scenario:failed-worker] shows a useful error', async ({ page }, testInfo) => {
  await page.goto(process.env.WORKFLOW_TEST_URL!) // use your isolated local test server
  // Drive and assert the real feature behavior here.
  await expect(page.getByText('Worker failed')).toBeVisible()
  const image = testInfo.outputPath('failed-worker.png')
  await page.screenshot({ path: image, fullPage: true })
  await testInfo.attach('screenshot:failed-worker', { path: image, contentType: 'image/png' })
})
```

Before completing, a browser lane runs the spec files it changed with a JSON report and checks the report with the verifier's own rules (the same function in `workflow/checks.py`):

```bash
WORKFLOW_VERIFICATION_PHASE=<worker|candidate> PLAYWRIGHT_JSON_OUTPUT_FILE=<tmp>/report.json \
  PYTHONSAFEPATH=1 PYTHONPATH=<md-manager checkout> <its .venv/bin/python> -m workflow browser-queue run --label <lane> -- \
  npx --no-install playwright test --config=<config> --reporter=json <spec files>
PYTHONSAFEPATH=1 PYTHONPATH=<md-manager checkout> <its .venv/bin/python> -m workflow check-report \
  "$(git rev-parse --show-toplevel)/../policy.json" <lane> <tmp>/report.json
```

The controller appends this command to the pinned task of every lane with a browser check, spelled out with its own interpreter and checkout: a target's worktree cannot import `workflow`, `python` may not be on the lane's PATH, and `PYTHONSAFEPATH` keeps a target's own `workflow` directory from shadowing the tool's. The policy is the run's pinned `policy.json`, one directory above the lane's worktree (`<run>/worktree-<lane>`), the one the verifier applies, so the command works from anywhere in the worktree. `check-report` also takes a feature directory or any policy file, and `--all` for a full run; it needs jsonschema but not LangGraph, so an operator can run it from any directory: `PYTHONPATH="$HOME/dev/md-manager" "$PY" -m workflow check-report ~/dev/project-B/features/<feature> <lane> report.json`.

The `browser-queue run` prefix waits for a free browser slot while the machine's browser queue is on (below) and runs the command at once while it is off; it exits with the command's code. Runs pinned before the queue existed spell the command without it.

### Browser queue

A browser suite (the API, a Vite dev server and Chromium) is the heaviest step of a run: on an 8-core, 11 GiB machine one took about 2.7 GiB and 166 s alone, two at once 205 s each, three at once 321 s each with the load at 12. The browser queue lets runs and lanes work in parallel and makes only their browser suites take turns: every browser check, the verifier's (worker and candidate phase) and a worker's own run before `check-report`, first takes one of N machine-wide slots and waits while all are held. It is off until switched on, for every run on the machine at once, running or not:

```bash
"$PY" -m workflow browser-queue on --slots 2   # queue from now on; --slots is kept when omitted (2 at first)
"$PY" -m workflow browser-queue status         # on or off, and who holds each slot (run, phase, lane, attempt, check)
"$PY" -m workflow browser-queue off            # every browser check runs at once again, also those waiting
```

A slot is an flock on `slot-<n>.lock` in `~/.config/md-manager/browser-queue/` (`MD_MANAGER_BROWSER_QUEUE` names another directory), beside `settings.json` (`{"enabled", "slots"}`). The kernel frees a slot when its holder exits however it exits, so a killed check or controller never leaves one taken. Settings are read again every 2 s while a check waits: `off` or more slots frees waiting checks at once; fewer slots let the current holders finish. The queue never fails a check: a malformed `settings.json` is reported in the controller's output and the check runs unqueued (`on` or `off` rewrites it). Waiting is not check time: the verifier's `timeout_seconds` starts once the slot is taken. A waiting check prints `Browser queue: <run> <phase> <lane> attempt <n> <check> waits for one of <n> slots (held by ...)` to the controller's output, and the line it took a slot with; the viewer does not show the wait.

`check-report` prints one line per required scenario of the lane's browser checks: `ok`, `not in this report`, or the problem in the verifier's words, then the test counts. It exits 1 on any problem: a misnamed, missing or duplicated `screenshot:<id>`, a duplicated scenario title, a scenario or other test that did not pass, Playwright's global errors. Scenarios of spec files the worker did not run are listed as `not in this report` and fail only with `--all`. It checks that each screenshot file exists, not that it lies in the verifier's output directory, which only the verifier's run has.

The runner adds `--reporter=json`, an isolated `--output`, `--workers=1`, and `--retries=0`, and controls `PLAYWRIGHT_JSON_OUTPUT_FILE`. These trusted additions are recorded separately as `effective_commands`; the v1 command field retains the approved policy argv. Use a distinct scenario ID for each viewport/project variant. Failed/skipped/flaky cases do not satisfy required scenarios. No automatic screenshot is substituted for a missing attachment.

Have your Playwright config start/stop an isolated local web server on a nonconflicting port. Workers are stopped before checks, but the verification lanes can execute concurrently. Never reuse a developer's existing server and call it isolated verification. Process groups are terminated after each check, including timeout cleanup.

Python unittest and Node TAP/spec summaries are supported for non-browser test counts. Unsupported/custom test reporters produce missing test evidence and block rather than infer success. Browser assertions/reporting and screenshot inspection remain the reviewer's responsibility; PNG headers/hashes do not prove visual quality.

### run-report: test output for workers

A worker that runs its tests through Bash reads their whole output into its context. An automatic worker's prompt asks it to run them through `run-report` instead, spelled out like `check-report` (this controller's interpreter, the tool on `PYTHONPATH`, `PYTHONSAFEPATH=1`):

```bash
PYTHONSAFEPATH=1 PYTHONPATH=<md-manager checkout> <its .venv/bin/python> -m workflow run-report [--log FILE] [--max-lines N] [--summarise haiku] -- <command> [args...]
```

It runs the command (argv, no shell, the current directory as cwd, the checks' environment from `check_environment`, except that it keeps `PLAYWRIGHT_JSON_OUTPUT_FILE` for the worker's own Playwright run before `check-report`, plus `NO_COLOR=1 FORCE_COLOR=0 CI=1`), writes its combined stdout and stderr to a log and prints at most `--max-lines` lines (default 60) and about 6 KB: the command, exit code and duration, the counts the verifier's parser reads (`counts: 3 passed, 1 failed, 0 skipped`, or `no summary parsed`), each failing test with its first assertion or error line (unittest `FAIL:`/`ERROR:` headers with the exception line, vitest `FAIL` lines with the first `Error:`, TAP `not ok` lines with their `error:`), each line capped, the log's last 10 lines instead when the command failed and no failing test was found, then `full log: <path> (<n> bytes)`. A summary that would pass a cap ends its list with `… <n> more lines in the full log`. Its exit code is the command's (127 when the command cannot start). The default log is `<tmp>/workflow-run-report-<hash of the cwd>/<UTC time>-<pid>.log` under the temporary directory, never inside the worktree (freeze snapshots untracked files); `--log` names another file. It parses for the worker's eyes only: the verifier reruns the checks and counts them itself.

`--summarise haiku` (off by default) then starts one headless read-only Claude Code job (`claude --print` as the print-mode reviewers run, on `claude-haiku-4-5-20251001` with `--max-budget-usd 0.25`, the environment `sessions.scrub_env` leaves; `WORKFLOW_CLAUDE` names another executable) on the log's last 200 lines and appends at most ten lines (failing tests, likely cause, the file:line to look at) under `summary (haiku):`. A job that cannot start, fails, returns no usable answer or takes over 60 s gets one line, `summary (haiku): unavailable: <why>`; the deterministic summary always prints first and the exit code stays the command's.

## 5. Review the exact candidate

Successful verification interrupts at `independent_review` and produces:

- `review-bundle.json`: frozen revisions, policy digest and packet hashes: per lane, one worker packet of its snapshot and one candidate packet of the combined revision, on the run's base. Review, approve and integrate refuse a bundle with a packet missing or doubled, of another phase, lane or commit, or with another base.
- `verification/worker/.../packet.json`: worker checks, logs, screenshots, file lists and assumptions, the changed text files captured as `file` artifacts and `files_not_captured` with the reason for each other changed path (see "Created files are evidence").
- `verification/candidate/.../packet.json`: checks of the combined candidate, or, in a one-lane run without a browser check, the reused worker packet named by `reused_from` (the folder then holds only `packet.json`; logs and captures stay with the worker packet). These are candidate-verification records, not per-worker ownership claims.
- `candidate/`: clean candidate worktree for read-only inspection.
- `report.html`: the outcome block at the top (see "Outcome block" below), then the local visual graph, pending state/errors, timeline, checks and artifact/screenshot links.
- `run-state.json`: atomic, versioned private state export for the upcoming read-only project adapter; created during preparation and updated at reporting boundaries.
- `failure-drill.json` / `failure-report.json`: pre/post launch identities and observed verification attempts when the explicit lab drill is configured.

Ask Pi to assign an independent read-only reviewer against these exact artifacts. If the reviewer needs to run commands, give it another isolated worktree; do not let it mutate the captured candidate/check worktrees. The review JSON is:

```json
{
  "run_id": "my-feature-001",
  "bundle_sha256": "<SHA-256 of review-bundle.json>",
  "candidate_commit": "<candidate SHA from bundle>",
  "reviewer": "<independent Pi review run ID or human identity>",
  "independent": true,
  "verdict": "approved",
  "findings": []
}
```

Findings, if present, contain `severity` (`P0`, `P1`, `P2`), `message`, and `disposition` (`open`, `resolved`, `accepted`), optionally `worker` (one of the run's lane ids, `multiple` for several lanes, or `none` for cross-cutting findings; the legacy `both` is refused for new runs) and `requirement` (a verbatim quote from that worker's task text in `plan.json`, or null) so the viewer can link a finding to the task it concerns. P0/P1 must be resolved. Do not relabel a rejected review as approved. Code changes require new snapshots, verification and review—start a revised run rather than mutate an approved bundle.

```bash
"$PY" -m workflow review "$RUN" --review-file /path/to/independent-review.json                       # single built-in reviewer
"$PY" -m workflow review "$RUN" --reviewer general  --review-file /path/to/general-review.json        # feature with declared reviewers:
"$PY" -m workflow review "$RUN" --reviewer coverage --review-file /path/to/coverage-review.json       # one approved file per reviewer
```

Each file is one reviewer's review in the shape above. A feature that declares reviewers (`feature.json` 2.1.0 `reviewers`) needs one import per reviewer, named with `--reviewer <id>`; the import is stored as `review-<id>.imported.json` (`review.imported.json` for the built-in reviewer) and the run stays at the review gate until every declared reviewer is imported. The controller then writes the combined `review.json`: `reviewers: [{reviewer_id, session_id, verdict, accepted_at}]` in declared order, the union of the findings each tagged with its `reviewer`, and `reviewer` listing every stated identity. `approve` is refused until every declared reviewer is imported and approved. Review does not integrate. The graph then waits at a separate approval interrupt.

### Automatic mode: the review step

In an automatic run the review node launches every reviewer itself, once per bundle, and waits for all of their verdicts exactly as it waits for worker completion signals. A feature without `reviewers` has one reviewer, the built-in `review`, and behaves exactly as before; a `feature.json` 2.1.0 `reviewers` list runs one session per declared reviewer (`<id>`) in parallel over the same candidate. The default reviewer keeps the unprefixed names below; a declared reviewer's node and files are `review-<id>` (`review-<id>.interactive.json`, `review-<id>.prompt.txt`, `review-<id>.launch.log`, `review-<id>.completion.json`, `review-<id>.stop.json`, and `automatic-review-<id>.json` for its own status), its session is `workflow-<run>-reviewer-<id>` and its pane `Claude: reviewer <id>`.

- **Briefs.** The built-in brief is `workflow/prompts/review.md`; a declared reviewer's brief file replaces it and states only what to look for. The controller appends the same fixed blocks to every brief: first the severity rubric, one text for every reviewer and both transports (the brief's own severity definitions win for its subject in both directions, higher or lower than the generic scale, as a security brief's P0 for forged claims and the coverage brief's four P1 cases do; the generic scale applies only where the brief is silent; a requirement in a document the brief or a task tells the reviewer to read, such as a PRD or a list of SEC-* ids, counts whether or not a task cites it; the generic P0, P1 and P2: a P1 is a defect or a contradicted requirement to fix before merge, with the inputs, the expected and actual behaviour and path:line when the reviewer can give them, and a contradicted requirement, a line of a task, of a document a task cites or of an Operator decision in `decisions.md` included, is P1 at least, all of a `decisions.md` without the `## Operator decisions` heading counting as such; a split file's decisions block, which follows the worker claims, adds that a worker's departure from the rest that its completion names, inside its lane's owned paths and changing nothing another lane reads, is no contradiction; a worker's disclosure, the literal wording of a task or "not a regression" never lowers a severity; each P1 and P2 ends with `Consequence: ...`; a brief may name further blocking items; and how the verdict is derived), then the diff and bundle paths, task locations and this run's lane vocabulary, and for a run that pins completion 1.1.0 the run's inputs (the PRD copy and `policy.json`) and each lane's worker claims, unverified, inline from `<lane>.completion.json` (`open_assumptions`, `untested`, `falsifying_check`, `verify_yourself`; a missing or unreadable file is one line saying so and never fails the review; never the sidecar's ledger or the challenge's notes); then the completion protocol for that reviewer (its own node id, launch token and completion file; with several reviewers it names the others and tells the reviewer not to read their files). `prepare` pins each reviewer's id and brief text into `plan.reviewers`; the exact prompt each session received is kept in its `.prompt.txt`.
- **Native reviewer sessions (default).** `claude --bg --name workflow-<run>-reviewer[-<id>]` starts in `$RUN/review-worktree/` (one detached checkout of the candidate commit, shared by every reviewer) with tools Read, Glob, Grep and Write, permission mode `dontAsk`, no MCP servers, the run directory added as a readable path, and a single allowed write: that reviewer's completion file. The receipt is `<node>.interactive.json` (same keys as a worker receipt plus `candidate_commit`). Each session UUID is recorded in the timeline (`Reviewer <id> session <uuid> launched; awaiting <node>.completion.json`) and must differ from every worker's and from every other reviewer's: two reviewers sharing a UUID fail the independence check and block the run.
- **Reviewer panes.** When the run's Herdr tab exists, each reviewer gets a `Claude: reviewer [<id>]` pane as it launches: the first splits right of the last lane's pane, each following reviewer right of the previous reviewer, in declared order; each attaches with `attach-one --node <node>`. You can answer a question a reviewer asks there, exactly as for workers, without affecting the others; the transcript is the record, the verdict is only the file. A missing pane never fails the review; `python -m workflow.interactive attach-one "$RUN" --node review-<id>` reconnects in any available terminal, and `attach` adds the missing reviewer panes when the sessions already exist, also to a workflow tab whose worker panes were attached earlier.
- **Completion protocol.** Each reviewer writes its own completion file once, as its last action, then ends its turn. The controller polls every receipt and accepts a file only when it validates against `contracts/workflow/reviewCompletion.schema.json` (1.2.0: `node_id` is `review` or `review-<id>`), its `run_id`, that reviewer's `node_id` and `launch_token`, `bundle_sha256` and `candidate_commit` match the run, the session's turn is over (state `idle` or `done`, or status `idle`, and not `blocked`), every reviewer's recorded session UUID differs from every worker's and every other reviewer's, each one with a verdict is still listed as that session (an approval needs both; after a block only the listing is noted, see Verdict), and the review worktree, bundle and `review.diff` hashes are unchanged (the worktree check lists ignored files too, so configuration planted under an ignore rule such as `.claude/` refuses the verdict). A file whose `node_id` names another reviewer is rejected. Findings carry `worker` (a selected lane id, `multiple` or `none`; the prompt spells out this run's vocabulary, and the print fallback's structured-output schema is generated from it) and `requirement`. Before any block, a rejected file, including one naming a lane the run did not select, blocks the run with the reason in `automatic-review.json` (and in that reviewer's status file); nothing is relaunched. After a block, the other reviewers' files are read in the grace (below), whatever their session reads.
- **Verdict.** Derived from each reviewer's findings, then unanimous. The controller decides each reviewer's verdict from its findings: an unresolved P0/P1 (open or accepted) blocks, and so does a `blocked` verdict that lists no finding at all; anything else counts as approved, whatever the reviewer wrote. When the two differ, a `note` event names the override as the file is accepted (`Reviewer coverage wrote blocked, which counts as approved: 3 findings, no open P0/P1`), and the verdict the reviewer wrote stays as `accepted_decision` in its status file. A manual import keeps its own rule: a blocked file is refused. The run continues only when every declared reviewer's file was accepted and counts as approved. Each poll first accepts every native reviewer whose turn is over and whose file is there, whatever the declared order, and only then checks the others' deadlines and sessions, so a verdict ready at that poll is never lost to another reviewer's deadline or missing session. A rejected file (once the poll has read the other ready files, which the record keeps) or an expired deadline decides at once. The first accepted block decides the run too, but every other reviewer's verdict is still kept. A native reviewer gets the grace after it: until 10 minutes after that block was accepted, and never past its own deadline (a resumed controller continues the same window). A print job gets no grace and has until its own deadline (see the print fallback below). In the grace, each one's bound file is read at every poll whatever its session reads (a row stuck at `working` included), and recorded as a late verdict once it validates (`late: true` in its status file, `accepted` or `blocked`); a late verdict can add blockers and findings but never makes the review approved. A file that does not validate yet is read again at the next poll and, at the end of the grace or at its own deadline, kept as `late_error`. A reviewer still working when the grace ends or past its own deadline ends `superseded`, and so does one whose session is missing, ended or `stopped`/`failed`, its file unread; nothing that happens to it replaces the block, and the identity check before the verdict lists only the reviewers that gave one. That check reads the recorded session UUIDs first, whatever the verdict: a missing one, a worker's or one two reviewers share refuses the verdict and leaves no `review.json`, since `review.json` records them and the run's own validation refuses such a record (neither `workflow export` nor the viewer could load the run). A review that a rejected file or a deadline ended keeps no record then either, with one `note` event saying why. The listing of each session only protects an approval: once the review is blocked, `review.json` is written before it, and a session it cannot confirm (a blocker's session stopped, killed or gone during the grace) is kept as `identity_error` in `automatic-review.json` with one `note` event, never an error that replaces the block. Each step is a `note` event on the review node, which the viewer shows as a plain record. A reviewer that still needs attention in its pane is named again after each note, so the run keeps showing that it waits on you, and so is one that blocks again after its session worked, as a worker is. `review.json` is then written with the combined `verdict`, `reviewers: [{reviewer_id, session_id, verdict, accepted_at}]` in declared order (each `verdict` is the controller's verdict for that reviewer, null for a reviewer that produced none) and the union of the accepted findings, each tagged with its `reviewer` (the same defect reported twice is kept twice), and `reviewer` lists every session UUID. `review.json` is the review's record; the status files (`automatic-review[-<id>].json`) are the controller's restart state. An approval that still carries an unresolved P0/P1 is recorded as `blocked`, in its entry and in the combined `verdict`, and that reviewer's raw decision is kept as `accepted_decision` in its status file. Each reviewer's status file ends as `succeeded`, `accepted` (its approval was accepted but another reviewer blocked), `blocked` or `superseded` (no verdict when the run was decided); a reviewer whose accepted decision blocks reads `blocked` wherever `review.json` records the block, also when a rejected file, a deadline or a changed review worktree ends the review. A blocked review records one `blocked` event naming each blocker with its verdict and open P0/P1 counts, and the reviewers that gave no verdict, and the same text as a `review_blocked` attention record ("Attention records"); the run's error (what `workflow status` prints) names every blocker and the first sentence of each open P0/P1, at most three. Fixing findings means a new run with a new bundle.
- **Deadline.** `review_timeout_seconds` counts from each reviewer's own launch (`launch_requested_at`) and survives controller restarts. A reviewer whose turn is over with a valid file is accepted before its deadline is checked, so a verdict the controller reads again after the deadline (resumed after exit 75 or Ctrl-C) still counts. A reviewer whose file was accepted before the controller stopped (`accepted_at` in its status, saved with the `accepted_decision` and the file's `completion_sha256`) keeps that decision whatever its session does now (a follow-up typed in its pane), as a controller that never stopped would not have waited for it or read its file again: a file rewritten, half written or removed since is not read, and a `running` event says it changed after acceptance. A status saved by an older controller, without `accepted_decision`, is read again, and a file that no longer validates blocks as on its first read. A decision accepted by a controller from before derived verdicts (its status has no `derived: true`) is judged by its findings when a newer controller restores it, and one `note` names any change. So let every review in flight finish before you merge that change into the checkout the supervisor runs `automatic-step` from, or restart it as a new run after the merge: otherwise a block the timeline already announced may count as approved. Before any block, the first reviewer to reach its deadline without an accepted file blocks the run; verdicts already accepted from the others are retained in `review.json`; **no second reviewer is ever launched**.
- **Stop.** After the combined decision the controller stops every reviewer with the same identity re-check as for workers (`<node>.stop.json`); the transcripts stay resumable. A stop that cannot be confirmed after acceptance ends the controller with the verdict kept (`automatic-review.json` stays `succeeded`, that reviewer's `stop.json` absent or unconfirmed, the reason on the timeline); `python -m workflow automatic "$RUN" --live --by operator` retries the outstanding stops before continuing and launches nothing.
- **Interruption.** Ctrl-C, a closed terminal or a dropped SSH session while the controller waits leaves every reviewer running with `automatic-review.json` at `running`; `python -m workflow automatic "$RUN" --live --by operator` resumes waiting for the same sessions' files. The same holds inside a launch window once that reviewer's `claude --bg` was issued (its `.interactive.json` exists): the receipt is `running`, without `session_id` when the interrupt hit the settle poll, and resume rebinds that one session through reconciliation, never a relaunch; Claude Code unavailable during that rebind leaves the review resumable the same way (exit 75). An interrupt before a reviewer's launch was issued leaves the run at `needs_reconciliation`: resume rebinds the reviewers that were launched and launches nothing, so the run cannot continue; stop the running reviewers by their exact ids and start a new run.
- **Print fallback.** `--reviewer-transport print` (at `launch` or `prepare`, pinned into `plan.automatic`) keeps the headless `claude --print --json-schema` reviewer, one job per declared reviewer started in parallel: no pane, no human input, `<node>.stdout.json`/`<node>.stderr.log`, the same bundle binding and verdict rules. The controller reads each job as it exits, whatever the declared order, and reads every job that exited before it checks a deadline or ends the review on one that failed (the record keeps the others' verdicts); each keeps its own deadline. After the first accepted block, every other job still has until its own deadline. There is no grace, because the jobs already run in parallel. One that exits by then is read and recorded late, one whose output is refused keeps the reason as `late_error`, and one still running at its deadline is stopped and ends `superseded`. Plans pinned before the setting existed validate as `native` (they never launch a new reviewer); their exported inputs report the transport their recorded review used, or null.
- **Replay before a brief ships.** `python -m workflow.replay CASES --out DIR` measures a change to a brief, the rubric or the verdict rule on past runs before it ships. For each case it copies the run without its recorded verdicts, extracts the candidate tree with `git archive` (or rebuilds it from the base and `review.diff`), and runs N print jobs built exactly as the print reviewer's: at most two at a time, none while available memory is under 1.5 GB. `DIR/tally.json` holds each sample's raw and derived verdict and its findings. Nothing is written in the run directory or its repository. Each sample is a model call, so count the cost first.

To read or continue a reviewer's transcript after the run:

```bash
cd "$RUN/review-worktree" && claude --resume <reviewer-uuid>
```

The UUID is `session_id` in `$RUN/<node>.interactive.json` (or that reviewer's entry in `review.json`). Claude keeps transcripts under `~/.claude/projects/<encoded worktree path>/<uuid>.jsonl`, keyed by the worktree the session ran in, which is why the resume must start from `review-worktree`, the checkout every reviewer of the run shared.

## 6. Approve local integration

```bash
"$PY" -m workflow approve "$RUN" --bundle-sha256 <exact-reviewed-bundle-hash> --by operator
```

This explicitly authorizes a fast-forward of the original source branch. It checks review, packet/artifact hashes, source branch identity, clean source state and unchanged starting HEAD again. No push occurs. Do not allow another writer in the source checkout during this operation.

## Status, failures and recovery

```bash
"$PY" -m workflow status "$RUN"
```

Status takes no lock and writes nothing, so it answers while a controller runs. It prints `workers` and `excluded_workers` from `plan.json`; `next`, `pending` and `errors` from `run-state.json`, which the controller exports at the end of each graph step, so they can lag the timeline by one step (status says so once); the challenge status, `repairs` and `repair_workspaces` when there are any; `last_event`, the newest complete line of `events.jsonl` (a line still being written is skipped); and `next_step`, what happens next under the run's finish policy, with the command that goes on. The finish policy is `plan.automatic`, never `plan.mode`, which reads `interactive` for every run: an automatic run (finish `verified-feature-branch`) fast-forwards its feature branch itself once every reviewer approves and never stops for integration approval, while a manual run, and an automatic run with finish `approval` (see "Approval stop"), waits at `approve` and `next_step` names the bundle to approve. `launch` prints the same policy as its first line. Before any worker, `next_step` says what `resume` will do: a held attempt takes `resume --launch` (or an edit and a plain `resume`, which holds again), and the outcome block names the release command, or resume's refusal when the checks below fail; a paused attempt takes an edit or `--accept-challenge`; once a pinned feature file was edited, a bare `resume` commits it and reruns the challenge, and the override is not offered until the edit is reverted (`--accept-challenge` refuses it). Status first runs the checks `resume` runs before it commits (a task or `decisions.md` with a `TODO:` line or a missing section, the checkout off the run's branch, other changes in it, commits after the base that `resume` did not make): when one fails, `next_step`, a held run's outcome block and the override's refusal say `resume refuses: <reason>` instead (the outcome block says so for a held run that changed since its attempt: an edit, or a rerun that failed after its re-pin). When the source checkout cannot be read, a held run's outcome block still says it is held and that resume needs the checkout. A challenge job started and never decided (a Ctrl-C, or a `start` or `resume` still running it), an interrupted `resume` (`challenge-revision.json`) or a rerun that failed after its re-pin is rerun by a bare `resume`, with no edit and no override offered. Status looks for those edits with `git status` in the source checkout, without taking its index lock. The run does not record whether `start` was given `--herdr`, so the `start` and `resume` commands of `next_step` say to add it for the worker panes. A manual step with no gate and no error is running now or was stopped mid-step, and `next_step` says that, not that it failed. Without `run-state.json` (a run from before the export) the next step is unknown until `export` writes it. A finished run says that main is untouched only when the run's branch is not main and the repository has a main branch.

**Outcome block.** `status` prints the run's outcome block last, after its JSON and the report line, and so do the success lines (`automatic --live`'s and `resume`'s `Automatic run reached a verified feature branch. Evidence: ...`, and `launch`'s `Automatic run finished`; `launch` runs `automatic`, so its terminal shows the block twice), the Blocked output of `automatic --live` and of `resume`, and the top of `report.html`. It is built from the run record (`review.json`, the `automatic-review*.json` status files, each lane's completion file and the sidecar ledger), never from memory. It lists each reviewer's verdict, with what its file says when the controller derived another verdict and `late` for a late one; or `no verdict accepted` with the reason and whether a file was written (for a print reviewer, what its job's output says when it is a successful result with a verdict, `its print job's output says blocked (1 open P1)`, else whether the job wrote output; `general: no verdict accepted (deadline exhausted); its file says approved`). Then the open P0/P1 with their first sentences, the accepted P2s as "Known limits", each lane's `untested` and `verify_yourself` items, and the sidecar's unresolved list. A clean approval is one line, followed by the cost line when any cost is known: `Outcome: approved by general and coverage; no open P0/P1 (5 open P2 in review.json).`, or without the parenthesis when no P2 is open; it never says "nothing open", since most approved runs keep open P2s. Clean means no difference between a derived and a raw verdict, nothing late, no missing verdict, no open P0/P1, no known limits, no `untested` item and no unresolved sidecar item. `verify_yourself` alone does not count, since every completed lane writes one; it shows whenever the block is longer. A run with nothing recorded yet prints no block. The block ends with the run's cost when any session's cost is known: `Cost: $14.04 (workers $8.57, reviewers $5.47); 1 session unpriced`, the known costs summed, each role left out when none of its costs is known, and the count of sessions whose cost is unknown, so a partial total never reads as the whole (see "Cost" below). Paste it as it is when you report a run.

`report.html` is written by the controller at the end of each step and by `export`, not by `status`. It is a local snapshot viewer, not a live multi-user HTTP dashboard. Open it where its relative artifact files are accessible, or use your trusted SSH/local file-viewing setup; do not publish the run directory or logs. There are no unauthenticated HTTP execution controls.

**Cost.** Each session's cost comes from what Claude Code itself records. A native worker or reviewer is priced once its stop is confirmed: the controller reads its transcript (`~/.claude/projects/*/<session id>.jsonl`, under `CLAUDE_CONFIG_DIR` when set), takes the last `cost-state` row of each process of the session (`startTime`) and sums them, and writes `<node>.cost.json`. If the controller stops between a confirmed stop and that record, the next freeze (for a worker) or the next entry to the accepted review (for a reviewer) records it, without stopping the session again. That row type is undocumented, so a transcript without it records null. A session resumed after its stop is not counted, except by a record written late: one written after a kill (as above), or for a run stopped before cost records, prices the whole transcript, so it also counts any resume made before it. A print job (a challenge attempt, a print reviewer, a sidecar pass) reports `total_cost_usd` and `duration_ms` in its `<node>.stdout.json`. The export's `costs` section lists every session (node, role, transport, cost, duration, models) with each role's total and the run's, null where unknown; the outcome block prints the total and how many sessions it could not price. A `cost-state` row whose `startTime` is neither a number nor a string is skipped, and a cost record that fails for any reason only warns on stderr: the stop stands.

**Attention records.** A state that needs you writes one record. `$RUN/attention.json` holds the run's latest, `{version, run_id, kind, node, text, at}`, plus `states`, the latest `{kind, node, text, at}` of each state (kind and node) the run reported, and one line `{at, run_id, run_dir, kind, node, text}` is appended to `attention.jsonl` in the Projects registry's folder (`MD_MANAGER_PROJECTS_CONFIG`'s, else `~/.config/md-manager/`): one feed for every run, which a Monitor or a bot can tail (`tail -F ~/.config/md-manager/attention.jsonl`). The kinds are `question`, `pane`, `challenge_paused`, `review_blocked`, `controller_blocked`, `finished`, `sidecar` (a review sidecar P0/P1 that reached no lane, or an escalation, on the finding's lane) and `awaiting_approval`. A paused design challenge writes `challenge_paused` with the `resume` commands (a held one too, with `resume --launch` and `resume`), an automatic run that stops for your approval writes `awaiting_approval` on `approval` with the approve command (never `finished`: nothing was fast-forwarded; `approve` forgets it), and the fast-forward at the end of a run writes `finished`. The automatic controller writes `question` when it records a worker's question (on the lane, with the `answer` command), `pane` when a worker's or a reviewer's session needs attention in its pane (on the lane or the reviewer's node, with the `attach-one` command that reattaches the pane), `review_blocked` when the review blocks (on `review`: the blockers with their open P0/P1 counts and the reviewers without a verdict, and where the findings are), and `controller_blocked` for every stop it does not retry (on `controller`: the timeline's text and the `status` command). Each poll that finds a session not blocked forgets its `pane` state and each one that finds no question waiting forgets its `question` state, also after a restart, so a pane that blocks again is recorded again. A record that repeats its state's latest (same kind, node and text) writes nothing, so a restarted controller never repeats a line, however many states are open at once; `attention.resolved` forgets a state that ended, so it is recorded again when it comes back (a pane that blocks again). A record that cannot be written is reported on stderr and never stops the controller: a feed another process keeps locked costs at most 5 seconds and one line on stderr. The export does not carry it yet. A tailer that pushes each line to your phone is "Attention notifications" below.

```bash
"$PY" -m workflow export "$RUN"
```

Export rebuilds `run-state.json` from the run directory under the current export version (1.7.0: the `review` and `inputs` sections the Projects viewer reads, the lane list, one `reviewers` entry per reviewer, and the guardrails: `inputs.decisions`, `inputs.challenge` with `attempts`, the completion's version, evidence and unrecorded question, and `inputs.workers.<lane>.questions`, null and `[]` for runs without them, the review sidecar's ledger as `sidecar`, null for runs without one, `inputs.roles`, `inputs.controller` and `inputs.automatic.profile`, left out for runs prepared before them, `inputs.challenge.history`, each earlier record `challenge-<n>.json` with its status and P0/P1, and `costs`, what each session cost), then rewrites `report.html` from the same state. A run recorded before configured lanes keeps its stored graph definition (same node ids, same labels), reports `ui` and `adapter` as its selected lanes and carries its launch receipts and packet paths under `values.lanes` and `values.packets`. It takes the controller lock, reads the persisted checkpoint without invoking any node, constructs no sessions (a copied run whose worktrees are gone still exports), launches nothing, and refuses a run whose `plan.json`, pinned policy or `review.json` fail validation. Unchanged content does not bump `updated_at`. Run it on runs recorded before a newer export version, such as project-workflows-001, so the viewer shows their review and inputs.

- **Controller blocked:** before an automatic controller stops at a failure it does not retry, it records one `controller` `blocked` event that starts `Controller blocked:` and says why: a graph step that failed and is not retried, with its error (`Controller blocked: the review step failed: ...; not retried, inspect retained evidence`), or a stop of its own, with its reason: a freeze that failed, a review worktree a failed review left behind (with the command that removes it), an unexpected manual gate, or a finished graph without a verified feature-branch completion. It is written once per controller process; a later `automatic --live` that stops at the same failure says it again. A worker wait that ends (a deadline, a blocked lane) and a check that failed identically or ran out of attempts record their own `controller` `blocked` event with the error instead. Two stops before any step can be resumed, so they record a `controller` `interrupted` event instead, naming what comes before `automatic "$RUN" --live`: a source checkout that left the run's source branch, and a start that did not complete (both below). Nothing is stopped or relaunched, and the viewer shows the run interrupted with those steps, not blocked. The bullets below say what to do for each kind of failure.
- **Failed verification:** inspect its packet/log. Attempts default to a hard limit of three per lane, phase and revision (a lane repair starts a new revision, see below); policy v1.1.0 and later can explicitly set `max_verification_attempts`. For a transient check/environment failure at the same immutable revision, explicitly retry only that lane (`--node` accepts any lane of the run and nothing else):
  `python -m workflow retry "$RUN" --phase worker --node adapter --by operator`.
  On an automatic run the supervisor retries a failed check by itself within the limit; `retry --phase/--node` is for a check step it stopped at without a verdict (an interrupted check, one whose worktree Git could not create, a candidate step that failed before its checks, for which one lane without a candidate packet is enough). There it only raises the attempt and prints `automatic "$RUN" --live`, whose controller runs the step at that attempt: invoked by `retry`, the graph would run the review node, reviewer launches included, in the CLI process.
- **Failed combined check:** use `--phase candidate --node <lane>`. Already successful candidate checks are reused after artifact validation. A saved packet is reused only for its own phase, lane and attempt; one of another (a worker packet at a candidate path) is refused.
- **Worktree creation failed:** the error ends with Git's own message. `cannot lock` or `.lock': File exists` after the retries means another Git process holds that lock file, or a crashed one left it behind: make sure none is running, delete the named `.lock` file, then rerun what failed: a check or the candidate step with `retry` as above (it left no packet, which `automatic --live` never retries by itself), the design challenge's checkout with `resume` (Guardrails), the review worktree of an automatic run with `automatic "$RUN" --live`: its controller re-enters a review that launched no reviewer once per `automatic --live` (the timeline says `Re-entering the review`; `review-restart.json` keeps it to once across the supervisor's step processes), and stops if the same failure comes back. A `review-worktree/` left behind by a failure after its creation stops it with "Partial review worktree … remove it with git worktree remove --force …": remove it, then rerun `automatic --live`.
- **Failure after stopping/snapshotting or integrating:** `retry "$RUN"` resumes only failed graph steps; it never launches a new Claude worker. On an automatic run it refuses until the review is recorded (`review.json`), since it would run the review, reviewer launches included, in its own process: before that `automatic --live` continues the run; after it (a failed integration) `retry` finishes it and launches nothing. Stop-intent recovery checks whether the prior stop already completed before issuing another native stop.
- **Ambiguous startup:** inspect receipts/native inventory, then `reconcile "$RUN"`. It only permits existing durable launch intents and exact surviving sessions; no new native process is launched during reconciliation. Missing proof remains blocked. On an automatic run, `automatic "$RUN" --live` stops before any step while the start is incomplete, with a `controller` `interrupted` event that names the launches to reconcile, then `automatic "$RUN" --live`; for a run that was never started, it names `start "$RUN" --live` instead.
- **Prompt too long:** a worker's or native reviewer's prompt travels as one command-line argument, which Linux caps at 128 KiB. One over 120,000 bytes is refused before its launch receipt is written (`Worker <lane>'s prompt is <n> bytes, ...`, a `blocked` event). For a worker nothing was launched and nothing needs reconciling. For a native reviewer the review is left at `needs_reconciliation`, and reviewers launched before it keep running: stop each by its `background_id` (`claude stop <background_id>`, from `<node>.interactive.json`), since `automatic --live` then stops at `Reviewer <id> needs reconciliation`. The long parts of a worker's prompt are its task, the design challenge's notes, `CLAUDE.md` above its operator-notes heading and `decisions.md`; of a reviewer's, its brief, the worker claims, `CLAUDE.md` and `decisions.md`. Shorten them, commit and prepare a new run. Print reviewers, the design challenge and sidecar passes read their prompt from stdin, with no such limit.
- **Source feature branch changed:** before every step the automatic controller checks that the run's source checkout (its own worktree since C56; your checkout for older runs) is still on the run's source branch, which integration fast-forwards. When it is not (the checkout was switched while the run went on), the controller stops before that step with a `controller` `interrupted` event that names both branches; nothing is stopped or relaunched, and the sessions keep running. Switch the checkout back (`git -C <source checkout> switch <source branch>`; the interrupted event in the terminal names it, `status` prints it as `source_checkout`, and for runs launched since C56 it is `<run directory>.source`. The viewer redacts paths, so its first step is that `status` command), then run `automatic "$RUN" --live`. That holds only while the run can continue: the controller first reads the run's graph (it changes nothing), and a run that already stopped for good (a review block, a failed freeze, a step it does not retry, workers stopped when their wait failed) keeps its block instead, in the words the source branch uses: `Controller blocked: <reason>`, or the reason alone for a check that failed identically or reached its attempt limit and for workers stopped when their wait failed. Never the interruption, which would hide the block from the viewer; and one text, so moving the checkout back and forth never pages you again for the same stop.
- **Changed code:** before review, `repair` (below); after review started, a follow-up run of the feature (`brief`, then `launch --follows`; "Follow-up runs" below). **Changed policy:** create a new run. Do not modify frozen snapshots/evidence and reuse approvals.
- **Partial candidate/worktree allocation:** preserve and inspect it. Speculative Git conflict resolution is intentionally unavailable, and so is automatic cleanup, with one exception: a check attempt that passed loses its checkout and caches once its packet is saved (Cleaning up a run, below).
- **Workspace trust:** `claude --bg` refuses a folder nobody trusted (`Workspace not trusted. Run claude in <dir> once and accept the trust prompt`), and a trusted parent folder does not count, so every run's fresh worktree would need the prompt. Before each worker and native reviewer launch, the controller records that worktree as trusted in Claude Code's config (`$CLAUDE_CONFIG_DIR/.claude.json`, else `~/.claude.json`: `projects.<worktree>.hasTrustDialogAccepted`), as accepting the prompt does, only for worktrees inside the run directory, keeping the rest of the file, and reading the entry back (written again if Claude Code's own rewrite dropped it, refused after three tries; a config that is not JSON is never overwritten). It does so before the launch receipt is saved, so a refused write records nothing and the launch step can run again. Runs whose launch failed on trust before this change keep their receipt and are never relaunched: abandon them and launch a new run. Print-mode jobs (the design challenge, print reviewers, the sidecar) skip the trust prompt by design.
- **Claude Code unavailable (exit 75):** an update replacing the `claude` binary, or its background service restarting, is not a verdict on any session. Every `claude` call the controller makes waits it out for 60 seconds: a launch, a print job or a stop is repeated only when its exec failed (nothing ran, so none ever starts twice), and the `claude agents --json` listing, which only reads, is asked again every 2 seconds while it fails, prints no list or hangs (each 15-second timeout counts against the 60). After that the automatic controller stops nothing: it records an `interrupted` event naming the cause, and `automatic` (also `launch --automatic` and `resume`) exits 75 with the resume command and any stale Claude processes to restart (its `automatic-step` child exits 69, EX_UNAVAILABLE, which the supervisor turns into that 75, whichever step was running; 75 from a step still means a checkpoint persisted). The service also respawns idle sessions (a finished lane, a lane paused on a question, a reviewer that wrote its file) under new PIDs, about 15 seconds after it restarts or at any later time: while `claude agents` lists such a session without a PID, in a state between two processes, with its ended PID or not at all, the worker and reviewer waits, the reviewers' identity check before the verdict and every stop look again every 2 seconds, and a stop follows the new PID (same background id and session UUID); a gap that lasts 30 seconds counts as Claude Code unavailable. Only a stop already issued (`issued` in `<node>.stop.json`, written right before `claude stop` runs, and cleared when it exits non-zero, times out or cannot be executed, as it can while the service restarts; a Ctrl-C while it runs leaves it set) counts a session the listing leaves out as stopped; a failed stop is issued again to the respawned session. Once `claude --version` works, run `"$PY" -m workflow automatic "$RUN" --live --by operator`: it waits for the same sessions again (a review interrupted this way re-enters its node, rebinding the running reviewers; a freeze re-enters, marked by `freeze-interrupted.json`, completing the stops it recorded in `<lane>.stop.json`; each marker is removed only once that re-entry ends, so a Ctrl-C or a closed terminal during it leaves the run resumable the same way); nothing is relaunched. A reviewer launch it interrupts leaves the review at `needs_reconciliation` (below), and a print review it interrupts terminates its jobs: no resume continues either, so the controller records a `blocked` event naming the cause and `automatic` exits 1. A deadline, a `blocked` completion, a rejected file, a `stopped` or `failed` session or a changed session identity still stops the sessions: every lane's stop is attempted, and the ones that cannot be confirmed (usually that lane's own) are named together on the timeline. A session still missing after 30 seconds makes every `automatic --live` exit 75 the same way: `claude agents --json --all` and `claude logs <id>` show whether it ended; waking it with `claude attach <id>`, or stopping the run (below), is your decision.
- **Usage exhausted:** workers stay at the manual terminal/handoff boundary. Preserve their receipts/worktrees, record the decision, and ask the owner to wait or approve a new plan/provider. A run you will not continue is closed with `abandon` and followed up by a new run ("Follow-up runs" below). The system never switches to another payment/provider mode or replays an opaque Claude workflow automatically.
- **Stopping an unfinished run:** `abandon` ("Follow-up runs" below) stops the recorded sessions and closes the run. By hand, use the exact native IDs from its receipts (`<lane>.interactive.json` for every selected lane and, in automatic mode, `review.interactive.json` or `review-<id>.interactive.json` for every reviewer) with Claude's `stop` command after verifying identity. Closing Herdr alone is not a stop. All run artifacts and lane worktrees are retained; cleanup is a separate operator decision (Cleaning up a run, below).
- **Reviewer needs reconciliation:** `automatic-review.json` at `needs_reconciliation` or `blocked` never relaunches a reviewer. Inspect each reviewer's `.interactive.json`, `.launch.log` and status file (`automatic-review.json` for the built-in reviewer, `automatic-review-<id>.json` per declared reviewer) and `claude agents --json`, stop a stray reviewer by its exact ID, and start a new run for a fresh review.

- **Cleaning up a run:** a check attempt that passed keeps its folder, `packet.json`, logs, `artifacts/` and `browser-report-<n>.json`. Once its packet is saved, the verifier removes its `worktree/` (`git worktree remove --force`, under the repository's worktree lock), `npm_config_cache/`, `xdg_cache_home/` and the raw `browser-<n>/` output of each check that did not fail. A browser check deferred in the worker phase can fail in an attempt that passes; its `browser-<n>/` is kept, since its failure screenshots and traces may be there only. A recheck reads only the packet and artifacts, so the attempt still rechecks, retries and repairs work as before, and the viewer is unchanged. A failed attempt is kept whole, to inspect. A removal that fails is a warning on stderr, never a failed check. When `git worktree remove` fails partway (read-only content), Git still forgets the worktree; the verifier and `clean` then delete what is left and run `git worktree prune`. The failure drill's attempt is kept whole too: the drill fails it after its checks pass. Everything else stays until you run
  `"$PY" -m workflow clean "$RUN" --by operator [--dry-run]`.
  It refuses while the run's controller or supervisor lock is held, while a receipt (`<node>.interactive.json`) cannot be read, or while `claude agents` lists a live session of the run: one with a receipt's `background_id` or `session_id`, one with the ID a never-bound receipt's `<node>.launch.log` printed, or one named like the run's launches (`workflow-<run id>-<lane>`, `workflow-<run id>-reviewer[-<id>]`). A `stopped` or `failed` row does not count, nor a row without a PID whose stop the controller confirmed in `<node>.stop.json`. It also refuses when `claude agents --json` gives no listing, since it cannot then tell whether a session of the run is live. Stop the run first (above). It prints what it will remove, then prunes every passed attempt of the run as above (runs from before this pruning included), removes the lane worktrees, `candidate/` and `candidate-<g>/`, `review-worktree/` and `challenge-worktree/`, and, once the run is finished (its branch fast-forwarded), its source checkout `<runs root>/<run id>.source`; then `git worktree prune`. The source checkout goes last, and only once every other removal succeeded: a rerun of clean still finds the repository. It is kept, with a `Kept:` line, while it holds uncommitted changes or a rebase or merge in progress (where you integrate when `--ff-only` refuses): commit or discard them, then rerun clean. clean finds the repository through the first checkout of the run Git can still read (the source checkout, a lane, candidate, review, challenge or attempt worktree), so it still cleans a run whose source checkout you removed by hand; with none left, it deletes the leftover folders Git forgot (no `.git` at all, or a `.git` file naming a gitdir that is gone) and skips the prune. When a folder's `.git` file still names a gitdir that exists, Git cannot run there (a broken `.git/config` or environment): clean refuses that folder with `Git cannot read <path> although its repository <gitdir> exists`, keeps the source checkout and exits 1. A `.git` file it cannot read or that names no gitdir, and a `.git` that is no file (a FIFO), are refused the same way (`Git cannot read <path> and its .git file names no gitdir it can check`), and a `.git` symlink with `Git cannot read <path> and its .git is a symlink`: that is no evidence Git forgot the folder. Check `git -C <path> status`, fix Git, then rerun clean. `--dry-run` marks each folder it will refuse (`Git cannot read it ...: clean will refuse it`), and when no removal finished the error says `no removal completed` (a failed removal may still have deleted part of its folder). A second clean of a cleaned run prints `Nothing to remove`. It keeps failed attempts, repair workspaces (one may hold your uncommitted fix), every packet, log, artifact and run file, and a lane path that is not inside the run directory. `--dry-run` only lists. Cleaning a blocked run removes the lane worktrees a repair would use, so run it with `--dry-run` first: without it, removal starts right after the list. In a run stopped before freeze, a lane worktree holds the worker's only, uncommitted copy of its edits: the list marks each lane worktree with uncommitted changes as `the lane's only copy of them`, or, for a frozen lane (freeze leaves the worktree dirty), `captured in snapshot <sha>`. A failed `git worktree prune` is reported with the removals that failed. After clean, `cd "$RUN/review-worktree" && claude --resume <uuid>` no longer works, since that directory is gone; the transcript stays under `~/.claude/projects/`. Only you run it: `--by maintainer` is refused, since cleanup is not mechanical recovery.

Lanes are configuration, not a fixed pair: the tests exercise one, two and three. Selective check recovery is tested independently of Claude's own workflow-relaunch semantics.

### Blocked after freeze: repair a lane

A check verdict after freeze is final for the frozen code: a retry reruns the same revision, and two identical failures stop the run (`controller blocked`, `failed identically on attempts 1 and 2`). When the cause is the code and no reviewer has seen a candidate (no `review-bundle.json`), `repair` turns a fix commit you make into new snapshots of the lanes it concerns, instead of a new run. It launches no session, runs no check and never invokes the graph. workflow-guardrails-001 ended this way: the ui lane's `[scenario:inert-markdown]` test attached its two screenshots under other names than `screenshot:inert-markdown`, and the candidate refused it twice identically. With `repair`:

```bash
"$PY" -m workflow repair "$RUN" ui --workspace --by operator
# edit in $RUN/repair-workspace-1 (a detached checkout of the failing candidate), then commit there, never on the source branch
git -C "$RUN/repair-workspace-1" commit -am "ui: exactly one screenshot:inert-markdown"
"$PY" -m workflow repair "$RUN" ui --commit $(git -C "$RUN/repair-workspace-1" rev-parse HEAD) --by operator \
    --reason "the verifier requires exactly one screenshot:inert-markdown attachment" --dry-run     # prints what it would do
"$PY" -m workflow repair "$RUN" ui --commit ... --reason "..." --by operator                                     # the same without --dry-run applies it
"$PY" -m workflow automatic "$RUN" --live --by operator                                                          # a manual run: "$PY" -m workflow retry "$RUN" --by operator
```

- **The base.** After a candidate block the workspace is the failing combined candidate (`candidate.json`, or `candidate-<g>.json` after earlier repairs), so a lane that cannot build alone (001's ui lane needed the controller lane's contract fields) is fixed where it failed; a fix there may span lanes (`repair "$RUN" ui,controller`), and each lane gets the fix's files it owns. After a `verify_<lane>` block the workspace is that lane's snapshot, and the repair names that one lane. `repair-workspace-<m>.brief.md` lists the blocked step and attempt, every gate reason verbatim, the failing packet, logs and browser reports, the lanes' owned paths and check commands, the browser evidence rules for a lane with a browser check, and the exact `--commit` command.
- **What `--commit` checks.** The commit descends from the current candidate or from the named lane's snapshot, changes only paths the named lanes own (never an excluded lane's), adds no symlink or gitlink and changes something. The source checkout must still be on the run's branch, at the base commit and clean, as integration requires: a fix committed there is refused (commit it in a workspace instead; moving the branch back is your decision).
- **What it records.** `repairs.json` (the repair, first `recorded`, then `applied`), one commit per lane (its snapshot plus the fix's files it owns, parent the base, dated at the recorded time; ref `refs/workflow-repair/<hash>/<n>/<lane>`, the fix itself `.../source_commit`), `repair-<n>.diff` (the change per lane), the raised `attempts.json`, the timeline events (`verify_<lane>` and `candidate` paused, `controller` running) and one new checkpoint. `snapshots.json`, `plan.json`, `candidate.json`, every packet and every lane worktree stay as they were. The lane keeps its worker's session as its identity; the snapshot's summary and `repair` object, the timeline and every reviewer's prompt (with the path of `repair-<n>.diff`) name the repair and its reason.
- **What the graph does next.** The checkpoint is forked at the freeze boundary (after `handoff`, before the verifies; never the failed head), so the continuation re-verifies every lane: the repaired lane at a new worker attempt, the others by rechecking their packets, then a new candidate generation (`candidate-<n>.json`, `candidate-<n>/`) checked by every lane at new attempts, and only then review. A candidate built after a repair on the candidate must have exactly the fix commit's tree. After a repair `automatic --live` is the only continuation of an automatic run: `freeze` and plain `retry` refuse it.
- **Attempts.** The limit counts per lane, phase and revision: the repair starts the repaired lanes' worker attempts and the candidate attempts of every lane that has some past the existing ones, and the three attempts count from there. Two identical failures stop the run only when both checked the same revision. At most three repairs per run.
- **Refused** (exit 1, `Blocked:`, nothing written): a run not stopped at a check verdict after freeze (`reconcile` a launch; an interrupted check, a check step that failed without a verdict such as an infrastructure failure, or a run stopped between steps: run what the refusal prints for the run's mode, on a manual run `retry` (`--phase <p> --node <lane>` for an interrupted check), on an automatic run `automatic --live`, after `retry --phase <p> --node <lane>` for a check step), a lane blocked before freeze (an automatic run then needs a new run), a started review, a held lock, a moved, dirty or switched source checkout, a fourth repair and a plan without configured lanes. An applied repair is not replaced before the run continues from it: check it with `--dry-run` first. Once the continuation stops at a check verdict again (the repaired lane's own check included), the next repair builds on it.
- **Crash.** While a repair is `recorded`, `automatic`, `automatic-step`, `retry` and every other `repair` refuse; rerunning the identical command completes it (the same commits, one fork). `status` lists `repairs` and any `repair_workspaces`; removing a workspace (`git worktree remove`) is your decision.

### Follow-up runs: brief, --follows and abandon

A run blocked by its review, cut short by an outage or a usage limit, or approved with P2s you want fixed is followed up by a new run of the same feature under the next run id. Nothing in the old run is reused: the follow-up has its own bundle, checks and reviewers.

```bash
"$PY" -m workflow brief "$RUN"                     # Markdown on stdout: per lane, what the follow-up's task needs
# paste what each lane needs into its task (features/<feature>/<lane>-task.md, under ## Context), commit in the target
"$PY" -m workflow launch <feature> --repo <target repo> --run-id <feature>-002 --follows "$RUN" --live --automatic --by operator
"$PY" -m workflow abandon "$RUN" --reason "followed up by <feature>-002" --by operator   # once you will not continue it
```

- **`brief`** reads the run and writes nothing; it works for any finished run. Per selected lane it prints the restore recipe, `git restore --source=<sha> --staged --worktree -- <owned paths>` and the check `git diff --stat <sha> -- <owned paths>`, which prints nothing once restored. The source is the candidate, or the lane's snapshot when the run has no candidate, or when Git no longer holds the candidate (a run from before the candidate ref whose worktree was removed): the brief says so and names each lane's snapshot ref. It asks Git in the run's source checkout, or, once that is removed, in a lane, candidate, review or challenge worktree of the same repository; with none left it keeps the candidate and says the repository could not be read. Unlike `git checkout <sha> -- <paths>`, the restore deletes a file the candidate removed. An owned path the source does not have at all goes to `git rm -r -q --ignore-unmatch -- <paths>` instead: the follow-up's tree may lack it too (the approved branch was merged), and `git restore` would then refuse every path. The paths are the followed run's pinned policy's. Then the lane's findings, verbatim, from `review.json` and from each reviewer's bound file (`review[-<id>].completion.json`, a print job's `<node>.stdout.json` or an import), validated as the controller does; a finding in a file that `review.json` does not hold (a superseded or late reviewer) is marked `unrecorded`, and a file that does not validate is named, never raised. Then the worker's own claims from its completion file: `untested`, `verify_yourself` and `open_assumptions`. After the lanes come the findings on several lanes or none, and the review sidecar's `handoff.unresolved`. The brief can run long; you choose what goes into each lane's Context.
- **`launch --follows <run>`** takes the followed run's directory, or its run id under the run root. `prepare` pins `plan.follows`: `{run_id, verdict, candidate_commit}`, the verdict and candidate null when the run recorded none (a run a usage limit ended has no `review.json`). It is refused, before any Git action, only when the directory has no `plan.json`.
- **The candidate ref.** The candidate step keeps the candidate commit as `refs/workflow/<run hash>/candidate` (next to each lane's snapshot ref, `refs/workflow/<run hash>/<lane>`), so the brief's recipe still works after the candidate worktree is removed. Runs from before the ref have none; their candidate lives only in `candidate.json`'s worktree.
- **`abandon <run> --reason "<text>" --by operator`** closes a run that will not go on. It is your decision, so `--by maintainer` is refused. It takes the supervisor and controller locks as `repair` does and refuses while a controller holds either. It stops each recorded worker and reviewer session (`<node>.interactive.json`) that is still live, by its exact ids, through the controller's stop (`<node>.stop.json`): a receipt's ids as `claude agents` lists them; for a launch whose receipt was never bound (`needs_reconciliation`), the id its `<node>.launch.log` printed, identity checked; for an unfinished stop the controller left, its ids or its process. A session that is gone, or listed `stopped` or `failed`, is recorded as not running; one listed under another run's name or worktree is refused. A session listed without a PID (a Claude Code restart's respawn gap) is stopped like a live one: the stop waits the gap out. If no respawn comes within that grace, it is a stop abandon cannot confirm, not a failed listing: the other sessions are still stopped. A never-bound launch whose session is still `starting` is a failure: rerun once it settles. It lists sessions only when a node has a receipt, so a run that never launched is abandoned while Claude Code is unavailable. A listing that fails ends the abandon at once, after one 60-second wait, and records nothing. A stop it cannot confirm withholds `abandon.json` and the event: inspect it and rerun the same command. The stops it did confirm keep their markers and are not issued again. Then it writes `abandon.json` (`reason`, `by`, `abandoned_at`, `stopped`, `not_running`) and one `controller` event with the status `cancelled` (`Abandoned by the operator: <reason>. Stopped: ...`); the viewer then reads the run as cancelled, out of the Running list. Afterwards `automatic`, `automatic-step`, `start`, `attach`, `freeze`, `retry`, `reconcile`, `review`, `approve`, `resume`, `answer`, `note`, `repair`, `sidecar-pass` and `tryout` refuse the run. `status` (with `abandoned` and a `next_step` naming the brief and the follow-up), `export` and `brief` still read it. A run that reached integration is refused, and so is a second abandon. Worktrees and evidence stay; cleanup is a separate decision: `clean` removes an abandoned run's worktrees but keeps its source checkout, which `brief` reads.
- **The reviewed route for hand fixes.** A fix made by hand after approval, a re-review after an outage or a usage limit, and a merge chore all go through review the same way: a new run of the feature, or of a one-lane hotfix feature folder (`challenge: false`, the `general` reviewer only), whose lane task only restores the commit. Start from `workflow/templates/restore-task.md`: restore `<sha>`'s owned paths with `git restore --source=<sha> --staged --worktree -- <owned paths>`, confirm `git diff --stat <sha> -- <owned paths>` prints nothing, change nothing else and run no checks (the controller verifies), then write the completion. Freeze refuses a change outside the lane's owned paths, the reviewers review whatever lands, and the empty diff catches drift. A feature with the design challenge on still runs it on the restore task.

## Attention notifications

`python -m workflow attention-notify` pushes each new line of `attention.jsonl` ("Attention records") to you through the notify command you already use. It is a oneshot: it reads the feed from the byte offset it saved last time, groups the new records by run in feed order, sends one message per run with the title `md-manager` and one line per record, `[run_id] kind: text`, appends one line per pushed record to `attention-notified.jsonl`, then saves the offset. A systemd user timer runs it every minute. It reads no secret: the tokens and channels stay in the command it runs. Every file lives beside the Projects registry, so `MD_MANAGER_PROJECTS_CONFIG`'s folder when it is set, else `~/.config/md-manager/`:

| File | Holds |
| --- | --- |
| `notify.json` | `{"argv": ["<command>", "<argument>", ...], "env": {"<NAME>": "<value>"}}`: the command run for each message, with the title and the body appended as its last two arguments; it must exit 0 within 30 seconds. On this machine it is agent-workflow's `runner/notify.sh`. `env` (optional) sets variables in the command's environment, which is how the target chat is chosen: `{"TELEGRAM_CHAT_ID": "-100…", "NOTIFY_STRICT": "1"}` makes `notify.sh` send to that Telegram group instead of its default, the operator's DM, and exit non-zero when the send fails. A name that looks like a token, key, secret, password or credential is refused (exit 2): the tokens stay in the command's own files, never here. `topic` (optional): `{"argv": ["<command>", ...], "env": "TELEGRAM_THREAD_ID"}`, the command that creates one topic per run in a forum group (run with the run id as its last argument, it prints the topic's thread id) and the variable each send of that run then carries; see "Telegram group with topics" below. |
| `presence.json` | `{"status": "working"\|"away", "since": "<ISO>", "until": "<ISO>"\|null}`, written by `presence` (below). Missing or malformed reads `working`. |
| `attention-notify.state.json` | the offset, the sends of the last hour (the cap), the held lines, `pushed`, the records a pass already sent before a send failed, each by run id, timestamp, kind and node (kept while a send fails, cleared once every message went), and `topics`, each run's thread id in the forum group. Deleting it replays the whole feed from its first byte, drops the held lines and resets the cap window: to get past a refused line, edit the line where its copy lives instead (Failures, below): the feed for an unsent run record, this file's `held` entry for a held one. |
| `attention-notified.jsonl` | one line `{at, sent_at, run_id, kind}` per pushed record; the raw material for a by-hand finished-to-noticed measurement, from the run's first `--by operator` event after `sent_at`. |
| `attention-notify.lock` | taken without blocking by each pass; a pass that finds it held (a run by hand while the timer fires) says so and exits 0. |

**Presence.** `python -m workflow presence` prints the status; `presence working` and `presence away [--for 9h]` set it (`--for` takes `9h`, `30m`, `1h30m`, `2d`); after `until` passes the status reads `working` again, so a forgotten flag flips itself back. While **working**, every kind is pushed every minute. While **away**, the kinds that wait on you (`question`, `pane`, `challenge_paused`, `review_blocked`, `controller_blocked`, `awaiting_approval`) are pushed at once; `finished`, `sidecar`, `attack` and `panel` are held and go out as one digest when the status returns to working. The message carries no presence marker.

**Cap and digest.** At most 10 messages go out per rolling hour across all runs; only sent messages count. Past the cap a run's lines are held, and the next pass sends one digest for what is held: a first line `N more records`, then the lines. The digest counts as a send and exactly one goes out per full window; after it the held lines wait for a slot to free. A pass sends the run messages first and the digest last, so a held line the channel refuses holds back no question or block that waits on you. Each text is cut at 300 characters and a body at 3,500 (one Telegram message), ending with `… and N more in the feed`; the lines left out are held for the next digest.

**Failures.** A missing or malformed `notify.json`, or a feed that cannot be read, prints one line to stderr and exits 2 with nothing sent and the offset unchanged, so `systemctl --user status attention-notify.service` shows the unit's failure. A command that exits non-zero, cannot run or does not end within 30 seconds is printed the same way; the offset stays, and the next pass reads again from it to the end of the feed, skips the records already sent (the state's `pushed`, each by run id, timestamp, kind and node, never a byte span) and sends the rest, so a record that did go out is not repeated and one appended meanwhile is not lost, even when the feed changed under the retry. No placeholder goes out in its place: a line the channel keeps refusing (a body it rejects) is retried every minute and the only sign is the unit's failure, since the broken channel is the one that would tell you. The pass stops at the first refusal, so the records of runs whose first unsent record follows the refused line wait, unlost, until the line is edited or deleted; the digest is planned last, so a refused digest holds back nothing else. Unstick it by hand, in the place where the refused text lives. An unsent run record (its line is at or after the saved offset: the state's `offset`, and `pushed` lists what already went): edit that line's text in `attention.jsonl`, or delete the line; the next pass re-reads from the offset and nothing is lost. A held record (the digest: `N more records` is its first line) has already been read past, and its only copy is the matching entry of `held` in `attention-notify.state.json`: stop the timer (`systemctl --user stop attention-notify.timer`), edit that entry's `text`, or remove the entry to give it up, start the timer again. Never edit or delete a feed line before the offset: that shifts the bytes under the offset, which then lands mid-line and the first unsent record loses its head, and it changes nothing for a held record. Do not delete the state file for this: that replays the whole feed and drops every held line. A feed shorter than the offset (truncated or replaced) is read from the start; a line still being written waits for the next pass; a complete line that is not a record is reported and skipped. The feed is read with a plain open, never its lock, so a slow notify call never costs a controller a record.

**Telegram group with topics.** The operator's design: one Telegram group with Topics (forum) on, one topic per run named after the run id, every record of the run posted inside it, and the operator's panel bot in the same group so replies in a run's topic can reach the panel. The tailer does its part through the notify command: with `topic` in `notify.json`, a run's first message runs `notify.sh --create-topic <run id>` (Telegram's `createForumTopic`; the script prints the `message_thread_id`), the id is kept in the state's `topics`, and every message of the run is sent with `TELEGRAM_THREAD_ID` set, which `notify.sh` passes as `message_thread_id`. A digest (lines of several runs) goes to the group's general topic. A topic that cannot be created (the group has no topics, the bot is no admin, a network failure) is one stderr line and exit 2: the message still goes, without a topic, and the next message of that run tries again. What the operator provides: the group's chat id (a negative number, `-100…`), Topics switched on in the group settings, and the notify script's bot (on this machine agent-workflow's `notify.sh` uses the Telegram plugin's bot token) added to the group as an administrator with **Manage topics**; a bot without it gets `not enough rights` from `createForumTopic`. The panel's Telegram plugin (claude-plugins-official `telegram` 0.0.7, read, not changed): it delivers a group's messages only once the group is opted in with `/telegram:access group add <chat id>`, and then only messages that @mention the bot, reply to one of its messages or match `mentionPatterns`, unless the group was added with `--no-mention` and the bot's privacy mode was switched off at BotFather; what reaches the session is `<channel source="telegram" chat_id message_id user user_id ts>`, with no `message_thread_id`, `is_topic_message` or replied-to message, and its `reply` tool takes `chat_id`, `text` and `reply_to` (a message id, which Telegram places in that message's topic) but no thread id; permission prompts go to the allowlisted DMs only, never to a group. So the panel can read a message typed in a run's topic and answer inside it by replying to it, but it cannot tell from the message which topic it came from: routing a reply to the run's session needs the run id in the message, or a plugin change that exposes the thread id.

**Install** (the unit files are examples at `workflow/systemd/`; the service runs md-manager's venv from `~/dev/md-manager`, so edit both paths if yours differ, and uncomment its `Environment=` line with the registry path your launches use when it is not the default):

`launch` refuses an existing run directory and an existing source checkout. Its first line names an automatic run's profile, `Run <dir> (profile unattended): ...`, and says how the run ends, from the automatic settings `prepare` pins as `plan.automatic`: `automatic, finish verified-feature-branch: ... it does not stop for integration approval, ...`, `automatic, finish approval (the attended profile): once every reviewer approves, the run stops for your approval; ...` (or `(a feature marked critical)`), or `manual: you freeze the workers, import each review and approve the fast-forward of <branch>; nothing is pushed`. It runs, in order: `preflight` (on your checkout), `git worktree add -b <branch_prefix>/<run-id> <run root>/<run-id>.source HEAD` (in the target), `prepare`, then registers the run in the Projects registry, then `start`, and with `--automatic` also `automatic`; when the design challenge paused the run at `start`, or held it after a pass (`--hold-challenge`, `--profile attended`), it stops there and exits 0; when an automatic run stopped for your approval, it prints the approve command and the open items and exits 0. Ctrl-C while the design challenge runs prints the `resume` command; later it prints `automatic --live` for an automatic run. A registry that cannot be updated after `prepare` is reported and the launch continues. A policy `failure_drill` that names a lane the selection leaves out is skipped, with a note and a timeline event.

## Interactive panes and session identity

LangGraph launches each worker with `claude --bg` into a persistent native terminal in its worktree; Herdr only attaches to terminals that already exist (`claude attach <id>` in each pane, keyboard input enabled). Herdr never submits tasks, launches replacements or decides that work is accepted.

- A dedicated `Workflow: <run-name>` tab holds one `Claude: <lane>` pane per lane in declared order, then one `Claude: reviewer [<id>]` pane per reviewer. Your own tab is not split and focus is preserved. Before typing a command into a pane, the adapter checks that only the pane's idle shell is in the foreground; an occupied pane is refused.
- **Ctrl+Z** detaches to the pane's shell; the background session keeps running, and `answer` types into that pane only once attach-one runs in it again. Closing a pane or losing SSH does not stop the worker. **Ctrl+C inside Claude** interrupts its current turn. Do not type `/exit` unless you mean to end the session.
- Direct human messages consume Claude usage and change work outside any graph node; the graph does not know them. Idle or done is never completion.
- Native `--bg` ignores `--session-id` and assigns its own id: the plan's `session_id` is a launch token. The launcher writes its intent before calling Claude, keeps the launch output, binds the id printed by that launch and resolves the exact UUID through `claude agents --json`, cross-checking worktree and launch name. A guessed UUID or a name-only match is never adopted; unsupported states fail closed.
- `done` in the native inventory is a finished turn, not an exited process; attaching requires a live native PID as well. PIDs are never authority to kill a process.

## Verification policy and evidence

Feature requirements are supplied per feature; the gates are reusable. The policy (`contracts/workflow/verification.schema.json`, bundled with the tool) gives each lane a node id, a `role` label, exact owned path prefixes (no globs; `src/workflow` owns itself and its descendants, not `src/workflow-other`; lanes never overlap), its checks and `required_check_kinds`. A check has a unique id, a kind (`build`, `typecheck`, `unit`, `integration`, `contract`, `browser`), an argv array, a timeout and, for browser checks only, named scenarios. Every listed check is required. `independent_review` and `integration_approval` are schema constants, `true` in every policy: they say what a policy cannot switch off, not whether the run stops for approval. That is the run's finish policy (`plan.automatic`): a manual run waits at `approve`, an automatic run with finish `approval` (attended, or a critical feature) waits there too, and an automatic run with finish `verified-feature-branch` fast-forwards its feature branch itself once every reviewer approves. Packets no longer list `pending_gates`; those written before keep the key, and a recheck recomputes the gate without it.

| Lane kind | Usually required | Add when relevant |
| --- | --- | --- |
| UI | build; browser tests for every named scenario with a PNG screenshot each | typecheck, accessibility, mobile/desktop scenarios |
| Backend | unit tests with a nonzero passing count | contract, integration and failure/recovery tests |
| Every lane | ownership, exact run/attempt/revision identity, executed check logs, matching artifact hashes | task-specific checks |

- Policy commands are operator-approved configuration, never code a worker invents. The runner executes argv without a shell, with timeouts, in a separate verification worktree with isolated caches, ports and artifact paths.
- Test checks need parsed counts (Python unittest or Node TAP/spec summaries); an exit code with zero executed tests is not evidence. Browser checks need exact scenario ids, passed status and a screenshot each. Build and typecheck checks need no counts.
- The evidence sidecar binds the policy SHA-256 (canonical JSON: sorted keys, no whitespace, literal UTF-8), run id, lane, attempt and output commit; each check points to one entry of the worker result, whose command is `shlex.join(argv)` run in the backend-owned worktree.
- The **worker phase** verifies one lane's snapshot in isolation: its `build` and `browser` checks run and are recorded but do not gate (`gate.deferred_checks`), because another lane may be changing what they compile against; `unit`, `contract` and `integration` gate in both phases. The **candidate phase** runs every lane's checks on the combined revision and gates on all of them (a one-lane run without a browser check reuses its worker packet, as above).
- The timeline says what each gate saw. A passing worker gate names each deferred check with its exit code: `Required tests and artifacts passed; recorded for the candidate gate: build (exit 1), browser (exit 0)`. A lane's candidate check keeps its event `Combined revision <sha>` (`; worker checks reused from <packet> ...` when it reused the worker packet); when it blocks, a second event on the same node gives the gate's reasons (`Candidate gate blocked on attempt <n>: <reasons>`). A check that passes on attempt N after attempt N-1 failed on the same revision says so: `passed on attempt N after attempt N-1 failed` in the verify event, or `Candidate gate passed on attempt N after attempt N-1 failed` as the candidate's second event. A lane repair's new revision starts over.
- One exception: the evidence of a passed scenario test (a duplicated `[scenario:<id>]` title, a missing, misnamed or duplicated `screenshot:<id>`, a screenshot outside the output directory) is the lane's own work whatever another lane changes, so it gates in the worker phase too, prefixed with the check id (the packet's `scenario_errors`). The browser check's exit status, failing tests, Playwright's global errors and a report that was never written stay deferred.
- Artifact paths resolve through a backend-owned registry, constrained to its root and hash-checked. PNG header checks are format sanity only; screenshots are for the reviewers to examine.

## Operator boundaries

- Choose the feature, ownership and acceptance tests before preparing a run; `verification.example.json` is illustrative.
- Tests and setup commands are trusted code, not sandboxed workloads; worktrees are not an OS sandbox.
- Terminal edits must stop before frozen verification. Independent review is a separate session or an imported artifact; the graph never invents approval.
- Ambiguous native sessions, partial candidate allocations, source drift and exhausted usage stop for operator action, never a silent relaunch or provider switch.
- Update Claude Code between runs, not during them. An update replaces the binary under every running session and restarts the background service, which drops attached panes. The controller turns the auto-updater off in every Claude process of a run, so a run never updates itself; your other Claude sessions still do. The processes it starts itself (print reviewers, the challenge job, `attach`, the `agents` and `stop` calls, the short `claude --bg` helper) get `DISABLE_AUTOUPDATER=1` in their environment. Worker and native reviewer sessions are started by Claude Code's background service with the service's own environment, which the helper's does not reach, so every `--bg` command also passes one `--settings` argument, merged over your own settings: `DISABLE_AUTOUPDATER=1` and `CLAUDE_BG_ISOLATION=none` in its `env`, and `"worktree": {"bgIsolation": "none"}`, so the `--bg` system prompt neither sends the session to EnterWorktree nor tells it to commit and push. A worker's `--settings` adds its deny rules, `HUSKY=0` and `GIT_TERMINAL_PROMPT=0` (README "What a worker can reach"). Preflight refuses a Claude CLI without `--settings`. After an update, restart the long-lived Claude sessions started before it: they keep running the deleted binary and keep reinstalling Claude Code. `start` and `resume` name them before launching (pid, working directory and command line of each process whose executable is `(deleted)`), as does an `automatic` exit 75; this is a warning, never a refusal.
- After a Claude Code update, run a canary before you trust a long run: one throwaway worker session started as the controller starts workers (`claude --bg` with the worker's `--settings`), then check in it: its `--bg` system prompt neither sends it to EnterWorktree nor tells it to commit and push; a Read of a denied path (`~/.config/gh/hosts.yml`) and a Bash `pkill` are refused; a Read of its own saved tool output (`~/.claude/projects/<project>/<session>/tool-results/...`, the path Claude Code names when an output is too large to show) works; and a Read of its own transcript (`~/.claude/projects/<project>/<session>.jsonl`) is denied while Bash `tail` or `grep` of it works. A check that fails means the README's "What a worker can reach" no longer holds for this version: settle that before the run.
- `report.html` is a local snapshot viewer; the controls are local CLI actions, not a web service.
- Run and worktree cleanup (`clean --by operator`), pushing and merging `main` remain separate, explicit actions. The one automatic removal is a passed check attempt's checkout and caches.
