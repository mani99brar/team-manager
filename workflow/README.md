# LangGraph workflows

A supervised multi-lane workflow for Claude Code workers. The controller lives in md-manager's `workflow/` and drives any Git repository: one native interactive Claude worker per configured lane, each in its own worktree and Herdr pane, then an explicit freeze, immutable snapshots, isolated checks, a combined-candidate check, independent review (one or more reviewers), approval and a local fast-forward. Automatic mode (`--automatic`) runs the same graph unattended and stops at an independently reviewed, verified feature branch; an attended run (`--profile attended`) or a feature marked `critical` stops after review for your `approve` instead. The controller never merges `main` and never pushes. Workers run as your account, so that alone does not stop a worker from pushing: see "What a worker can reach".

**Procedures, recovery and bounds are in [RUNBOOK.md](RUNBOOK.md).** `report.html` in each run directory is a local graph/results viewer, and `run-state.json` (export 1.7.0) is what md-manager's Projects viewer reads.

Features at `feature.json` 2.2.0, 2.3.0 and 2.4.0 (what `init` writes) run with enforced guardrails: tasks written as outcome briefs, a `decisions.md` from an interview before launch, a design challenge before any worker starts, and worker completions that say what would prove them wrong (see "Guardrails" below). A 2.3.0 or 2.4.0 feature may add a review sidecar that reviews the lanes while they work (see "Review sidecar"). A 2.4.0 feature may be marked `critical` (the grill sets it): its automatic runs stop after review for your approval (see "Approval stop").

## Commands

```bash
PY="$HOME/dev/md-manager/.venv/bin/python"   # run from md-manager's checkout, or anywhere with PYTHONPATH pointing at it
```

| Command | What it does |
| --- | --- |
| `$PY -m workflow init <feature> [--repo X]` | writes `features/<feature>/` in the target (and a starter `CLAUDE.md` when missing); never overwrites |
| `$PY -m workflow launch <feature> [--repo X] --dry-run` | validates the feature and prints the commands and the registry entry; executes nothing |
| `$PY -m workflow launch <feature> [--repo X] --live [--automatic] --by operator` | preflight, feature branch, prepare, start (and supervise with `--automatic`) |
| `$PY -m workflow <action> "$RUN"` | one pipeline step: `preflight`, `prepare`, `start`, `automatic`, `freeze`, `review`, `approve`, `retry`, `reconcile`, `attach`, `status`, `export` |
| `$PY -m workflow resume "$RUN" [--accept-challenge "<reason>"] [--herdr] --by operator` | 2.2.0: commits the edited feature files on the run's branch and reruns a paused design challenge on them, or accepts it with a reason; then launches the workers (and supervises an automatic run) |
| `$PY -m workflow answer "$RUN" <lane> "<text>" [--no-herdr] --by operator` | 2.2.0: answers a worker's question, restarts its deadline and types the answer into its pane |
| `$PY -m workflow note "$RUN" <lane> "<text>" --by operator` | types `[Note from the operator N-k] <text>` into a running worker's pane and records it in `<lane>.notes.json` and on the timeline; an operator note may amend the lane's task, a maintainer note is advice |
| `$PY -m workflow sidecar-pass "$RUN" [--final]` | 2.3.0 with a `sidecar`: one review sidecar pass, synchronously; a manual run's passes, and its final pass before `freeze` (refused while an automatic supervisor owns the run) |
| `$PY -m workflow repair "$RUN" <lane>[,<lane>] --workspace --by operator`, then `--commit <sha> --reason "<text>" [--dry-run]` | after freeze and before review: a detached worktree at the failing candidate or lane snapshot, then that fix commit as new lane snapshots with the checkpoint forked at the freeze boundary; launches nothing and runs no check, `automatic --live` (a manual run: `retry`) re-verifies (RUNBOOK "Blocked after freeze: repair a lane") |
| `$PY -m workflow check-report <feature-dir or policy.json> <lane> <report.json> [--all]` | checks a Playwright JSON report against the lane's browser scenarios with the verifier's own rules; exits 1 on any problem (a browser lane's pinned task spells out the command it runs before completing) |
| `$PY -m workflow.interactive attach-one "$RUN" --node <node>` | reconnects one native session in the current terminal (what the Herdr panes run) |

Every gate action (`start`, `automatic`, `retry`, `reconcile`, `approve`, `resume`, `answer`, `repair`, `launch`, `note`) requires `--by operator` or `--by maintainer`, with no default. The maintainer is a Claude session acting for the operator, for mechanical recovery only: it is refused `answer`, `--accept-challenge`, `repair`, `approve` and `launch`, and `resume` while the design challenge is paused (unless it finishes an interrupted rerun the operator started; RUNBOOK "Who acted"), or while a pinned feature file holds an edit made after an interruption. The actor goes into the timeline, never into `challenge.json` (RUNBOOK "Who acted: --by and notes").

The target is `--repo`, else the current directory when it is a Git repository with a `features/` directory, else md-manager itself; the run records it in `plan.json` (`repository`), so later actions need no flag. A feature is any directory under `<target>/features/` that holds a `feature.json`. Flags, actions and the files of a run directory are listed in [RUNBOOK.md](RUNBOOK.md#command-reference).

## Use it in another project

1. **Prepare the repository.** It must be a Git repository with at least one commit and a named branch. Sessions start in worktrees of it with `--safe-mode`, which does not load its `CLAUDE.md`. For a 2.2.0 or 2.3.0 feature, prepare pins `CLAUDE.md` as the run's base commit holds it, up to the heading `## Workflow (operator notes; workers skip this section)`, and every worker, design challenge and reviewer prompt gets that text (see "Guardrails"): put the project's conventions above the heading (build and test commands, style, directories a worker must never touch) and your notes about running workflows below it. A 2.0.0 or 2.1.0 feature gets none of it, so each task must state what its lane needs. `init` writes a starter `CLAUDE.md` when there is none; it ends with that heading.
2. **Scaffold the feature.**

   ```bash
   $PY -m workflow init my-feature --repo ~/dev/project-B
   ```

   This writes `features/my-feature/` with a 2.4.0 `feature.json` (one lane `main`, the bundled `general` and `coverage` reviewers, a `prd` to name or delete, `critical: false`; its `README.md` shows the optional review `sidecar` key), a 1.2.0 `policy.json` with a placeholder check, `main-task.md` in outcome-brief form (`## Goal`, `## Context`, `## Constraints`, `## Acceptance`, `## Stop`; its Acceptance keeps one default line: run targeted tests while iterating, then the lane's non-browser policy checks once before the completion, and browser specs only through `check-report`; that line alone still leaves the Acceptance empty), a `decisions.md` placeholder in the grill's four sections and a `README.md`. Every value to decide is a `TODO:` placeholder; `launch` refuses the feature and names each one until none is left. It checks only the files `init` writes (`feature.json`, `policy.json`, `README.md`, `decisions.md` and the task files), and only JSON values or Markdown lines that begin with `TODO:`, so prose that mentions the marker is fine. Add lanes by adding a `workers` entry to both files and a task file per lane.
3. **Interview.** Run the `workflow-grill` skill (below) in Claude Code in the target: `/workflow-grill my-feature`. It asks at most five questions and writes `decisions.md`.
4. **Fill in and commit.** Give each lane its owned paths and the checks the controller runs independently (`kind` `unit` needs a Python unittest or Node TAP/spec summary; see "Verification policy and evidence" in the runbook). A `browser` check names its `scenarios`: each id must appear in exactly one test title as `[scenario:<id>]`, and that test, when it passes, must attach exactly one `image/png` named `screenshot:<id>` (other attachments are fine). The task `init` writes states this with the Playwright JSON report command a browser lane runs before completing, and the controller appends the exact `check-report` command to a browser lane's pinned task (see "Playwright evidence convention" in the runbook); delete the paragraph for a lane without browser checks. A reviewer's `prompt` is a feature file or `builtin:general` / `builtin:coverage` (the briefs in `workflow/prompts/reviewers/`). Commit: preparation refuses a dirty tree.
5. **Accept permission bypass once.** Automatic workers start with `--dangerously-skip-permissions`, which Claude asks you to accept interactively the first time. Do it once before the first automatic run, in the target: `cd ~/dev/project-B && claude --dangerously-skip-permissions`, accept, then exit.
6. **Dry run, then launch** from a Herdr pane:

   ```bash
   $PY -m workflow launch my-feature --repo ~/dev/project-B --dry-run
   $PY -m workflow launch my-feature --repo ~/dev/project-B --live --automatic --reviewer-transport print --by operator
   ```

   A 2.2.0 launch runs the design challenge before any worker; when it pauses, the launch exits 0 and prints the concerns and the `resume` commands. Otherwise an automatic launch keeps printing the run's timeline in that pane, one line per event (UTC time, node, status, message); a resumed `automatic --live` starts with the last five events. Runs are stored under `~/.local/state/agent-workflows/<repo-name>/<feature>/<run-id>` (`--run-root` overrides; storage must be outside the target). md-manager keeps `~/.local/state/md-manager-workflows/<feature>`.
7. **See it in the Projects viewer.** A live launch adds or updates the target's project in the registry named by `MD_MANAGER_PROJECTS_CONFIG`, else `~/.config/md-manager/projects.json`: project id is the repository name lowercased, the workflow id is the feature, with its runs root and the graph over every lane the feature declares (a `--workers` subset launch registers the same graph). Only that workflow is replaced, and its stored labels are kept while its nodes are unchanged; every other entry keeps its bytes. The file is written atomically under a lock on its directory, so launches in parallel tabs cannot drop each other's entries, and a symlinked registry stays a symlink with its target updated. Runs roots are compared after resolving symlinks, as the server does. A malformed registry blocks the launch before any Git action; a runs root another workflow already covers leaves the file unchanged with a note. The dry run prints the entry it would write. The server reads the registry at startup, so restart it (with `MD_MANAGER_PROJECTS_CONFIG` pointing at the same file) to see a new project.

## What a worker can reach

A worker runs as your user, with Bash, and in automatic mode with permission checks bypassed. There is no sandbox yet: Claude Code's Bash sandbox needs bubblewrap, socat and user namespaces, which the VPS lacks (AppArmor restricts them). So every launch runs this way, and there is no flag for it. `prepare` pins it in `plan.json` as `worker_authority`: `{"worker_settings_sha256": ..., "sandbox": false, "authority": "account"}`, the digest of the exact `--settings` every worker gets (`sessions.worker_settings`). `report.html` shows it from the next report write (`start`, a step or `export`). That argument denies Claude Code's own file tools Read and Edit of `~/.ssh`, `~/.config/gh`, `~/.git-credentials`, `~/.pi`, `~/.claude/.credentials.json` and `~/.config/vps-wallet.env`; Read of the transcripts (`*.jsonl`) and `memory/` under `~/.claude/projects`; and Edit of all of `~/.claude/projects`, `~/.bashrc`, `~/.profile`, `~/.config/systemd`, `~/.gitconfig`, `~/.config/git`, `~/.claude/settings*.json` and the controller checkout (unless the run directory lies inside the controller checkout). The rest of `~/.claude/projects` stays readable: Claude Code saves a tool output too large to show in the session's `tool-results/` there and tells the worker to Read it. No rule can name the worker's own session, so every session's saved outputs are readable. A worker whose context was compacted cannot Read its own transcript (`~/.claude/projects/**/*.jsonl`): that Read is denied, and Bash `tail` or `grep` reads it. It never denies all of `~/.claude` or `~/dev`: a job's temp directory is under `~/.claude/jobs`, pine's worktrees under `~/dev/pine-runs`. It denies `Bash(pkill:*)`, `Bash(killall:*)`, `Bash(git push:*)` and `Bash(git commit:*)`, sets `HUSKY=0` and `GIT_TERMINAL_PROMPT=0`, and turns the background isolation off (`worktree.bgIsolation` `none`, as for every `--bg` session), so the `--bg` system prompt no longer tells a worker to use EnterWorktree, or to commit and push. The checks run without secret-like environment names (see the runbook's "Guarantees and boundaries").

None of this stops a program the worker runs. A Bash `cat ~/.ssh/id_ed25519` is not a Read tool call, `sh -c "git push"` or `kill $(pgrep -f x)` passes the prefix rules, and the network is open. Until workers run under another user or a sandbox, the only real fix is to move credentials off this account: move the funded deployer key in `~/.config/vps-wallet.env` to another user or a hardware wallet (only you broadcast mainnet transactions), put a passphrase on the SSH key, replace the gh token with a fine-grained one, take API keys such as the DeepSeek key out of `~/.bashrc`, and run the Telegram decision bot as another user.

## Guardrails (feature.json 2.2.0 and 2.3.0)

`init` writes 2.4.0, which keeps every 2.2.0 guardrail and the optional review sidecar of 2.3.0 (below) and adds `critical` (below); a 2.2.0 or 2.3.0 feature launches unchanged, and a 2.0.0 or 2.1.0 feature (md-manager's existing ones) still launches exactly as before, with the same commands and graph, and the launch prints a note that no guardrail is enforced and how to migrate: set `"version": "2.2.0"`, give every task the three required sections and write `decisions.md`. Runs prepared before the guardrails keep their commands, exports and 1.0.0 completion files unchanged. For a 2.2.0 or later feature:

- **Outcome briefs.** Every lane task needs `## Goal`, `## Acceptance` and `## Stop`, each with at least one non-blank line before the next `## ` heading (`## Context`, `## Constraints` and `## Process` are optional; three one-line sections are a valid task). `init`'s default Acceptance line on running the checks is process, not a result, so it does not count as such a line, bulleted or not; an Acceptance left with only that line is refused with a message that says so. `launch` refuses a task that lacks one or leaves one empty, naming the file and the headings, before any Git action. The worker prompt repeats the `## Stop` section as the bound on the work.
- **Decisions.** `features/<feature>/decisions.md` must exist and be non-empty; the `workflow-grill` skill writes it in four sections: `## Operator decisions` (`[O<n>]`: your answers, each with its question number, the chosen option's text and your words verbatim; never edited in place, so a later change is a new bullet citing the id), `## Grill defaults` (`[G<n>]`: the grill's own defaults, delegations with the items they cover and riders tagged `[added, not asked]`), `## Changes after launch` (`[L<n>]`, each with the run id and attempt) and `## Deferred`. It is pinned into `plan.json` at prepare and every worker and reviewer prompt includes it after the task. What binds depends only on whether the file has the `## Operator decisions` heading; no section is parsed. With it, the prompts say that the Operator decisions bind the run and win over the task, and that workers follow the other sections too but may depart from a grill default or a change after launch to apply a design-challenge note, or when the code shows the bullet cannot hold, only inside their own lane's owned paths (a departure that would change anything another lane reads is a question for you, and each departure is named in the completion's `open_assumptions`). Reviewers read the same: a contradicted Operator decision is P1 at least, while a departure named that way, inside the lane's owned paths and changing nothing another lane reads, is no contradicted requirement, and an unnamed or out-of-lane one is (the review rubric counts a contradicted line of `decisions.md` only among its Operator decisions, or anywhere in a file without the heading). The design challenge may reopen an Operator decision only by showing it cannot hold, as a P1, and the rest like the tasks. Without it (every file written before), all of it binds as before, the challenge reopens none of it unless it shows it cannot hold, and `launch` prints a Note saying so. An optional `prd` in `feature.json` (relative to the target, any format Claude can read, PDFs included) must exist; it is copied into the run for the challenge, and every reviewer prompt names the copy.
- **Project conventions.** Sessions start with `--safe-mode`, which loads no `CLAUDE.md`, so prepare pins the target's `CLAUDE.md` as the run's base commit holds it (a link inside the repository is followed; an edit in your checkout never counts) into `plan.json` as `conventions` (`commit`, `sha256`, `text`). The text ends at the line `## Workflow (operator notes; workers skip this section)`: what is below it, your notes about running workflows, no session gets; a file without that heading is sent whole, and no file pins an empty text. Every worker, design challenge and reviewer prompt (both transports) gets it right before `decisions.md`, and the review sidecar's pass prompt after its brief, under `Project conventions (CLAUDE.md at <commit>; the controller's rules, the task and decisions.md take precedence)`. `resume` keeps it: it commits only the pinned feature files, so `CLAUDE.md` is the same at every base the run moves to. `launch --dry-run` prints its source and size under `guardrails.conventions`, or `none`, and a Note naming each `## ` section below the operator-notes heading, since that text is cut. Runs prepared before have no `conventions` key and get no block. There is no separate size cap on `CLAUDE.md`: a worker's or native reviewer's prompt travels as one command-line argument, and a launch refuses one over 120,000 bytes before it writes anything (RUNBOOK "Status, failures and recovery").
- **Design challenge.** It runs inside `start` and `resume`, not as a LangGraph node: it must decide before any worker session exists, and it pauses and resumes on its own. The exported graph shows it as the first node, `challenge` ("Design challenge"), and every launch depends on it. Before any worker session, one read-only `claude --print` job (Read, Glob and Grep only, a worktree at the base commit) reads the pinned PRD, tasks, project conventions and decisions and returns concerns (severity P0, P1 or P2, each with its consequence; each message ends with `Recommendation: <one action and its done-condition>`, never a fallback such as "or at least", since two options left make it your decision with the recommended one first, and `Acts: operator | worker | note`; each P0 and P1 cites the file:line it rests on or says "no file evidence"), the strongest simpler alternative and one cheap experiment; the controller validates it against `contracts/workflow/challenge.schema.json` and writes `challenge.json`. While the job runs, the terminal prints `Design challenge attempt <n> still running (<m> min)` once a minute (never a timeline event), and Ctrl-C stops the job and prints the `resume` command that runs it again. Only P2 concerns: `passed`, the workers launch. Each worker prompt, and never a reviewer's, carries the final record's concerns after `decisions.md` as advisory notes numbered as in `challenge.json`, without the alternative and the experiment: the worker does each recommendation or says in its completion why not, and asks you (a question in an automatic run, in its pane otherwise) before it builds on a note marked `Acts: operator`. After `--accept-challenge` the overridden P0/P1s follow apart, with your reason, as context only: the worker neither acts on them nor asks about them, even one marked `Acts: operator`. These labels are text: the schema and the pause rule are unchanged, so a P2 marked `Acts: operator` pauses nothing. A P0 or P1: `paused`, no worker is launched, the timeline records the pause, the run's attention record says so (`challenge_paused`, RUNBOOK "Attention records") and the launch exits 0 printing the concerns and the commands. Then either edit the task files, `decisions.md` or the PRD in the run's source checkout (its own worktree, which the paused message names) and run `$PY -m workflow resume "$RUN" --by operator` (re-reads them from the paths pinned at prepare, commits them on the run's branch, moves the run to that commit so the source checkout stays clean for integration, updates the plan's copies and reruns the challenge as the next attempt, whose prompt lists the paused attempt's P0/P1 concerns and the changed files and asks for each concern again unless the change resolves it; without an edit `resume` refuses, since a rerun on the same files would only re-roll the same challenge, and a concern outside the feature files needs a new run; earlier attempts stay as `challenge-<n>.json`; the policy is never re-pinned; any other change in the source checkout, a task or `decisions.md` with a line that begins with `TODO:` (as launch refuses it), or a run worktree that is not the clean base, is refused before anything is committed; until the move is pinned, `challenge-revision.json` makes `start` and the override refuse and a rerun continues it), or run `$PY -m workflow resume "$RUN" --accept-challenge "<reason>" --by operator` to record `accepted` with the reason and continue without rerunning (refused while a pinned feature file no longer holds the plan's copy, and when the paused attempt read other files than the plan now pins because a later rerun failed). Add `--herdr` to attach the worker panes. `"challenge": false` in `feature.json` records `disabled` and the graph has no challenge node.
- **Completion 1.1.0.** A worker's completion file adds `untested` (behaviours no executed check covers; may be empty), `falsifying_check` (the check id or command that would fail if the work were wrong) and `verify_yourself` (one assumption the operator should verify), plus `question` (null). A `completed` file without the evidence is refused, and a 2.2.0 run refuses a 1.0.0 file; runs prepared before keep reading 1.0.0. The prompt asks the worker to end its `summary` with a Proof table: one row per Acceptance line and per `## Design (settled)` line, each naming its proof (a test, a check id, a self-report, or none); the coverage reviewer verifies each row. Every reviewer gets `open_assumptions`, `untested`, `falsifying_check` and `verify_yourself` inline, as worker claims (unverified). The commands actually executed remain the verifier's evidence, not the worker's claim. When the controller first accepts a lane's completion, the lane's timeline says so once: `Worker <lane> completion accepted: <n> untested, verify_yourself given` (or `none`).
- **Questions.** A worker may end its turn with `status: question` and the text in `question`. The controller keeps the file as `<lane>.question-<n>.json`, lists it in `<lane>.questions.json`, records an event and pauses only that lane's deadline from when the worker wrote the file (persisted in `<lane>.deadline.json` as `paused_seconds`, so a restarted controller computes the same deadline); the other lanes keep running. Answer with `$PY -m workflow answer "$RUN" <lane> "<text>" --by operator`: it records the answer, restarts the deadline and types it into the lane's Herdr pane (`herdr pane send-text`, then Enter), followed by the lane's new deadline in UTC (for a lane whose completion was already accepted: none while another lane works, then the latest lane deadline); with `--no-herdr` it prints the `claude attach <id>` command and that text to type yourself. It types only while the pane's foreground is `claude attach <id>` of that session, never into the shell a detach leaves or attach-one between two attaches. A failed delivery (no Herdr pane, a closed pane, a pane not showing the session) keeps the answer recorded and the deadline running; rerun the same command, or with `--no-herdr`, to deliver it: the text is typed at most once (after a failed Enter the rerun presses Enter only, and only while `herdr pane read` shows the text in the session's input; otherwise look at the pane). After a Herdr timeout on the text itself, look at the pane before rerunning: the text may already be in the input. Typing the answer straight into the pane works too: when the session works again (a poll sees it `working`, or it writes its next completion signal: the registry may report a whole reply turn as `blocked` or `done`) the controller records a placeholder answer and restarts the deadline; until that next signal `answer` can still replace it, since a session may also work again on its own. Once the worker went on from its question (its next completion signal, its saved handoff, its stop), `answer` is refused and types nothing: a stopped worker's pane is a shell. At most three questions per worker: the prompt says so from the start, and a fourth is treated as `blocked`. Before a worker builds on a reading of a task line that departs from its plain words (its own reading, or one an advisory note or a sidecar message suggests), its prompt has it say so: in an automatic run it records an open assumption that starts with `reading:` and quotes the line, and goes on (a run launched with `--automatic --profile attended` asks with a question quoting the line instead); in a manual run it asks in its pane. A behaviour it could not test is no such reading: it stays in `untested`. A run of a 2.0.0 or 2.1.0 feature (completion 1.0.0, no question status) gets the same rule: recorded in an automatic run whatever its profile, asked in its pane in a manual one.

The export (1.5.0) carries all of it for the viewer: `inputs.decisions`, `inputs.challenge` (the latest `challenge.json` without `run_id`/`version`, plus `attempts`), on `inputs.workers.<lane>.completion` its `version`, the three evidence fields (null for a 1.0.0 completion), the `question` status and `question` (the text of a question not recorded yet), and `inputs.workers.<lane>.questions` (`{n, question, asked_at, answer, answered_at}`, `[]` for older runs). A completion is exported only as the controller reads it: a file it refuses (another version, stale or foreign) is null, and a fourth question is exported as `blocked` with its text. The Projects API serves them as run inputs 1.4.0.

### The workflow-grill skill

The interview ships with the tool as a Claude Code skill in `workflow/skills/workflow-grill/SKILL.md`. Link it once into your personal skills so every repository can use it:

```bash
mkdir -p ~/.claude/skills
ln -s "$HOME/dev/md-manager/workflow/skills/workflow-grill" ~/.claude/skills/workflow-grill
```

Then, in Claude Code inside the target repository: `/workflow-grill <feature>`. It reads the target's `CLAUDE.md`, the PRD and the lane tasks, and asks at most five questions one at a time, each with a recommended default and its consequence. When a lane owns a path listed under "Critical paths" in the operator notes of the target's `CLAUDE.md`, its first question is whether AI workers may write those paths; it records your answer with the feature's R32 cell as an Operator decision and sets `"critical": true` (2.4.0) when you confirm the code is critical ("Approval stop"). Every limit on what the feature delivers (only, never, except, excluded, deferred) is played back to you as the first question, even when the documents quote your own words. An answer commits to nothing its option did not state: a rider becomes its own question or a grill default tagged `[added, not asked]`. Where the drafts or its own defaults keep a value by hand that the repository already records, it offers the repository's own mechanism, and it labels a reason that exists only because of the workflow run as a run limit. It restates each answer you give in your own words, keeps a question you did not answer as a `TODO: Q<n>` line (launch refuses it), resolves or defers anything else still open after the fifth, and writes `features/<feature>/decisions.md`. Before it hands back, also when you asked up front to launch, it lists every bullet you did not choose (an existing file's `[L<n>]` changes after launch included, which a re-grill keeps as they are, with its Operator decisions) and asks you to confirm or edit; that question is not one of the five. What you change there, or confirm by its id, is recorded as a new Operator decision with the date. On an older `decisions.md` without `## Operator decisions` it carries the old bullets over as grill defaults and asks in the same question which of them are yours. It never writes code; `critical` is the one key it sets outside `decisions.md`.

## Approval stop (attended runs and critical features)

An automatic run normally fast-forwards its feature branch once every reviewer approves. It stops after review for your approval instead when you launched it with `--profile attended`, or when its `feature.json` (2.4.0) says `"critical": true`. The workflow-grill skill sets that flag: when a lane owns a path listed under "Critical paths" in the operator notes of the target's `CLAUDE.md`, its first question is whether AI workers may write those paths, and it records the answer with the feature's R32 cell. Launch never refuses a lane for its critical paths. `prepare` pins the finish as `plan.automatic.finish: "approval"`. The run then stops with the approve command (`$PY -m workflow approve "$RUN" --bundle-sha256 <digest> --by operator`) and the open items: the open review findings below the block threshold, the sidecar's unresolved findings, and each lane's `untested` and `verify_yourself` items. `approve` integrates as in a manual run; the maintainer is refused it. Nothing is pushed.

## Review sidecar (feature.json 2.3.0)

An optional independent senior-engineering reviewer beside the workers during the work phase ([docs/PRD_REVIEW_SIDECAR.md](../docs/PRD_REVIEW_SIDECAR.md)). It advises: it never blocks, pauses, approves, freezes or integrates anything, and the reviewers after freeze stay the gate. Declare it in `feature.json` 2.3.0 or 2.4.0:

```json
"sidecar": {"prompt": "builtin:senior-review", "cadence_seconds": 900, "pass_timeout_seconds": 600, "max_passes": 16, "max_messages_per_lane": 6}
```

- **Declaration.** `prompt` is a feature file (existing, non-empty) or `builtin:<id>` for a brief in `workflow/prompts/sidecar/` (today `senior-review`); the bounds are optional, with the defaults shown and the ranges `cadence_seconds` 60..7200, `pass_timeout_seconds` 60..3600, `max_passes` 1..64, `max_messages_per_lane` 0..20. `false` or no key: no sidecar. `sidecar` on 2.2.0, an unknown builtin, a missing or empty brief, an unknown key and a bound out of range are refused before any Git action, naming `feature.json` and the key; so is a lane named `sidecar` or `sidecar-*`. The launch passes `prepare --sidecar-brief <path> --sidecar-settings <json>`, which pins the brief text and the bounds as `plan.sidecar` (never an entry of `plan.nodes`) and writes the empty ledger; `launch --dry-run` prints them under `sidecar`. The exported graph and the registry entry show the node `sidecar` ("Review sidecar", kind `review`) right after `challenge` (first without one) and before every launch; `handoff` depends on it last.
- **Passes.** Each pass is one `claude --print` job with `--tools Read,Glob,Grep` (no Bash, no `--bg`) and structured output only (`$defs.output` of `contracts/workflow/sidecar.schema.json`), in its own process group, with `--add-dir` for `sidecar-inputs/<n>/` and every lane worktree. Its inputs: `manifest.json` (per lane its head commit, native state, completion, waiting question, deadline, diff and pane files, untracked and binary paths), `<lane>.diff` (`git diff <base>` as text, no `--binary`, then the untracked files; every Git command in a lane worktree runs with `GIT_OPTIONAL_LOCKS=0` and is killed after 60 seconds, which fails the pass), `<lane>.pane.txt` (the visible pane through Herdr, escape and control bytes stripped; absent without Herdr), copies of the lane's completion and questions files, `ledger.json` and `tasks/` (with `tasks/reviewers/`, the briefs `plan.reviewers` pinned, as context only). A run keeps the inputs of its last eight passes. The job's prompt is the brief, the project conventions (`plan.conventions`, none for a run prepared without them), then the controller's protocol, which sets the severity rule (operator decisions 4 and 12, never a reviewer brief's bar): P0 or P1 only for a defect the code, a check or a pane shows, work that contradicts a line of a task, of `decisions.md` or a safety line of the PRD, a failure the worker disclosed, or a security or data-loss risk; untested behaviour, risks and suggestions are P2. In automatic mode `wait_handoffs` polls each pass as a child: pass 1 at the first launch plus `cadence_seconds`, then on the cadence after the previous pass ended, and at once when a lane writes `completed` (a completion pass); never while one runs, never past `max_passes`. Once every lane's completion is accepted, a running pass is interrupted and the final pass runs (the only one past the budget); the handoffs are saved only after it is recorded while the deadlines keep being checked, so freeze waits at most one pass timeout. A pass past `pass_timeout_seconds` is `timed_out`.
- **Ledger.** `sidecar.ledger.json` is written only by the controller, under `sidecar.lock`, validated against the schema and replaced atomically; at most 4 MiB. New findings get `S-<n>` (within one output a new finding is cited by its `ref`, `new-<k>`); an upsert overwrites the finding and appends its disposition, revision, evidence and note to `history`. `verified_resolved` and `withdrawn` need evidence, `accepted_trade_off` a note, and reopening a terminal disposition evidence. An output with an unknown id, ref or lane, a duplicate id or ref, an illegal transition, more than 256 KiB, or that would push the ledger past 4 MiB is rejected as a whole: the ledger stays byte-identical and the rejection is an event. A pass that fails, times out or is interrupted is recorded with that status, and the run continues.
- **Messages.** The controller types a message into the lane's pane as `[Review sidecar S-n] <text>` (newlines as spaces), then Enter, only after a fresh gate: the lane's row is `working` or `idle`, the pane's foreground is `claude attach <id>` of that lane's session, and the visible screen shows an empty Claude Code input line (`❯` under a rule, down to the closing rule or to the end of the capture, which Herdr may end at the input). Otherwise it is `undeliverable` (`lane_blocked`, `pane_busy` for a dialog, a menu or a typed draft, `pane_not_attached`, `pane_unknown`, `herdr_unavailable`, `herdr_timeout`) and nothing is typed. It is `refused` before any gate for a lane not launched, a lane that went on (its completion, handoff or stop: a completion pass reviews the lane that just completed but never messages it), a lane with a question waiting (the operator answers questions), a second message to a lane in one pass, a lane with `max_messages_per_lane` delivered, and anything after freeze. The merged ledger with the messages `pending` is written before anything is typed; a controller stopped meanwhile leaves them `undeliverable` (`interrupted`). `<lane>.deadline.json` is never touched. Workers are told in their prompt and reply in their pane, which the next pass reads.
- **Events.** The node `sidecar` gets `running` when pass 1 starts and one `running` line per completed pass (counts only), `interactive` for a pass that failed, was rejected, timed out or was interrupted, for a message that failed on an error, and for an escalation (`escalation S-3 (security): see the sidecar page`); no model-written text goes into `events.jsonl`. Every escalation, and every finding a pass made an open P0 or P1 (new, raised or reopened) that no message of that pass delivered to its lane (refused, undeliverable or never sent), also writes a `sidecar` attention record on the finding's lane (runbook, "Attention records"), quoting the finding's or the escalation's first sentence; a P0 or P1 delivered to its lane does not. Each is written once, when the ledger first shows that the lane will not get it: an escalation (its event too) or a finding refused or never sent right after the merge write, before anything is typed; an undeliverable one when its delivery ends; one whose message a stopped controller left `pending` when the next controller records it `interrupted`. Freeze closes it `succeeded` with the counts (`no final pass` when none ran); a run stopped before freeze closes it `succeeded` too; a Ctrl-C or exit 75 writes nothing.
- **Manual runs.** `$PY -m workflow sidecar-pass "$RUN"` runs one pass synchronously; `--final` runs the final pass, which fills the ledger's `handoff`: run it before `freeze`. It is refused without a sidecar, while a pass runs, after freeze, past `max_passes` (except `--final`) and while `automatic-supervisor.lock` is held (an automatic run owns its passes; use it there only for debugging).
- **Export 1.6.0.** `run-state.json` carries the ledger as the top-level `sidecar` section (the empty ledger before the first pass, `null` without a sidecar); the Projects server reads the live file first. The post-freeze reviewers do not receive the ledger.

## Setup

From md-manager's root (Python 3.12 recommended):

```bash
python3 -m venv .venv
.venv/bin/pip install -r workflow/requirements.lock
npm ci
npx --no-install playwright install chromium
.venv/bin/python -m workflow.run_tests   # parallel by test class; or: -m unittest discover -s workflow -t . -v
npm run test:contracts
```

The tests use fake workers and reviewers with real Git worktrees, checks, checkpoints and headless Chromium; they make no Claude model calls. `test_portable.py` covers the portable-workflow scenarios, `test_guardrails.py` the guardrail scenarios (with a fake challenge job and a fake Herdr), `test_sidecar.py` the review sidecar scenarios (a scripted fake print job, a fake Herdr, real lane worktrees), `test_browser_rules.py` `check-report` and the browser scenario rules, `test_repair.py` lane repair, `test_attention.py` the attention record, `test_replay.py` the review replay (a fake print job); `testdata/` holds copies of finished features' files the tests read. The test modules whose runs can record attention point `MD_MANAGER_PROJECTS_CONFIG` at a temporary registry, so `attention.jsonl` never lands beside yours.

## Files

- `launch.py`: target resolution, feature scanning, validation (placeholders, bundled briefs, the 2.2.0 guardrails, the 2.3.0 sidecar declaration) and the one-command launch.
- `sidecar.py`: the review sidecar: its declaration and `plan.sidecar`, the pass inputs, the read-only print job, the ledger merge and its schema checks, the gated message delivery, restart recovery, the scheduler `wait_handoffs` runs and `sidecar-pass`; `prompts/sidecar/` holds the bundled briefs.
- `guardrails.py`: outcome briefs, decisions pinning, the design challenge and `resume`, worker questions, the persisted deadline pause and `answer`. `skills/workflow-grill/`: the interview skill.
- `scaffold.py`: `init`. `registry.py`: the Projects registry entry and its atomic merge.
- `attention.py`: one record per state that needs the operator: `<run>/attention.json` and a line on `attention.jsonl` beside the Projects registry, never repeated for a state until `resolved` forgets it; it never raises and waits at most 5 seconds for the feed's lock. The module is callable, so `from . import attention as attention_record` records with `attention_record(...)`.
- `sessions.py`: run preparation (one worktree per selected lane, then the shared .git digest), lane id rules, receipts, locking, and the `claude` process helpers (`run_claude`, `popen_claude`: the auto-updater off and the controller's Git configuration left out, an update in progress waited out; `background_settings`: the same setting and the background isolation off as `--settings` for `claude --bg` sessions; `worker_settings`: a worker's `--settings` with its deny rules, see "What a worker can reach") with the stale-process warning.
- `interactive.py`: native `claude --bg` launches, Herdr panes (one per lane, reviewers to their right), reconciliation, `attach-one`. `herdr.py`: the Herdr CLI helper.
- `pipeline.py`: the supervised graph over the plan's lanes, freeze/ownership, verification, candidate, review, approval, integration and the CLI.
- `repair.py`: `repair`, lane repair after freeze: `repairs.json`, the deterministic snapshot commits, the attempt floors, the checkpoint fork at the freeze boundary and `--workspace`.
- `automatic.py`: unattended supervision, completion signals, the native/print reviewers (one per declared reviewer, each one's verdict derived from its findings, unanimous) and the severity rubric every reviewer gets; `prompts/review.md` is the built-in brief, `prompts/reviewers/` the bundled ones.
- `replay.py`: `python -m workflow.replay`, the review replay: past runs' reviewers rerun with this checkout's prompt on scratch copies without their recorded verdicts, the print reviewer's own prompt, command and schema, at most two jobs at a time, and a tally of raw and derived verdicts.
- `verification.py`, `checks.py`: policy validation against the bundled `contracts/workflow/` schemas and isolated check execution (`check_environment`: no secret-like names, recorded in the packet); `checks.py` also holds the browser scenario rules that the verifier and `check-report` share.
- `export_state.py`: the versioned `run-state.json` export (1.7.0).
- `worktrees.py`: every `git worktree` change, one at a time per repository, retrying Git's own lock errors; the controller's own Git configuration (hooks and fsmonitor off, added at `python -m workflow` entry and by `pipeline.main` and `launch.main`, and left out for Claude processes, Herdr and the checks) and the shared .git digest that freeze, review and integrate compare (it also covers the global attributes file and `~/.config/git/config`).
- `requirements.txt` / `requirements.lock`: bounded Python dependencies, installed separately from the Node application.
